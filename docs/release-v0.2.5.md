# Saker 0.2.5

Saker 攻防平台（猎隼）0.2.5 版本。本轮从 0.2.3 起累计 **13 个提交、70 个文件变更**（**+1037 / −320**），
核心是**对 dsh 0.1.5-rc.1 的破坏性变更做完整适配**，并在真实宿主上把用户反馈的每个问题逐条修到位，附带一轮可量化的性能优化。

> 验证环境：DeepSeek Harness `0.1.5-rc.1-183f08e`（**全部修复均在安装版实跑验证**，非静态差分） · Node.js `>=22.5`

## 一、适配 dsh 最新版（0.1.5-rc.1）

0.1.5-rc.1 对插件运行时上下文做了破坏性调整，**静态 API 差分发现不了**，是实跑才暴露出来的。

### 1.1 `connection` 服务的依赖注入收窄

| | 0.1.5-rc.1 之前 | 0.1.5-rc.1 |
|---|---|---|
| `connection` 的 inject | `["webServer", "credentials"]` | `["credentials"]` |
| 路由注册归属 | 消费方插件 | **调用方插件**（`owner.webServer`） |

后果：沿用 `connection.rpc.handle(channel, handler)` 的插件，其 getter 用 `this.ctx` 当 owner ——
在 0.1.5 下 **不绑定消费方插件**，`owner.effect(() => owner.webServer.register(route))`
**静默注册失败且不抛任何错**。表现是设置页永久停在「加载中…」、HTTP 探测通道返回 404，日志里一句报错都没有。

**修法**：改用 `connection.register(ctx, channel, handler)` 显式传插件自己的 `ctx`，
并确保该插件的 inject 里带 `webServer`（否则会抛
`cannot get property "webServer" without inject`，而且是**插件整体加载失败**，不只是 RPC 不可用）。

涉及 6 个插件：`method-stack` / `skill-browse` / `knowledge-hub` / `sec-config` / `mcp-studio` / `webshell-mgr`。

### 1.2 实测结论：这类问题只能靠实跑

本次专门验证了一条工程结论并写进项目规范：
**「逐包 API 差分通过」≠「在真实宿主上能用」**。0.1.5 的上述变更全部属于运行时上下文行为，
类型层面完全看不出来。此后所有适配一律以「在安装版上端到端跑通」为验收标准。

### 1.3 适配后实跑基线

| 项 | 结果 |
|---|---|
| 设置页分区 | **10 / 10** 渲染正常（无「加载中…」残留） |
| 插件 RPC 路由 | **12 / 12** 已注册 |
| 插件加载失败 | **0** |
| 模式菜单 | 渗透测试 / 代码审计 / 标准（三项齐全） |

## 二、修复问题

本轮修复的都是**实跑挖出来的真缺陷**，不是代码审阅的猜测。

### 2.1 工具探测：Windows 上每个工具都被误判「未安装」 ⚠️

- **现象**：装配期给模型的工具面永远显示 0/13 就绪，把模型推向无谓的三级兜底。
- **根因**：`where <名字>` 补扩展名依赖环境变量 `PATHEXT`，而宿主进程的 env 里
  `PATHEXT` **是 `undefined`** —— 于是 `where node` 返回 1、`where node.exe` 返回 0。
- **修法**：不再 spawn 任何进程，改为 **Node 侧 PATH 直扫**（自带扩展名候选，不依赖环境继承）；
  `where` 仅作 App Paths 兜底并显式补 `PATHEXT`。
- **效果**：playbook 依赖由 **0/13 → 8/13 就绪**，与机器实况一致。

### 2.2 模型看不到「目录里的自有马」 ⚠️

- **现象**：设置页明明显示 17 个自有马，模型调 `webshell_library_list` 却报 **0 个**。
- **根因**：设置页走 `self-list`（**目录扫描**，「目录即库」），而模型工具只读已登记的
  **元数据** `WS_CFG.selfShells` —— 两者**不同源**。手工拷进目录的马界面看得见、模型看不见。
- **修法**：抽出唯一真源 `listLibraryShells()`，`self-list` RPC 与两个模型工具全部改走它。
- **效果**：模型报告「自有马 **17** 个（JSP 10 + PHP 7）」并能读取具体马源码。
- **回归锁**：新增测试「库列举同源」，锁住两条路径不会再分叉。

### 2.3 MCP 挂载失败后永不重试 ⚠️

- **现象**：Burp / Yakit 明明已启动，界面却一直显示「不可达」，**只能重启宿主**。
- **根因**：挂载只在插件启动与「配置签名变化」时做一次。典型时序是
  **先起 dsh、后起 Burp/Yakit** → 首次连接注定失败，之后不会因服务上线而重试；
  而界面的「立即挂载」在配置未变时是**空操作**（签名相同 → 不重建挂载）。
- **修法**：加**自愈看门狗** —— 以「工具可见性」为准（这才是对模型有意义的事实），
  已挂载但零可见工具的服务按 15s 起**指数退避强制重挂**（封顶 5 分钟）；
  删除/停用的 server 同步清账。另加只读诊断端点便于定位。
- **效果**：实测临时挂一个死端口服务，看门狗 3 次重挂（15s→30s→60s）、真服务**零误报**；
  真实服务 `connected 2 / 80 工具`。

> 顺带澄清一个长期困惑：**状态徽章反映的是「工具视图里有没有 `mcp__<名字>__*`」，
> 不是连接状态**。所以「诊断能连上、界面说不可达」不是矛盾——诊断是独立的新连接。

### 2.4 安装器：`install-all.mjs` 变量声明被行注释吞掉

`const installed = new Map()` 被上一行的注释末尾吃掉，导致安装阶段必抛
`ReferenceError: installed is not defined`——而**打包阶段 `pack-all` 22/22 全绿**，
完全掩盖了问题。

**工程结论已固化：打包通过 ≠ 装得上，这是两道不同工序，发布前必须都跑。**

### 2.5 scanner-tools：ffuf 证据被 stdout 覆盖 + 回读指针跨平台分隔符

ffuf 的 JSON 输出在回读时被后续 stdout 覆盖，证据丢失；回读指针使用 POSIX 分隔符，
在 Windows 上定位不到文件。两者均已修复。

### 2.6 RPC 路由未注册 / 标准模式缺失

- RPC 路由静默注册失败（见 1.1），导致部分设置面板永久「加载中…」。
- **标准模式**在预设里不可见，日常办公场景无法切回通用 Agent —— 已恢复。

### 2.7 界面：WebShell 设置页合并为「单一库视图」

原先「我的 webshell / 内置马模板库 / 已登记连接」三张并列卡片，操作者要在三个列表之间对照。
现改为**一个库**：

- 行首**来源标签**（自有上传 / 内置模板 / 已登记连接）+ 来源计数过滤
- 按 **语言 → 绕过形式** 两级分组，组内按来源排序
- 语言下拉 + 关键词搜索 + 展开/收起

**绕过方式与连接密钥全部保留**：自有条目行内可改语言/绕过形式、可改密；
内置模板保留参数与默认口令；已登记连接仍显示明文口令（模型侧脱敏）。

## 三、性能优化

### 3.1 安装器：pnpm 在 Windows 上自锁死（阻塞级）

升级根包（1674 文件 / 17 MB）时**卡死 9 分 43 秒**。定位过程：

| 观测 | 值 | 推论 |
|---|---|---|
| TCP 连接 | **0 条** | 不是网络问题 |
| CPU 时间 | 68 秒 / 583 秒 | 基本在等锁 |
| 目标目录 rename | **被拒** | 目录被占用 |
| kill pnpm 后立刻重试 | **成功** | **持有者就是 pnpm 自己** |

**修法**：安装前先用 Node `fs.rmSync` 删掉旧目录（不走 shell，避免被外部安全删除机制拦截）。

**效果**：根包升级 **9 分 43 秒（失败） → 45 秒（22/22 通过）**。

### 3.2 工具探测：从「每工具一次进程 spawn」降为 **零 spawn**

原先每个工具探测都要起一次子进程；改为 PATH 直扫后，13 个依赖工具的探测
**不再产生任何进程**，装配期同步调用开销显著下降，且不再受环境变量继承影响。

### 3.3 提示词瘦身：persona 9244 → 8940 字符

移除平台级元防御条款（**语义保留、不再以「纪律」命名**），删除与 Iron rules 重复的
whoami / 上传路径限定，合并重复的授权假定表述。方法正文里的
`纪律：…` 统一改写为 `边界：仅做无害最小验证。`（26 个方法全覆盖）。

### 3.4 测试套件：从「只有 4 套能跑」到 **15 套 / 968 断言全绿**

补齐测试桩（解析宿主裸包与 `@dsh-external/*` 子路径导出），使 15 套套件真正可运行。

> 平台差异说明：部分套件写于上游 9 模式平台，含 redteam 与八专业用例，
> 而本发行版代码侧只有 `pentest` / `code-audit` 两个模式 —— 这类失败按**发行版差异**判定，
> 已在测试输出中显式标注「本发行版适用」的通过数。

## 五、安装 / 升级

```bash
# 1) 取本版本源码
git clone https://github.com/ITroyeSivan/Saker.git
cd Saker

# 2) 一键安装到 dsh 的 web profile（会按版本号跳过已是最新的包）
node scripts/install-all.mjs

# 3) 重启宿主
dsh web
```

> 升级提示：`install-all.mjs` 按 **package.json 版本号**跳过同版本包。
> 如果你自行改过插件代码，务必同时升版本号，否则不会重装、改动静默不生效。
