## 是否白费 token

这次实际界面观察记录 90 次本地请求，主要是已有的设置和任务状态轮询；没有模型提交或任务启动请求。专用会话的原生 transcript SHA256 前后完全相同。打开页面、展开成本、查看历史、调整人数本身没有新增模型调用。轮询仍有本地性能成本，后续应整合订阅，不能称为零成本。

界面显示的历史记录不等于自动注入模型的全文。上一版的[原生传输审计](../task-prompt-cost-2026-10-09/README.md)确认，41 个工具定义共 35,762 字节，其中 redteam 的 10 个工具为 13,662 字节。登记与更新两个声明共 6,540 字节，是值得继续优化的具体来源。字节不是 token 计费数据；本版未改变这些模型工具定义，也未捕获新模型传输体，**不能把这次 UI 整理宣称为 token 节省**。

证据登记、回执、独立验证、交付闸门和预算守卫仍有明确用途。更高优先级是使工具说明按模式和当前操作加载，并用真实模型回合证明没有增加猜字段、重试或错误确认，而不是删除验证机制来缩短上下文。

## 工具启动检查：G0 的一部分

安全配置的工具库增加“检查启动”，只对已保存路径执行内置固定帮助/版本参数，使用与扫描工具一致的解析器。没有保存的路径、旧路径、未知探测方式、安装程序、超时、依赖失败、输出不完整及标识不匹配分别显示原因，不靠文件存在或退出码 0 判可用。不会自动安装或更改路径。

Desktop 实际点击 16 项：

| 结果 | 工具 |
|---|---|
| 可启动，10 项 | nmap、sqlmap、httpx、subfinder、afrog、nuclei、dirsearch、ffuf、katana、semgrep |
| 已保存入口不存在，4 项 | bloodhound、kerbrute、mimikatz、impacket |
| 尚未提供固定检查，2 项 | fscan、jwt_tool |

“可启动”只证明本机返回预期帮助/版本，**不证明目标请求成功或模型已经加载该工具**。这是 G0 的启动诊断部分，尚未实现每项任务的必需能力就绪判定。

第一轮 Desktop 验收曾发现前端误读 RPC 包装：后台 ffuf 帮助成功，但界面显示“读取启动检查失败”。修复读取 `result.value.check`，加入实际包装和反向检查后，16 项实际结果均正确显示。保留这次失败，不能把第一轮单测全绿当作已验收。
