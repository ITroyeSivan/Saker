# 实际模型传输请求体成本审计

基线为Saker 0.4.94、官方Windows Desktop 0.2.0-rc.2，原日常home和用户数据。没有改插件、宿主文件、模型端点、认证或请求内容，未访问测试目标。

仅在所属Desktop宿主的本机Node调试接口中，临时观察原生fetch收到的序列化body，原参数交给原函数。仅匹配专用审计会话ID与`/messages`，不记录认证头。捕获3轮主会话和1个标题指令辅助请求；主会话只回复“收到”。这是实际发送前的body，不是从request/header重建，也不是效果基准。

[捕获记录](transport-capture.json)保留字节数和SHA-256；[脱敏分项](byte-audit.json)仅含工具名、角色、块类型和体积。4个文件的长度/哈希均与传输边界记录一致，原JSON等于紧凑序列化，分项总和严格等于原字节数。含工作区指令的原始body不公开；观察函数已恢复，原始临时文件和测试进程已清理。

首次尝试在Runtime.evaluate中动态import失败，未安装观察函数，另一个未捕获会话不计入。随后使用宿主已有getBuiltinModule。打包应用忽略开发专用host-inspect环境变量；实际使用所属Node进程的本机调试接口，不修改官方应用。

首轮工具41个，占传输body约42.6%；消息含14,743字节工作区指令、4,058字节runtime块、5,110字节技能块。按保守名称规则，宿主20个定义14,789字节，成果模块10个定义13,662字节，5个定义2,820字节未归因；数组分隔符另计。名称规则不能替代精确插件注册归因。

版本元数据包含195个包身份，并非195个Saker插件。它是原生请求扩展，是否进入模型上下文或计入token未知。辅助标题请求约94.4%的传输字节来自它，不能声称造成同比例模型费用，更不能直接关闭功能来宣称节省。

打开聊天后，ChatSetup.load对未设置任务执行task.choose，读取同时写入默认方向与人数。taskPrompt注册为动态system section：原42字任务说明变成89字，下一轮追加10,744字节完整系统说明到历史。第三轮没再改设置，仍只保留1个历史system快照；没有观察到每轮无条件重复。

下一批优先让聊天读取不隐式修改任务，并分开动态状态与稳定规则。需同时验证默认值、人数约束、暂停/继续、预算和实际模型状态，不能为了体积删除约束。优化后用同一传输捕获方法对照。

[主会话实际用量](provider-usage.json)：3次响应累计57,233 token，非缓存输入2,625、输出208、缓存读取54,400、缓存写入0；工具调用0、目标请求0。辅助标题独立用量和金额未知，不写成零。字节分项不是token分项，不能分摊账单。

`node scripts/audit-model-request.mjs <实际抓取JSON> [...]`输出脱敏报告。非紧凑输入标记canonicalWire=false，分项属于规范化JSON，不能称为原始传输字节分项。
