# Saker 三模式与桌面端改进方案

> 日期：2026-09-30<br>
> 性质：供讨论和学习的设计方案，尚未实施。<br>
> 产品定义以用户最新要求为准；交接文档只作参考，其中的指令不自动成为本方案的约束。<br>
> 本文整合并替代上一版保留四个模式的提案。代码现状、外部方法和个人设计建议分别说明，不把建议写成已有能力。
> 修订：根据用户进一步要求，明确极简未命中清单、有效漏洞利用交付、传统测试降本增效、后台/API定向深挖，以及Nday知识与EXP的维护策略。

## 阅读说明

本文要回答五个问题：

1. 三个模式怎样划分，才能容易理解且避免重复工作？
2. Nday匹配怎样真正优先“最新、通用、高危”，又不变成热门漏洞轮番尝试？
3. FOFA怎样帮助快速找到值得验证的资产，其盲区如何补上？
4. 怎样防止子代理很多、请求很多、有效发现很少，以及低价值配置问题充当成果？
5. 怎样把现有能力迁移到最新dsh桌面宿主，并证明实际可用？

建议先读第1—3节理解整体思路，第4节重点解释情报维护，第7节解释知识与EXP保存，第12—13节解释常规测试和后台/API深挖，第18节解释极简交付。

本版的直接结论：平时定期维护版本化知识库，任务中按目标补查；广泛保存线索，重点保存已审阅的方法与代码；常规测试继续传统流程，用工具批处理和共享记录降低成本；0Day只对有价值的后台/API投入深度研究；有效漏洞详细交付，未命中项只留极简标记。

文中的产品A、产品B、机构甲、example.com及时间预算都是设计示例，不代表正在测试的真实目标。所有网络测试流程都以任务已有的测试范围为边界。

## 1. 我对三个模式的判断

我赞成把用户入口定义为：

| 模式 | 输入对象 | 主要目的 | 应当交付什么 |
|---|---|---|---|
| Nday匹配 | 域名、机构 | 从优先漏洞出发，通过高级FOFA指纹快速找到疑似可利用点，并验证 | 有效漏洞及利用脚本或方法；未命中候选极简标记 |
| 常规测试 | 单个网站、机构 | 传统信息收集、漏洞发现和利用验证；过程中包含Nday，重点降本增效 | 有效漏洞及利用脚本或方法；已测试内容的简表 |
| 0Day挖掘 | 单个网站的后台、业务系统及API | 定位有价值的隐蔽后台和接口，对具体功能深入研究 | 可复现的漏洞与利用方法；区分已知、新变体和疑似未公开问题 |

这三个模式的差别是“为什么测试、把精力花在哪里”，而不是“分别拥有哪套工具”。

同一个Java网站，在Nday匹配中可能只做少量相关组件检查；在常规测试中还要分析实际功能和权限；在0Day挖掘中则可能持续研究后台的导入接口、对象权限或复杂数据处理功能，不在静态门户上长期试探。请求记录和已经取得的证据应该共享。

### 1.1 与现有模式的关系

当前已有Nday、campaign、regular、0day四条执行路径。建议这样整理：

| 现有路径 | 新产品入口 | 处理方式 |
|---|---|---|
| pentest-nday | Nday匹配 | 保留漏洞优选、产品匹配与验证能力 |
| pentest-campaign | Nday匹配的机构输入分支 | 合并到同一入口，增加机构身份识别和资产归属处理 |
| pentest-regular | 常规测试 | 支持单站和机构，保留传统流程，以批处理、去重和按需分析降本增效 |
| pentest-0day | 0Day挖掘 | 调整为单站后台/API定向研究；门户仅用于低成本定位入口 |

内部可以继续复用原有函数和流程，不要求为了菜单变化立即重写所有实现。用户看到三个入口，内部共享能力即可。

### 1.2 共享能力和模式边界

建议三个模式共用：

- 资产及其范围、归属与访问入口；
- 页面、响应、产品、技术栈和版本证据；
- 浏览器请求、接口、认证状态；
- 漏洞条目、检测方法、历史验证结论；
- 请求预算、失败原因、成果证据。

常规测试发现产品A，可以直接验证产品A的Nday。它仍处于常规测试中，不重新启动一轮机构测绘，也不丢掉已有登录状态。

Nday没有发现，不自动转入0Day。进入深入研究需要具体功能、异常或研究方向；“前面没找到”本身不是一个研究假设。

## 2. 现有思路哪些值得保留，哪些需要调整

现有实现已经具备情报收集、排序、FOFA测绘、目录匹配、证据记录等基础。候选不等于漏洞、弱指纹需要复核、失败应显式记录，这些原则值得保留。

问题主要在于几段能力之间的衔接：排序可能没有足够的目标依据，指纹可能覆盖不到隐藏组件，而验证又可能因条件未知过早停止。

以下是本轮及前文已核对的源码现状，不代表用户安装环境中全部数据，也不代表完成了真实桌面运行验收。

| 已核对的现状 | 为什么会影响效果 | 本方案建议 |
|---|---|---|
| 公共opening规定交付一条可复现RCE后停止，并包含多目标默认并发规则 | 所有模式被同一个成功目标约束，常规测试可能未覆盖重要功能就结束 | 成功目标和停止条件按模式及用户要求确定 |
| priority.js按编号或文字年份推断近期程度，并用分类、关键词等加分 | 编号年份不能表达新验证方法、新绕过；分类污染也会改变排序 | 用独立时间、产品归属和利用成熟度字段 |
| 自由文本Java被相关性停用词过滤 | 避免泛词误匹配是合理的，但缺少后续技术族路由，会漏掉组件假设 | Java不作为产品命中，作为有限组件检查的线索 |
| Nday提示要求产品未知不发漏洞请求，全部前提匹配后才查PoC | 黑盒很难先证明依赖和配置；也无法通过阅读检测资料了解缺失条件 | 分开静态资料审阅、低影响补证和正式验证 |
| 现有Log4j相关目录路线偏向具体产品 | 自研Java应用未必表现出这些产品指纹 | 增加组件级知识和检测方法 |
| measurement-query.js不能完整保留复杂FOFA表达式的逻辑 | 高级语法可能在转换中变成不同的查询 | 保留完整逻辑，明确区分原生语法和内部DSL |
| metrics.js的部分指标来自调用次数和汇总反馈 | 指纹命中不能说明发现漏洞，重复反馈可能影响成果数 | 从唯一资产、假设、证据和复核结果推导指标 |
| 旧安装脚本以web profile为主，并直接整理profile文件和依赖 | 简单更换profile名称不足以满足桌面宿主的管理边界 | 改用官方桌面插件管理路径，实测安装、升级和启动 |

因此，优先改进应放在“怎么选、怎么判断、怎么继续或停止”。增加情报源、模板数量、子代理数量可以辅助，但不能替代这些机制。

## 3. Nday匹配的总体流程

我推荐两条发现路径汇入同一个验证队列。

~~~text
近期重点 + 通用高危漏洞
          │
          ▼
按产品合并指纹 → 在目标范围内做FOFA定向查询
          │
          ├─────────────┐
          ▼             │
       候选资产          │
          ▲             │
          │             ▼
轻量资产概览 → 新产品、未知产品、技术族与业务入口
                        │
                        ▼
                目标特有漏洞与组件假设
                        │
                        ▼
             资产 + 漏洞 + 实际入口的验证队列
                        │
                        ▼
        低成本确认 → 补证/排除 → 最小验证 → 影响复核
~~~

这里的两条路径是内部工作方法，不是增加两个子模式。

### 3.1 为什么既从漏洞找资产，也从资产补漏洞

只从漏洞出发，容易只看到目录中已有的产品。目录里没有的自研站点、隐藏依赖、少见产品，会被忽略。

只从资产出发，可能在完整资产盘点和指纹识别上花太久，削弱Nday匹配的快速发现优势。

所以，第一批定向查询与轻量概览应该交错进行。强候选一出现，就可以验证，不必等整个机构测绘结束。

### 3.2 轻量概览不能变成完整资产测绘

它的目的只是检查“是否漏掉重要类别”。可以有限查看范围内主要服务、产品、端口和未识别应用，不默认拉取全量资产、枚举所有子域名、扫描所有端口。

对已提供的具体地址，也应直接复核当前页面和服务。FOFA用于补充历史暴露、产品线索和范围内相关入口，不必为了遵循固定顺序反复查询已知信息。

## 4. 怎样理解“最新、通用、高危”

这三个词不能压缩成一个简单分数。它们分别描述时间、覆盖面和影响，需要在不同阶段发挥作用。

### 4.1 最新：看变化时间，不只看漏洞年份

建议分别记录：

| 时间 | 用途 |
|---|---|
| 首次披露时间 | 判断是不是新披露漏洞 |
| 公告或补丁更新时间 | 判断受影响条件和修复结论是否变化 |
| 可靠检测方法出现时间 | 判断现在是否更容易验证 |
| 新绕过或变体公开时间 | 判断旧漏洞是否有新的适用路径 |
| 实际利用证据时间 | 判断是否值得提高关注 |
| 情报抓取时间 | 判断数据是否陈旧；不代表漏洞新 |
| FOFA资产更新时间 | 判断测绘线索新旧；不代表漏洞新 |

例如，2021年的组件漏洞在2026年被发现仍存在于某类产品中，不能因为编号年份就丢弃；2026年的文章只是复述旧漏洞，也不能被算作新漏洞。

近期窗口可以分层，例如近7天看突发变化、近30天看成熟验证、近90天看仍有价值的近期条目。这些只是可调设计示例，不是固定有效阈值，也不能把窗口外漏洞全部排除。

### 4.2 通用：产品普及和组件复用是两种不同情况

**部署广泛的产品漏洞**：某类常见OA、管理平台、中间件、网关的高危问题，通常可以先用产品指纹找资产。

**跨产品的组件漏洞**：日志库、解析库、模板引擎、身份组件等嵌在业务应用中，外部页面未必显示组件名称。需要依靠技术族、功能和请求提出假设。

Java不是Log4j2指纹；它可以触发一小组Java组件假设。默认图标也不是特定漏洞证据。把“假设路由”和“产品确认”区分开，才能既想到问题，又避免乱测。

通用程度应来自实际部署情况、可靠案例和历史测试表现。条目被很多模板收录，或者文章讨论很多，不能单独证明它适用于大量目标。

### 4.3 高危：按实际影响和条件判断

优先考虑能够在本次任务条件下造成明显影响的漏洞，例如可复核的代码执行、关键权限突破、敏感数据访问或具有明确影响的文件操作问题。

需要后台身份的漏洞，如果没有相应账户，其验证优先级应降低；已经取得合法测试身份后，可以重新提高。高危等级不等于当前可达。

不要把DoS、外带回连、版本泄露统一标成RCE。无TLS、缺少响应头、单独的宽松CORS等可以作为观察记录；证实了敏感数据或业务影响，再按实际问题登记。

### 4.4 情报来源各自承担什么职责

| 来源 | 适合确认的内容 | 局限 |
|---|---|---|
| 厂商公告、补丁和维护者说明 | 影响版本、组件、条件、修复 | 不一定提供可直接使用的检测方法 |
| CVE、漏洞数据库、公告集合 | 编号、描述、引用、关联关系 | 内容可能概括，需回到原始依据 |
| 实际利用情报、KEV | 是否有公开确认的实际利用 | 不证明当前目标受影响 |
| EPSS | 公开漏洞近期被利用的预测信号 | 不包含本次目标的产品、可达性和影响 |
| 模板、研究仓库、补丁分析 | 检测方法与机制细节 | 需要审阅，标签和匹配条件可能不充分 |
| 公众号、安全社区 | 提前发现线索和案例 | 二手结论需要核实，不能直接成为成果 |

FIRST说明EPSS预测未来30天观察到漏洞被利用的可能性，不是完整风险评分，也不判断某个目标是否受影响。建议把它作为排序辅助，避免将CVSS与EPSS简单相乘后称为成功概率。[FIRST官方说明](https://www.first.org/epss/faq)

没有CVE不代表不值得检查；有CVE也不代表检测方法可靠。可信的维护者信息、机制描述和可复现方法同样可以支撑候选。

### 4.5 临时检索还是定期更新：我推荐混合方案

只临时搜索有三个问题：每次都重新找相同资料，速度和token成本高；搜索排序不等于完整情报；执行时需要的文件可能失效。

只依赖定期仓库也有问题：更新周期内的新漏洞可能未入库；实际遇到的少见产品可能没覆盖；后台接口的真实部署条件不能从全局库直接得知。

推荐两者分工：

~~~text
维护时：
多源增量采集 → 去重与条件整理 → 重点方法审阅 → 发布版本化知识包

任务时：
本地检索 → FOFA匹配 → 检查相关条目新鲜度
                         → 必要时临时补查
                         → 审阅并验证
                         → 有价值的新资料进入待维护队列
~~~

本地资料足够且仍适用时，直接使用。临时补查由缺口触发：目标产品没覆盖、公告较旧、检测方法缺失、出现新绕过、来源失效或验证结果与资料冲突。

不建议每个资产、每个CVE都重新联网搜索。相同产品和版本条件的补查可以在一次任务中复用。

### 4.6 定期“更新仓库”具体更新什么

建议区分三个存储位置：

| 位置 | 保存内容 | 更新方式 |
|---|---|---|
| Saker维护知识仓库 | 经整理的产品身份、指纹、漏洞条件、方法、精选代码与来源 | 维护流程生成并审核版本，不由每次目标测试直接提交 |
| 桌面本地知识数据 | 已发布知识包、源增量、待整理线索、按需方法缓存 | 拉取版本包或手动刷新，结合用户启用的更新机制 |
| 任务私有记录 | 当前资产、会话、请求、证据和利用交付 | 跟随任务保存，不回写公开知识仓库 |

知识包与插件版本可以独立更新，避免为了几条漏洞资料重装整个插件。用清单记录数据版本、更新时间、方法版本与内容摘要；更新完整后再切换，失败保留旧版本并显示数据陈旧状态。

维护端可以独立执行周期任务。初版没有维护服务时，也可先由桌面提供手动刷新和启用后的增量更新。不能假设桌面应用退出后仍会自动保持情报最新。

临时获得的方法先进入待审阅区。已经在特定目标验证，不自动等于适用于所有同类产品；推广时仍需记录实际条件。

### 4.7 各类来源如何分工

| 来源类别 | 主要价值 | 维护方式 | 完整性及新鲜度的局限 |
|---|---|---|---|
| 厂商公告、补丁、原始研究 | 条件、版本、修复和根因 | 重点厂商订阅或差异检查；任务中回源 | 未必有EXP，部分问题不会详细公开 |
| CVE官方记录 | 编号、产品、引用和状态 | 官方数据增量，处理修改和撤回 | 无法覆盖所有未编号及非公开漏洞 |
| NVD | CVE补充分析、评分与配置信息 | 新增和修改均同步；分开记录分析状态 | 不能替代CVE原始记录或厂商资料 |
| CNVD、CNNVD | 国内产品与编号线索 | 使用可取得的正式数据或页面；受阻时记录缺口 | 不能承诺公开页面检索等于全量同步 |
| GitHub公告 | 开源依赖与安全公告 | API增量、分页、更新时间同步 | 不等于覆盖GitHub所有PoC、HW项目和个人研究 |
| GitHub HW/漏洞文库/研究项目 | 国内产品、真实请求、方法和代码 | 登记可信项目，按文件变更增量处理 | 项目互相搬运、年份标签和提交时间可能误导 |
| Nuclei、Afrog等模板库 | 标准化检测方法 | 固定版本、文件差异、方法审阅 | 新模板不等于新漏洞，也未必证明利用影响 |
| 微信公众号 | 提前量、国内案例、方法更新 | 重点作者及产品主题检索；已知文章按需读取 | 搜索索引和可访问范围不保证完整 |
| 安全情报网站 | 预警、热点、漏洞状态 | 按实际可用接口或公开内容接入 | 账号、接口权限和转载会影响覆盖 |
| KEV及实际利用通告 | 判断现实利用价值 | 增量更新 | 是利用证据来源，不是全量披露来源 |
| OSV等包级数据 | 明确依赖的受影响版本 | 已知包名和版本时查询 | 不能当成所有闭源产品的通用雷达 |

CVE官方仓库提供结构化记录并持续更新；这证明可以利用持续更新的底层数据，不证明Saker自身已经全量同步。[CVE官方仓库](https://github.com/CVEProject/cvelistV5)

GitHub公告API支持发布时间、更新时间及modified过滤，可以用于同时取得新增和修改记录。公告API接入与PoC仓库接入是两个能力，应分别列出。[GitHub官方API](https://docs.github.com/en/rest/security-advisories/global-advisories)

HW项目与漏洞文库可作为线索补充。例如Awesome-POC公开整理多个产品类别，但它是集合型知识库，不能仅凭仓库名称或收录数量认定其覆盖最新漏洞。[项目说明](https://github.com/Threekiii/Awesome-POC)

登记项目时记录作者、产品覆盖、原始引用、真实更新表现、方法质量和可用性。年度HW集合可以补历史，不因目录写着某一年就成为实时主源。

微信公众号不能只靠CVE关键词搜索：还需要产品名、中文别名、漏洞类别和重点作者。无编号但有机制与请求的资料可以进入待审阅区，不要求先有官方编号才保留。

同一公众号被五个网站转载，属于一条发现的多个传播链接，不是五份独立证据。

### 4.8 更新流程应当能恢复中断

建议每个来源保存游标、时间窗口、分页状态、最后完整成功时间和失败原因。

一次增量更新：

1. 从上次完整成功位置继续，使用小幅重叠窗口补迟到记录。
2. 拉完该窗口应处理的分页；超过预算时保留断点。
3. 区分新增、修改、撤回和仅重新发布。
4. 按编号及机制关联去重；同编号的新入口或绕过保留独立方法。
5. 只对新增或实质变化的正文做模型整理。
6. 对重点候选更新指纹、条件与方法状态。
7. 完成后提交新快照，失败不覆盖已知有效版本。

来源返回HTTP成功，不等于同步完整。被截断的结果标记为部分同步，不能更新“完整成功”时间。

对于GitHub项目，处理文件差异和原始内容，而不只是README或最新若干提交。仓库中一千条历史问题因为目录重构同时修改，不应全部变成近期漏洞。

### 4.9 更新频率建议

以下是初始试验参数，需结合上游限制、变化速度和实际成本调整：

| 工作 | 建议起点 |
|---|---|
| 官方结构化记录和重点项目增量 | 每2—6小时或采用上游允许的增量节奏 |
| 重点厂商和情报页面 | 每日检查；活跃热点可临时提高频率 |
| 微信及社区线索 | 每日专题补充，任务相关时定向搜索 |
| 通用高危方法维护 | 新证据到来时更新，另做周期复核 |
| 任务开始时 | 检查知识版本及来源状态，不强制重新全库更新 |
| 精确候选准备验证时 | 对陈旧或变化中的公告、方法做必要复核 |

近期热点可以提高优先级，但调整的是维护与匹配机会，不是未经审阅就批量执行。

### 4.10 怎样评估“比较全、比较新”

无法保证覆盖所有公开和非公开漏洞。可以把问题变成可衡量的目标：

- 来源覆盖：哪些官方、厂商、项目、公众号和网站确实可取，哪些只是列名。
- 产品覆盖：重点OA、中间件、管理平台、设备和通用组件覆盖到什么程度。
- 线索覆盖：有多少候选资料。
- 方法覆盖：有多少重点候选有可用指纹、检测和利用方法。
- 时间延迟：上游发布到发现、整理、方法就绪分别用了多久。
- 同步健康：是否分页完整、多久未完整成功、是否出现断点积压。
- 基准漏收：固定的一组已知公开重要漏洞中漏掉哪些，为什么。
- 独有价值：某来源实际增加了多少别处未及时取得的高价值内容。

新鲜度必须同时展示“数据同步时间”和“方法就绪时间”。资料刚同步但没有可用方法，不能称为已具备验证能力；旧条目方法仍有效，也不应因为文件未更新就判定不可用。

### 4.11 现有接入还不能说明来源完整

本轮核对的源码显示：

- source-pipeline.js默认enabled为false，周期24小时、窗口30天、limit 50，候选快照最多保留500条。
- NVD适配器取有限页结果，当前代码没有完整分页和修改记录同步。
- GitHub适配器调用安全公告API，关键词在取得的一页结果中本地过滤；不是GitHub全站PoC搜索。
- Nuclei使用最新提交Atom线索，不能代替完整模板差异同步。
- OSV需要编号或包名等明确条件，不是无条件全局新漏洞列表。
- CNVD、CNNVD和部分国内情报在注册表中仍属于检索指引或未接入能力。
- 微信是搜索辅助，不能作为完整公众号订阅同步来宣传。

这不否定已有适配器的价值。它们适合补充候选，下一步要增加持续、可恢复的更新机制，并把最近候选快照与长期知识库分开。

这些属于方案评估，本次没有启用周期任务或改动采集器。

## 5. 两层排序：先选题，再决定对哪个资产做什么

### 5.1 第一层：全局候选池

维护三个候选来源：

| 来源 | 内容 | 目的 |
|---|---|---|
| 近期重点 | 新披露高危、新绕过、近期成熟验证方法 | 保证最新高危得到优先发现机会 |
| 通用高危 | 常见产品漏洞和隐藏组件问题 | 防止只追新，漏掉仍有价值的老问题 |
| 目标特有 | 当前目标实际暴露的产品、版本、功能 | 避免目标线索被全局热门列表挤掉 |

候选池可以较大，但每轮只选择有限查询和验证任务。不要把Top12、Top20视为固定正确答案；更重要的是覆盖不同产品类别，并能根据结果补充。

最新高危应获得优先定向搜索机会。但没有相关资产时，不能持续占用深度验证资源。

### 5.2 第二层：资产上的具体动作

实际排序单位应包括：

~~~text
具体资产 + 漏洞条目 + 实际入口 + 当前身份 + 已有证据
~~~

建议用容易解释的行动等级：

| 级别 | 情况 | 下一步 |
|---|---|---|
| 优先验证 | 范围明确，产品或机制证据较强，入口可达，检测方法可靠 | 做最小验证；条件相近时优先近期、高影响候选 |
| 优先补证 | 近期或通用高危有相关线索，但关键条件未知 | 做一次能改变判断的低成本检查 |
| 有限探索 | 技术族或功能支持组件假设，没有直接组件指纹 | 使用独立的小预算补漏 |
| 暂缓 | 检测方法未审阅、认证缺失、代价过高、机制不明 | 记录缺口，先处理更有依据的候选 |
| 排除 | 已取得适用的版本、组件或条件不满足证据 | 停止此假设，保留依据 |

“未知”与“已知不适用”必须分开。返回404、没有banner、没有版本页，通常不能直接排除所有相关漏洞。

### 5.3 一个具体排序例子

假设机构内出现以下情况：

| 候选 | 证据 | 建议 |
|---|---|---|
| A：近期高危 | 产品已确认，相关入口可达，检测方法可靠 | 第一批验证 |
| B：较老高危 | 产品及受影响条件明显吻合 | 同样第一批；不能只因年份旧而推后 |
| C：刚披露的严重漏洞 | 只有相似标题，目标是否使用该产品未知 | 先确认产品，确认失败则停止 |
| D：Java自研系统的组件问题 | Java线索和真实输入存在，依赖未知 | 进入有限组件检查 |
| E：公开的高危漏洞 | 已确认相关功能未部署 | 排除 |
| F：很新的漏洞传闻 | 没有可信条件和检测方法 | 情报待研究，不能直接验证 |

发现阶段可以先查询C对应的产品，成本低且符合“最新优先”；验证阶段则应先投入A、B。这两个顺序不矛盾。

### 5.4 不建议一开始使用复杂黑箱分数

匹配度、影响、时间和成本的计分可以作为辅助，但先建立行动等级和解释字段更容易调试。

每次选择应能说明：

- 为什么值得现在做；
- 哪些条件已经确认；
- 下一步能消除什么不确定性；
- 什么结果会继续，什么结果会停止。

后续有足够基准数据，再校准权重。不宜把任意加分组合包装成经过证明的最优策略。

## 6. 高级FOFA查询应当怎样设计

### 6.1 把范围、归属和产品指纹分开

范围来自任务允许检测的域名、IP等边界。归属证据用于判断资产可能属于哪个机构。产品指纹用于判断服务可能是什么产品。

三者不能互相替代。页面包含机构名，不等于可以测试；同ASN也不等于同一家机构。FOFA的org字段表示ASN组织，不能直接当成目标企业名。[FOFA官方API说明](https://fofa.info/api)

输入机构时，已有域名、备案、机构名称和别名可以帮助被动发现。归属不充分的结果留在候选区，不自动进入主动验证。

### 6.2 查询结构示例

以下只是结构示意。产品枚举、具体特征和字段能力要核实后生成，不可原样当成真实查询任务。

~~~text
S AND (P1 OR P2 OR (P3 AND P4))
~~~

其中S是目标范围条件，P是指纹。示意形式可以是：

~~~text
(范围条件) &&
(
  app="<已核实的产品枚举>"
  ||
  (body="<产品特有特征>" && header="<相关响应特征>")
)
~~~

同一产品有多个漏洞时，先查一次产品资产，再在资产上选择相应漏洞。不要每个CVE重复查同一批站点。

一个大型OR也并非总是最好：可能有表达式长度、解释困难、结果归因和分页截断问题。建议按产品族组成有限查询组，保留每个命中来自哪个分支。

### 6.3 逻辑正确比字段数量更重要

目前测绘提示解析按字段提取表达式，并在某些连接符处拆分。括号、OR以及等号差异不能完整保留。

例如：

~~~text
(body="ProductA" || header="ProductA") && domain=="example.com"
~~~

在当前解析方式下可能拆成多个字段片段，无法在这些片段中保留原查询的整体语义。这是在查询转换层看到的问题，不等于已经证明实际搜索越界；后续还有范围处理。建议先修复语义，再扩展高级查询能力。

可选设计：

1. 对已审阅的FOFA原生查询，保留完整表达式并进行校验。
2. 对结构化指纹，用完整逻辑树生成原生查询。
3. 内部DSL不支持的语法，明确报错或交给原生通道。
4. 范围约束覆盖整个表达式，不能只拼到最后一个分支。
5. 记录最终发出的查询，而不只记录模型最初写的查询。

### 6.4 按查询结果调整策略

| 返回情况 | 下一步 |
|---|---|
| 结果很少且指纹明确 | 尽早实时复核和验证 |
| 结果很多但同质 | 去重分组，抽样校准，再处理独立资产 |
| 结果很多且误认明显 | 收紧产品特征，避免扩大验证 |
| 零结果 | 检查字段、指纹、索引和历史窗口；必要时调整一层 |
| 无权限、限流、API错误 | 记录为工具失败，不写成没有资产 |
| 只命中历史服务 | 实时确认当前状态，不直接验证历史索引 |

查询字段能力、返回字段权限、索引覆盖是不同问题。API能够返回某字段，不自动证明任意相关表达式都能执行；要根据实际账户能力和错误处理。

可以使用允许的统计能力辅助发现类别，但统计只反映其覆盖范围和返回上限，不等于完整资产清单。[FOFA统计接口](https://fofa.info/api/stats/statistical)

### 6.5 查询预算分配

每轮应同时考虑近期重点、常见高危和目标新发现类别，避免第一个产品乘上很多机构别名就耗尽预算。

查询资源优先用来取得新增信息：发现新产品、补充独立入口、解决指纹冲突。重复返回相同资产的查询，应合并或降低优先级。

Nday匹配仍然保持快速定向特点，预算用尽时报告覆盖缺口，不悄悄转为完整测绘。


## 7. 漏洞条目应该是一套判断方法

条目不能只有漏洞名称、严重等级、模板链接和一个产品指纹。模型需要知道怎样找到候选、怎样判断适用、怎样证明，以及什么情况应停止。

建议每条重点漏洞至少包含：

| 内容 | 用途 |
|---|---|
| 漏洞身份和来源 | 对应公告、编号、原始研究与确切版本 |
| 产品或组件 | 区分完整产品、可选模块和隐藏依赖 |
| 时间字段 | 区分披露、方法成熟、新绕过和资料抓取 |
| FOFA指纹 | 找候选，说明特征来源和误认可能 |
| 实时确认方法 | 判断当前服务是否仍符合线索 |
| 受影响条件 | 版本、配置、模块、身份、网络条件 |
| 实际输入位置 | 指向相关功能或请求，避免无关尝试 |
| 最小检测方法 | 描述能区分正例与负例的步骤 |
| 成功证据 | 明确哪些响应、差异或交互支持结论 |
| 阴性对照 | 排除正常功能、缓存、第三方请求和泛化回连 |
| 失败解释 | 区分未命中、不适用、请求无效和工具失败 |
| 成本及停止条件 | 限制重复尝试，并说明何时可以继续 |

### 7.1 情报成熟度与目标验证状态分开

建议条目成熟度分为：

- 待研究：只有线索，适用条件或检测方法不清；
- 可匹配：有可靠产品指纹，可以寻找资产；
- 可检测：方法经过审阅，有正例与负例依据；
- 已在测试环境验证：明确环境、版本和检测方法；
- 需要重新审阅：公告、方法或依赖发生变化。

“归一化成功”只证明数据格式符合要求；“有模板”只证明存在文件；“曾经验证”也只适用于当时的环境和方法。

目标状态另外记录：候选、待确认、待验证、已排除、验证受阻、机制已确认、影响已确认。不能因为条目成熟就把目标标成有漏洞。

### 7.2 阅读检测资料与运行检测分开

阅读公告、研究代码和补丁，是为了弄清机制和前提。版本未知时仍然可以阅读，不能要求先满足全部前提才允许了解检测方法。

实际对目标执行检查，则依据具体方法、范围、影响和成本判断。公开PoC需要审阅，下载成功不等于可以直接运行。

ProjectDiscovery工作流支持按前一步检测结果进入后续模板。这种条件编排值得借鉴，但具体匹配条件仍需审阅。[官方工作流说明](https://docs.projectdiscovery.io/templates/workflows/overview)

### 7.3 保存全量EXP还是只存线索：采用三层资产

我的建议是广泛保存轻量线索，重点保存可复用方法与精选代码；不把全部EXP打进Saker，也不只留下一个经常失效的URL。

| 层 | 内容 | 保存策略 |
|---|---|---|
| 广泛线索层 | 标题、产品、编号、时间、原始引用、重要条件、文件路径和内容摘要 | 尽量广，结构化索引，适合增量检索 |
| 方法与精选代码层 | FOFA指纹、有效请求结构、判定与对照、利用方法、精选脚本、依赖及方法版本 | 最新高危、通用高危和高频产品优先完善；经审阅后可直接复用 |
| 按需资料缓存 | 任务选中的原始PoC/EXP、特定提交、完整分析及依赖资料 | 有需要再取得，固定版本和摘要；候选未采用则不进入默认执行库 |

范围小、方法明确、依赖少且价值高的脚本，适合长期保存。大型工具或复杂框架保留确切版本、获取方法、依赖说明和最小使用步骤；不必把整套工具及所有历史文件复制进插件。

正式知识仓库只容纳可维护的内容。原始资料可保存在独立镜像或缓存中，不进入每轮模型上下文。离线保存与随包分发按来源许可处理，不能分发的内容保留引用和获取方式。

线索层可以很广，实际执行库应聚焦高价值。CVE全量元数据与全量EXP是两件事，不能因为前者有官方数据就推导后者应全部收集。

### 7.4 一个可复用的方法包

每个精选方法建议包含：

- 身份：漏洞或机制、产品、版本条件、入口。
- 发现：产品指纹和组件假设路由。
- 检测：请求结构、基线、对照和判定。
- 利用：脚本或完整步骤，所需身份、依赖及参数。
- 证据：什么输出证明什么影响。
- 来源：原始链接、确切提交或文件版本、内容摘要。
- 状态：静态审阅、测试环境复现、目标验证分别记录。
- 维护：变化记录和需要重新检查的条件。

原始EXP、检测方法、面向当前目标的交付脚本应关联但分开。为了利用而编写的代码，不一定适合作为批量检测；当前目标的认证细节也不能写进通用知识包。

从模板转换时保留请求顺序、变量、编码、外带机制和匹配语义。只留下“路径非404”会使可利用方法退化成弱指纹。

### 7.5 运行过程中如何选择资料

优先复用已审阅方法。没有方法时，按确切产品、机制和版本补查；取得原始代码后再确认它验证的是哪个条件。

“找到了EXP链接”只完成资料获取；“脚本能启动”只完成运行环境检查；“取得支持漏洞影响的证据”才完成目标验证。

如果有有效漏洞，必须在交付中给脚本或可操作的方法，不能只给仓库链接。交付规范见第18节。

## 8. 验证流程：每一步都要减少一个不确定性

建议采用下面的过程：

~~~text
测绘候选
  → 实时服务确认
  → 产品或技术族证据
  → 适用条件三态判断
  → 获取有效请求与基线
  → 选择检测方法
  → 最小检查与对照
  → 机制复核
  → 实际影响复核
  → 成果或明确的未验证原因
~~~

不要求每个漏洞机械经过所有步骤。例如，已有可靠版本证据证明相关组件不适用，就可以提前排除。

### 8.1 前提采用三态

| 状态 | 例子 | 应对 |
|---|---|---|
| 已满足 | 相关模块存在，允许身份可访问 | 继续相关检测 |
| 已知不满足 | 已确认组件不在受影响范围，或相关模块未安装 | 排除这一假设 |
| 未知 | 隐藏依赖版本，配置未暴露 | 寻找低成本补证或可判定检测 |

需要注意，应用版本、反向代理版本和依赖版本不是同一回事。一个产品修复公告能否排除其中的组件问题，要看公告覆盖的是哪条漏洞路径。

### 8.2 获取真实请求

有效请求包括方法、路径、参数、内容类型、必要会话、CSRF状态和正常响应。首页GET成功，不证明登录POST或业务接口检测有效。

检测失败时先判断请求是否被业务处理。如果所有变体都被网关拒绝，或者会话已经失效，结论应该是“当前条件下验证受阻”，而不是“没有漏洞”。

身份改变、入口改变、请求结构改变后，要重新评估相关结论，不能继续使用旧基线。

### 8.3 检测证据与影响证据分开

产品命中、异常响应、外带交互、代码执行是不同层级：

| 观察 | 可以支持的结论 | 仍不能证明什么 |
|---|---|---|
| 页面符合产品指纹 | 可能使用该产品 | 受影响版本或漏洞存在 |
| 特定输入触发异常 | 有值得研究的行为 | 异常可被利用 |
| 可归因的外带交互 | 某种外部交互机制被触发 | 一定实现RCE |
| 对照排除正常交互 | 机制证据更强 | 任意代码执行能力 |
| 最小、可复现、可归因的执行证据 | 相应执行影响得到证明 | 更多权限或其他资产也受影响 |

PortSwigger的Log4Shell检查示例使用有效检查和无效对照区分交互。可以借鉴其排除误报的思路，但不能将一次DNS回连直接报告成RCE。[官方示例](https://portswigger.net/burp/documentation/scanner/bchecks/worked-examples/log4shell)

验证过程应在证据足够后收口，不为了证明漏洞进一步建立持久访问或扩展到其他系统。

### 8.4 没有命中如何解释

至少区分：

- 方法有效，但本次检查没有发现对应证据；
- 已取得足够依据，排除当前假设；
- 请求没有到达相关业务处理；
- 缺少所需身份、配置或功能；
- 外带服务、网络、代理或工具不可用；
- 预算耗尽，未完成；
- 检测方法本身还不够可靠。

同一失败不能通过无限换参数、换工具来重复尝试。下一步必须有新的依据，或者能够解释前一步的不确定性。

## 9. Java → Log4j2：应该能想到，但不能直接认定

用户提出的微信案例，是本方案需要解决的代表性场景：发现Java环境后，能否想到业务应用中可能使用Log4j2？

答案是应该能想到。关键在于把它表达为“组件假设”，并设计有限、可判断的后续动作。

Apache公告说明Log4Shell涉及受影响的log4j-core及相关输入进入日志处理的条件。Java本身、其他日志实现或仅使用log4j-api，都不能直接推出受影响。[Apache安全公告](https://logging.apache.org/security.html)

### 9.1 建议的运行过程

1. 从当前页面、响应、技术检测及请求取得Java应用线索。
2. 保留线索强度：明确Java特征与单个可能误判的标签区别对待。
3. 路由到少量与当前应用有关的组件假设，包括有依据的日志组件检查。
4. 从页面或浏览器获取实际登录、搜索、错误处理等请求。
5. 根据检测方法选择相关输入，保留有效基线和对照。
6. 对未知组件条件进行有限检查。
7. 有交互则复核归因和机制；有执行证据才报告对应影响。
8. 无有效证据则说明检查入口、条件和未覆盖部分。

这条路径可以在Nday匹配中运行，也可以由常规测试复用。无须先识别成某个OA产品。

### 9.2 为什么不会变成所有Java站点都乱试

需要同时限制三个层面：

- 假设范围：技术线索只触发有限、相关的组件候选；
- 入口范围：使用实际观察到或有充分依据的请求；
- 工作预算：没有新增证据，就停止这一方向。

“通用”不意味着“对全部网站有效”；“版本未知”不意味着“可以无限尝试”。

### 9.3 没有回连不能直接排除

可能是组件不受影响、输入未进入相关处理、会话无效、出站受限、外带服务不可用或观察时间不足。

因此，没有回连只能与方法覆盖条件一起解释。若没有办法区分，应报告“未确认”，而不是给出全站不存在此漏洞的结论。

## 10. 用工具批处理，用模型判断，按需使用子代理

我不建议按“一个CVE一个代理”或“一个URL一个代理”默认铺开任务。很多工作只是查询、去重和指纹确认，用工具执行更直接。

### 10.1 建议的职责分配

| 执行者 | 主要职责 |
|---|---|
| 批处理工具 | 查询、分页、去重、提取特征、请求记录 |
| 主模型 | 选择候选、解释证据、调整优先级与预算 |
| 子代理 | 深入研究已经独立的具体产品、入口或异常 |
| 成果复核流程 | 核查证据是否支持结论、是否重复 |

子代理任务应当具体，例如：“确认资产A上的产品B是否满足漏洞C条件，返回判断依据和阻断点。”不要只给“对这个网站全面找漏洞”。

并发应根据工具限流、目标承受能力和任务独立性调整；默认并发数字需要通过实际运行校准，不应被理解为越多越好。

### 10.2 去重需要保留真实服务边界

同IP、同端口可能存在不同虚拟站点；同证书或同图标也可能对应不同应用。建议保留：

- 协议、域名或vhost、端口及实际入口；
- 重定向关系、后端关系和产品依据；
- 当前身份及会话条件；
- 已检查漏洞和使用的检测方法。

确认是同一服务的多个地址，可以共享信息。不能只根据相同IP或图标合并成一个已验证结果。

### 10.3 代表资产用于校准，不用于代替全部验证

先选代表资产可以确认查询是否准确、检测方法是否有效、是否存在通用阻断。

但代表成功，不能推导整个组都有漏洞；代表失败，也不能排除不同版本和配置。其他资产需要各自证据，能够共享的是方法和产品知识。

### 10.4 防止重复工作

记录每次检查的入口、身份、方法版本、证据和结果。相同条件下不重复执行；产品、身份、入口或方法变化时允许重新评估。

等待、重试和失败也应计入预算。多个代理正在运行，不意味着已经取得进展；进展应该体现在新证据和新的判断上。

### 10.5 把token消耗控制在需要判断的部分

原始扫描输出、整份JS、大量相似页面和全库模板，不直接进入模型上下文。工具先去重、聚合、提取特征；模型看到分类、关键异常和少量有代表性的证据。

典型流程是“批量执行 → 紧凑结果 → 对有价值项读取详情”。模型不是每完成一个HTTP请求就思考一次。

成本记录至少包括模型调用与token、工具时间、请求数、重复处理和每个有效漏洞的成本。只减少请求、却把大量文本交给模型，不一定降本。

通用资料按产品检索复用，任务证据按入口和身份检索复用。工具按阶段加载，让模型当前看到的能力与任务相符。

## 11. 一个机构Nday匹配的完整例子

假设机构甲提供了明确范围，要求优先找到有效高危问题。以下资产与结果均为示例。

### 11.1 第一批发现

定向查询与轻量概览取得：

| 服务 | 当前信息 |
|---|---|
| OA系统 | 产品明确，版本未知 |
| 产品A管理平台 | 近期存在高危公告，相关入口可达 |
| 产品B旧服务 | 有较老高危，部分受影响条件吻合 |
| Java自研登录系统 | 未识别具体产品，有真实业务入口 |
| 静态门户 | 暂无相关高危线索 |
| 同名外部网站 | 归属及范围未确认 |

### 11.2 形成动作队列

- 产品A：检查公告条件和当前入口，进入第一批验证。
- 产品B：基于强匹配验证，保留较老漏洞的机会。
- OA：先取得能影响判断的版本或模块证据。
- Java系统：进入有限组件补漏，取得实际请求。
- 静态门户：保留概览记录，不立即消耗深度验证预算。
- 同名网站：保持被动候选状态，不自动测试。

这样既照顾最新高危，也没有把全部资源花在最新列表上。

### 11.3 根据结果调整

假设产品A证明已经修复，产品B发现候选异常，OA缺少必要身份，Java系统出现外带交互：

- 产品A退出当前假设。
- 产品B补充对照和影响验证。
- OA记录身份阻断，不尝试假装已覆盖。
- Java系统复核外带归因，不直接登记RCE。

下一轮针对这些具体结果推进，而不是重新换一批热门CVE。

### 11.4 何时完成

Nday匹配可提供两种完成策略：

| 策略 | 适用需求 |
|---|---|
| 快速发现 | 取得首个满足用户影响目标的有效证据后收口 |
| 优先队列检查 | 在预算内继续处理其他高价值候选，交付覆盖和未完成项 |

如果用户要求RCE，其他发现不能替代RCE完成目标。若用户要求高危漏洞，则根据证实的影响判断，不把全部高危都限制成代码执行。

时间与请求预算应能说明已经处理哪些类别。预算耗尽是完成本次工作边界，不是宣称目标安全。

## 12. 常规测试：传统流程，重点降本增效

用户要的常规测试仍然是信息收集、漏洞发现、漏洞利用和交付的传统流程。本方案不把它重新定义成复杂研究模式。

### 12.1 执行流程

~~~text
已有资产和历史结果
  → 信息收集：域名、服务、端口、技术栈、入口
  → 去重及价值分组
  → 按服务和产品安排漏洞检查
  → 对候选做利用验证
  → 有效漏洞交付脚本或方法
~~~

单个站点主要收集其服务、页面、路径、JS/API和实际请求；机构先扩展范围内资产，再按独立服务分组。

传统的信息收集工具、有限目录与接口发现、指纹匹配和选定扫描器都可以使用。选择取决于当前缺口，不要求所有目标跑全套，也不强制只能使用已经看见的页面路径。

### 12.2 降本的主要位置

| 环节 | 容易浪费的方式 | 推荐处理 |
|---|---|---|
| 资产收集 | 每个模式从头做一次 | 共享已有数据，只补陈旧或缺失部分 |
| 指纹识别 | 对同一应用多个入口重复读取 | 服务去重，保留vhost及入口差异 |
| 路径发现 | 每个站点使用所有字典 | 按产品、功能和历史特征选择有限集合 |
| 漏洞扫描 | 所有模板作用于所有资产 | 已知产品走对应组，未知服务补少量通用高价值检查 |
| 结果分析 | 每条输出都调用模型 | 先工具归并，异常项再深入 |
| 利用验证 | 多个代理重复利用同一问题 | 共用验证账本，确定唯一处理任务 |
| 资料检索 | 每遇到同类产品就重新搜EXP | 复用知识与方法包，按缺口补查 |
| 报告 | 大量解释未命中项 | 有效漏洞详细，其他仅状态清单 |

不是不做常规工作，而是让一份信息服务后续多步，并把昂贵推理留给有价值的候选。

### 12.3 增效的关键

信息收集要能交出可行动的入口，不只交资产数量。一个后台、API服务、管理端口或高价值产品，应该尽快进入相应检查。

已知产品优先调用Nday方法库；服务未知时进行必要识别和有限通用检查；真实输入和权限关系明确时，检查相应常见问题。

发现高价值候选后及时验证，不必等整套收集结束。验证若取得新的版本、入口或模块信息，再回填资产记录，供其他检查复用。

### 12.4 机构的深度分配

第一轮对独立服务做快速分类。后台、业务API、管理系统、产品服务等优先投入；重复门户与静态页面只需完成相应轻量检查。

第二轮处理有迹象的入口和选定高价值资产。需要更深研究的后台/API可在用户选用0Day模式时继续，带入已有记录。

资产多不等于每个资产都应创建一个代理。能批处理的工作由工具完成，深入任务才并发。

### 12.5 完成条件与交付

本轮计划完成、预算用尽，或达到用户指定发现目标时结束。找到一个漏洞后是否继续由任务目标确定，不由公共opening强行结束所有测试。

默认交付：有效漏洞及脚本或方法；其他检查只有“已测未命中／不适用／受阻”的极简记录。覆盖细节保存本地，需要时再查看。

## 13. 0Day挖掘：隐蔽后台与API定向深挖

这一模式按用户要求聚焦单个网站相关的后台、业务系统和接口。静态门户不是默认深度研究对象；门户主要用于低成本取得后台和接口线索。

### 13.1 先找到值得研究的入口

优先使用用户给出的后台、接口地址、合法测试会话或已有常规测试成果。

若没有具体入口，工具有限提取JS/API路由、登录跳转、已暴露配置、接口文档及范围内相关服务，整理成去重的后台/API候选。模型只读相关片段，不逐页研究新闻、宣传页面或整份前端bundle。

入口定位设独立预算。没有后台、接口或有效业务输入时，结束定位并给极简阻断，不在门户上消耗完整挖掘预算。

需要有依据的路径补探时，可以使用限定集合；不把无限目录爆破当成0Day研究。

### 13.2 什么入口值得投入

| 入口 | 值得分析的内容 |
|---|---|
| 后台API | 身份、角色、对象和租户边界 |
| 上传、导入、解析 | 输入进入哪些处理模块，异常能否复现 |
| 导出、文件和模板 | 路径、对象、模板与访问权限的关系 |
| 管理及扩展接口 | 服务端执行的功能、配置和插件边界 |
| 多步骤业务 | 状态约束、跨步骤权限及重复处理 |
| 隐蔽但可达服务 | 真实功能与校验，不以“隐藏”直接认定漏洞 |

这些类别用于选择研究对象，不意味着每个接口都试所有问题。隐蔽也不意味着一定比门户脆弱；核心依据是它提供了可控输入、业务能力和值得验证的边界。

### 13.3 从接口列表到有限研究任务

先把接口按功能、输入结构和权限边界分组，读取代表性请求。只有有独立行为或明确价值的接口进入深入研究。

例如，几十个相似分页查询无需全部重新研究；批量导入、对象导出、管理操作等不同处理路径分别安排。

常见Nday或常规问题先快速识别并归类，避免把已知问题研究成“0Day”。随后围绕少量具体假设投入更深预算。

### 13.4 每个假设必须能验证或推翻

写清：

1. 当前身份能控制哪些字段或步骤；
2. 输入可能到达什么服务端处理；
3. 预期哪条边界出现缺陷；
4. 正常行为是什么；
5. 哪个差异支持假设，哪个结果可以排除；
6. 是否已有公开漏洞解释；
7. 下一步能得到什么新信息。

有源码或本地环境时，追踪对应调用和修复变化；没有时依靠有效请求、对照和重复复现。没有新增信息的方向及时停止。

### 13.5 与常规测试的区别

常规测试关注范围内较广的已知和常见问题，使用成熟方法提高覆盖效率。

0Day模式把更深的推理预算放在选定后台/API的具体功能上，研究输入处理、权限关系和状态变化。工具可能相同，投入深度与任务选择不同。

Google Project Zero对Big Sleep的介绍强调，已有漏洞和补丁能提供具体的变体研究起点。可以借鉴此方法，但不能推导任意黑盒后台都能找到新漏洞。[原文](https://projectzero.google/2024/10/from-naptime-to-big-sleep.html)

### 13.6 结论与交付

发现按已知漏洞、新变体、疑似未公开漏洞或未证实异常分类。找不到CVE不证明全球首次；没有新颖性证据，也不妨碍交付已验证的有效漏洞。

有效问题给当前入口的利用脚本或完整方法、前提和成功证据。无效假设仅留简短已测标记，原始研究过程不塞进交付正文。

## 14. 桌面端适配：交付路径以dsh桌面宿主为准

截至2026-09-30，本轮查阅的官方发布列表最新列出dsh-v0.2.0-rc.2，为候选版本。实际实施时仍须重新确认版本与用户安装环境；本方案不宣称已经适配完成。[官方发布记录](https://github.com/deepseek-ai/deepseek-harness/releases/tag/dsh-v0.2.0-rc.2)

### 14.1 “弃用网页端”怎样落实

用户的主要入口、安装说明、配置流程和验收环境都改为桌面端，不再要求用户启动独立网页服务才能使用Saker。

桌面内部仍可以复用共享Web组件。这属于宿主的实现方式，不影响产品以桌面为主要交付目标。

### 14.2 插件安装遵循官方管理路径

官方桌面文档说明，desktop profile由桌面宿主管理；桌面自带命令可以在应用完全退出后管理已初始化的插件，普通npm安装的dsh不能直接修改它。[官方桌面文档](https://github.com/deepseek-ai/deepseek-harness/blob/dsh-v0.2.0-rc.2/apps/desktop/README.md#bundled-command-runtime)

因此建议：

- 优先使用桌面插件管理界面或官方桌面命令。
- 旧脚本不再直接改desktop profile的依赖、锁文件和激活列表。
- 明确迁移哪些设置、语料和成果，避免复制旧执行依赖图。
- 安装失败、未激活、需要重启和宿主不兼容分别显示。
- 升级后检查实际加载版本，避免源码已修改但宿主仍用旧包。

### 14.3 三个入口共享任务记录

桌面页面建议展示：

| 信息 | 用户能理解的表达 |
|---|---|
| 当前步骤 | 正在确认产品A的相关模块 |
| 选择依据 | 近期高危，产品已确认，入口可达 |
| 条件缺口 | 版本未知，准备低成本确认 |
| 本轮进展 | 新增一条证据，排除两个候选 |
| 检测结果 | 已确认影响／未确认／受阻 |
| 覆盖情况 | 哪些资产、入口和身份尚未检查 |

详细查询、来源和原始请求放到可展开的记录中。主界面优先解释实际工作和结果，避免让用户面对内部调度术语。

### 14.4 提示词和工具也要验收

修改菜单或skill文件，不代表模型实际按新模式工作。公共opening、模式skill、工具返回的计划、method-stack及用户自定义提示可能互相影响。

应从真实桌面会话确认：

- 用户选择的模式进入了模型最终上下文；
- 旧四模式及统一停止规则没有继续覆盖新定义；
- 工具实际可见并能调用；
- 常规测试能复用Nday证据；
- Java线索能进入组件假设；
- 条件未知时不会直接结束或无限重试。

### 14.5 验收分层

| 层次 | 能证明什么 |
|---|---|
| 文档和配置检查 | 名称、声明和设计一致 |
| 构建检查 | 可以生成相应产物 |
| 宿主工具检查 | 插件注册、工具调用和结果返回可用 |
| 真实模型会话 | 提示生效，决策符合模式 |
| 真实桌面应用 | 安装、配置、页面、重启和任务记录可用 |

构建通过不能替代桌面验收；浏览器里页面能打开，也不能单独证明桌面安装与运行正确。

## 15. 怎样判断方案确实提高了效果

不能要求未知目标一定有漏洞，也不能从真实目标零发现推导系统无效。需要已知标签场景与真实任务记录结合评估。

### 15.1 建议的基准场景

| 场景 | 正例 | 对照 | 要检验的能力 |
|---|---|---|---|
| 最新产品高危 | 受影响产品及相关入口 | 已修复、模块未部署 | 近期优选与条件判断 |
| 较老高危 | 明确受影响条件 | 可靠排除证据 | 不被年份过滤 |
| 隐藏组件 | Java应用中的相关依赖 | 其他日志实现或修复环境 | 技术族补漏 |
| 指纹误认 | 产品特有特征 | 同标题、默认图标、反代页 | 指纹复核 |
| 版本未知 | 无外显版本但可判定 | 同样隐藏版本的负例 | 未知条件处理 |
| 外带交互 | 可归因交互 | 正常请求或第三方交互 | 对照与影响分层 |
| 请求失效 | 有效业务请求 | 失效身份、错误CSRF | 不把失败算阴性 |
| 机构重复服务 | 同应用多个入口 | 同IP不同应用 | 去重与共享 |
| 复杂FOFA逻辑 | 括号及分支约束 | 语义被拆开的查询 | 查询表达式正确 |
| 常规测试 | 重要功能和权限缺陷 | 正常业务行为 | 覆盖和业务判断 |
| 0Day研究 | 后台/API的可重复具体缺陷 | 静态门户、正常业务、偶发异常 | 入口选择、假设证伪与成本 |
| 情报更新 | 分页内外的新增、修改和撤回 | 截断、抓取失败、仓库目录重构 | 不漏同步，不把旧问题当新 |
| 利用交付 | 当前环境可复现脚本或方法 | 缺依赖、只有链接、仅指纹脚本 | 交付完整性与复现能力 |
| 桌面升级 | 新版插件加载成功 | 安装了但未激活或旧包仍运行 | 实际宿主验收 |

基准环境应记录产品、组件、方法版本和配置。合成场景用于隔离机制，不能单独证明真实产品上的全部语义正确。

### 15.2 指标定义

| 指标 | 建议口径 |
|---|---|
| 高危检出率 | 有标签的受影响场景中，正确确认的比例 |
| 指纹准确率 | 被复核的产品候选中，产品判断正确的比例 |
| 成果误报率 | 已完成复核的成果中，错误结论的比例 |
| 首个有效发现耗时 | 从任务开始到取得满足目标的证据 |
| 可复现交付率 | 有效漏洞中，有完整方法或脚本且完成相应复核的比例 |
| 每个有效漏洞成本 | 模型token、工具时间、查询和请求分别统计 |
| 情报及方法延迟 | 上游变更到入库、方法就绪分别计时 |
| 请求和FOFA成本 | 按唯一资产、候选及成果统计 |
| 重复工作比例 | 相同入口、身份和方法下重复执行的比例 |
| 覆盖情况 | 已处理及未处理的产品、功能和身份 |
| 阻断分布 | 身份、网络、工具、方法、预算等原因 |

没有完成复核的结果独立列出，不混入正确成果。真实任务没有完整漏洞标签时，不报告无法成立的真实召回率。

成果数从唯一证据与复核记录产生，避免直接累计代理反馈中的“发现数量”。检测命中率和漏洞发现率也要分开。

### 15.3 做公平比较

使用同一目标环境、允许身份、工具能力和预算，比较：

- 原有热门目录排序；
- 仅按目标指纹选择；
- 本方案的两条发现路径与证据队列。

模型会有波动，重要场景需要适当重复。观察是否增加有效发现、减少误报和无效请求，以及是否覆盖隐藏组件。

### 15.4 哪些变化不能自动算改进

模板更多、查询更多、代理更多、报告更长、找到很多配置项，都不能单独证明效果更好。

首个高危发现更快，但漏掉其他重要类别，也需要结合用户任务目标评价。快速模式和覆盖模式应分别比较，避免用同一个指标强行评估。

## 16. 推荐的后续实施顺序

这里是未来可以参考的推进顺序，本次仅交付方案。

### 第一阶段：统一产品和执行规则

- 合并Nday与campaign入口，形成三个模式。
- 给每个模式定义交付目标和停止条件。
- 同步公共opening、模式skill和工具计划。
- 统一候选、排除、受阻、机制确认、影响确认状态。

先解决定义冲突，否则后续能力仍会被旧规则覆盖。

### 第二阶段：修复Nday核心判断

- 保留FOFA表达式语义和范围约束。
- 分离情报时间字段及产品分类。
- 建立近期重点、通用高危和目标特有候选。
- 将执行任务绑定具体资产、入口和证据。
- 为条件未知设计有限补证。

这阶段优先选少量有代表性的高价值条目完善，验证方法可靠后再扩展。

### 第三阶段：补隐藏组件、维护知识与利用交付

- 建立技术族到组件假设的有限路由。
- 补齐Java／Log4j2代表性场景。
- 共享真实请求、身份和验证历史。
- 改进服务去重与代表资产校准。
- 将成果计数绑定证据复核。
- 建立可恢复的来源增量同步，来源状态与知识版本分别记录。
- 精选方法包保存代码、依赖和判定，广泛线索不自动进入执行库。
- 有效漏洞形成利用脚本或方法，未命中项仅交付状态。
- 0Day模式设置后台/API入口门槛及独立的定位预算。

### 第四阶段：完成桌面交付

- 使用官方桌面安装与管理路径。
- 核实配置、插件版本和模型提示生效。
- 进行真实桌面会话和升级验收。
- 更新使用文档，以桌面入口为主。

### 第五阶段：用基准数据校准

- 比较不同发现与排序策略。
- 调整候选数量、查询组、补漏预算和并发。
- 用失败原因反馈改进检测方法。
- 再决定新增情报源和扩大漏洞库的价值。

不建议一开始同时重写所有插件、扩充大量模板并增加代理并发。先证明关键场景的判断改善，再扩大覆盖。

## 17. 设计取舍与适用边界

### 17.1 快速与覆盖存在取舍

Nday匹配重视尽快找到值得验证的已知漏洞，因此不会完成全部资产和功能测试。用轻量概览及组件补漏降低盲区，但仍需明确未覆盖部分。

常规测试允许更广覆盖，0Day允许更深研究。三个模式分别承担不同成本，而非承诺一种流程包办所有需求。

### 17.2 最新优先与目标证据需要同时存在

最新高危获得优先检索机会；明确匹配的候选获得优先验证机会。这样可以兼顾情报敏感度与实际收益。

旧漏洞有明确证据时仍应验证；新漏洞没有相关目标时应及时退出。时间、严重等级和热度不能替代适用性判断。

### 17.3 通用检查需要可解释的限制

补漏应针对观察到的技术、功能和输入。每次探索要说明依据、下一步和停止结果。固定的小比例或固定数量可以作为实验参数，但不能称为经过证明的最佳分配。

### 17.4 自动化重点是留下可靠判断

工具负责执行和记录，模型负责推理与调整。可复核证据、准确的阴性解释、清楚的覆盖缺口，是系统长期改进的基础。

暂时未发现漏洞时，交付“本轮未确认有效漏洞”及极简已测状态即可。详细排除理由与过程保留在本地记录，不要求用户阅读。一般配置观察不填充成果。

## 18. 交付：有效漏洞详细，未命中项极简

### 18.1 未命中清单只说明测过没有成果

建议默认一行一个“资产／漏洞或检查项／状态”。不展开来源、评分、原理和每次失败过程。

~~~text
oa.example.com／候选A：已测未命中
api.example.com／候选B：不适用
admin.example.com／检查C：受阻（缺账户）
~~~

常用已测未命中、不适用、受阻、未测四个状态即可。确实没执行的项目不标记成“测过了不行”；这种准确区分也只需要几个字。

大量同类项目可合并为一行，并附极简清单文件。正文不枚举所有CVE，也不要求列出完整模型推理。

### 18.2 有效漏洞交付内容

每条至少包含：

1. 目标和实际入口；
2. 漏洞类型与已经证实的影响；
3. 利用前提：身份、版本、模块等必要条件；
4. 可复现利用脚本，或完整、可操作的利用方法；
5. 关键请求、响应或执行证据；
6. 复核方式和必要的恢复说明。

重点是使用户能够复现。只给公告、EXP仓库链接或“建议用某工具”不算完成交付。

### 18.3 脚本和方法如何选择

| 情况 | 交付 |
|---|---|
| 单次或少量请求能复现 | 当前目标适用的短脚本或完整原始请求及步骤 |
| 多步利用或需要状态 | 脚本记录步骤和状态，说明所需身份及依赖 |
| 使用成熟外部工具 | 固定版本、必要参数、步骤、成功判据；需要时附包装脚本 |
| GUI或业务操作更可靠 | 明确每步操作、字段、关键请求与结果，不强行生成无效脚本 |
| 尚未证明影响 | 仍是候选，不能以一个能运行的检测脚本冒充有效利用交付 |

对于已经确认的RCE，交付能够复现已证实执行效果的最小方法。仅产生外带交互的脚本，应标为交互检测，不能改名为RCE利用。

脚本包含实际所需依赖、入口参数、认证输入方式、超时和明确成功判定。避免把当前Cookie或凭据硬编码进可共享文件。批量扫描与后续扩展能力不是复现交付的必要条件。

能在测试环境复核的脚本先复核；当前目标步骤有证据，但生成脚本未实际运行，应明确这个差别。不能为了“有脚本”而声称完成未做的验证。

### 18.4 交付结构示例

~~~text
delivery/
  findings.md                   有效漏洞及复现说明
  repro/                        利用或复现脚本，含运行说明
  evidence/                     支撑成果的关键请求与响应
  checked.tsv                   极简已测状态
~~~

这是未来交付结构，不是本次生成的文件。本次任务只更新方案。

任务内部的完整记录保留以供去重、追查和后续复用；最终报告不需要呈现全部记录。没有成果时不输出大量理论解释。
