# Saker 下一阶段完整目标：从插件集合到可验证的任务工作台

制定日期：2026-10-08。起点：Saker 0.4.92。依据：[ARTEX 固定提交代码评估](saker-artex-gap-analysis-2026-10-08.md)与[现有实际效果评估](saker-assessment-2026-10-08.md)。

**总目标：用户在聊天中设定范围、目标、执行方式与预算后，Saker 能用持久任务推进工作，按需共享原始依据，清楚区分线索和已确认发现；中断可恢复、复测可对照、成本可解释。首先服务学习和有人监督的使用，以真实验收决定后续自主性。**

本文是下一阶段目标和验收合同，所有新增指标均为建议门槛，不是当前成绩；不是定时任务，也没有启动后台持续工作。阶段顺序按依赖划分，不承诺日历日期。运行代码、Desktop 安装和用户数据本轮均未改动。

## 1. 产品定位与成功标准

面向三类用户：希望理解测试过程的学习者、希望少交互推进有界工作的熟练使用者，以及需要核验证据和复测结果的审阅者。单机 Desktop 保持默认入口，既有聊天与插件继续使用。

最终用户应该能直接回答：正在测什么、为什么测、已覆盖什么、哪些只是线索、哪些已经独立确认、消耗了多少、现在为何等待、怎样继续。代理数量与图节点数量不作为主要成绩。

核心效果指标是独立确认数、漏检和错误确认、每个成功案例的请求/模型用量/耗时、人工介入和失败恢复。知识检索率、工具数、测试断言数单独记录，不能混算漏洞检出率。

## 2. 实施顺序和阶段出口

| 阶段 | 目标 | 依赖 | 交付内容 | 阶段通过条件 |

| C：用户可操作 | G6、G8、G9 的第一批 | A、B 的稳定接口 | 聊天快速设置、统一任务详情、复测、报告版本 | 官方 Desktop 中完成设定→执行→查证→恢复→复测 |

## 3. G0：能力体检与实际可用性（P0）

**问题：** 配置存在、插件安装成功，不保证工具/MCP/模型实际可调用。此前已发现两项 MCP 未连接、四个登记工具路径失效。

**复用：** hunter 设置、MCP 宿主设置、sec-config、已有安装同步与 Desktop 验收脚本。实现负责人范围为宿主适配和工具接入。

**交付：** 按当前任务需要列出模型、必需工具、MCP、知识与验证器；状态明确为可用/离线/未配置/版本不匹配。每项显示原因与修复入口。必需项失败阻止依赖任务就绪；可选项缺失允许明确降级。登录需求由用户处理，不代登录。

**验收：** 对任务声明的必需项做真实最小调用，而非只检查文件；错误地址、失效路径、未启用插件各有可见失败。重启后配置保留。用户能看出“这项能力这次没用上”，不会得到与实际工具不符的报告。

**范围控制：** 不为证明可用而安装全部工具；不要求用户先启动所有 MCP 才能做本地学习任务。

## 4. G1：同模型、同预算的效果基准（P0，贯穿全部阶段）

**问题：** 当前没有能够回答“Saker 增加的结构比普通 Agent 多带来多少收益”的对照。

**交付：** 本地隔离且可重复重置的练习基准、机器真值、独立结果评分器和任务级原始记录。首先冻结 24 个案例：8 个单步阳性、6 个多步/身份依赖阳性、6 个阴性、4 个环境故障。另留 12 个隐藏验收案例，避免一边修改一边针对同一集合优化。

至少包括权限隔离、相似错误页、请求反射、过期身份、缺版本信息、前置步骤失败、没有漏洞但有相似响应、目标不可达。成功必须通过基准独立检查，不凭 Agent 的“完成”文字。

**实验组：** 普通 Agent、冻结 Saker 0.4.92、改进后的 Saker。ARTEX 固定提交作为可选第四组；能完成环境准备后加入，不能把它缺少的 bench 文件当成 Saker 不能先评测的理由。ARTEX 只在本地隔离条件下比较。

**公平条件：** 相同模型版本、访问身份、初始资料、任务预算、可用工具接口和重置快照；顺序随机，每例至少三次。原生完整工具链对比另列，不与受控同工具实验混合。保存模型路由与实际调用清单；无法统一的条件显式说明。

建议先用少量校准例确定预算，再冻结。可从每例 30 分钟、200 次目标请求、150k 输入/输出合计 token 的试验上限开始；这是试验建议，是否合适由校准决定。多代理共享总预算，不能每个代理单独领同额预算。重试和失败计入；未知用量单列。

**验收：** 完整记录每例：独立成功、错误确认、未确认/漏检、实际请求、token、时间、人工介入、失败原因、原始依据。隐藏验收集合中“确认”的阴性案例必须为 0；这是该有限集合的发布门槛，不是生产环境零误报保证。新结构若没有明显效果收益，也可因相同效果下节省成本保留；不能只报总分而隐藏失败。

## 5. G2：复用任务账本实现依赖与持续调度（P0/P1）

**复用：** `dsh-stage-gate/lib/index.js` 的状态机、锁内领取、心跳与父子任务；redteam `task-policy.js` 的父预算和 `task-flow.js` 的阶段兼容。

**交付：** 给现有任务增加 `dependsOn`、依赖产物引用、`blockedReason`、稳定 `taskKey`、执行租约和就绪查询；结构化事件唤醒必要规划，合并短时重复事件。任务定义/依赖/已用预算必须落盘；拒绝依赖环与跨范围引用。

程序判断前置条件是否满足，模型提出计划和可验证条件。程序禁止因模型声称“已有凭据/版本适用”而跳过对应证据检查。旧任务没有依赖时维持原语义。

**验收：** 本地三步练习链在前置未完成时下游不执行；并发领取不双发；重复事件不重复建任务；暂停/取消向所属工作传播。Desktop 重启后任务、依赖、预算和等待原因一致。模拟调用后崩溃但结果不明，任务进入待核实，不能盲重发有影响的动作。

**不做：** 另建第二套 task-board；仅把依赖描述加进提示词；把“任务 succeeded”直接当作依赖证据成立。

## 6. G3：贯通资产、任务、方法和原始证据（P0/P1）

**复用：** asset-inventory、hunter 范围关系、attack-atlas、task-context、execution-receipts、trace-vault 和现有成果账本。保持既有攻击链图，建立统一可查询引用。

**交付：** 稳定资产键和以下观察记录契约，字段命名在设计阶段定稿：

```text
Observation
  id, workspaceId, assetId, taskId, sessionId, actorRole
  methodId, methodVersion, receiptIds, claim
  supportingEvidenceIds, counterEvidenceIds
  capturedAt, identityRef, freshness, verificationLevel
```

节点/边都能指向依据，记录来源与更新时间；共享观察原子归并，矛盾保留，不以“最新摘要”静默覆盖。身份秘密用受控引用，不广播进每个代理上下文。

HTTP、浏览器、MCP、CLI/源码分析通过统一 receipt adapter 接入：原始完整输出独立存储，索引只放摘要、哈希、长度与读取指针。摘要与正文分离；哈希证明完整性，语义正确性由 G4 判断。报告使用 `evidenceVersion`，版本改变时旧报告待更新。

**验收：** 每个可交付发现能回溯“资产→任务→方法版本→实际执行→验证结果”；故意替换正文、删除引用、改方法版本、换身份时，相关确认失效或明确需要复核。清理普通流量不删除被发现引用的证据；导出、导入、恢复后哈希一致。跨子任务查询只返回允许的材料。

**迁移：** 先给旧记录添加可选引用并双读，旧证据标记能力边界；不把历史文字猜测成真实回执。首次整合提供可恢复快照，不急着引入独立图数据库。

## 7. G4：扩展已有独立验证，闭合复测与报告（P0/P1）

**复用：** `private-json-read/v1`、effect-verifications、impact-reviews、effect-jobs、delivery-evidence 与 delivery 闸门。已经存在的验证与恢复机制继续使用。

**交付：** 版本化 validator registry。第一批在既有私有 JSON 读取验证之外，加入两类能在本地练习环境提供正常与阴性对照的验证，例如浏览器实际执行的 XSS 证据、受控内容/行为差异的注入验证。最终选型以基准可独立判分和请求成本为准。

状态分为线索、已采集依据、依据支持、独立验证、需人工复核、无法确认；验证角色读取原始依据而非仅看 worker 结论。已有 recipe 规定的回执数量、身份与新鲜度不能因跨代理共享而降低。

发现详情提供复测入口，固定原发现/方法/证据版本、当前身份与目标版本；输出仍可复现/已修复/无法确认。只在成功且证据满足修复条件时更新处置状态。原证据与历次记录保留。

**验收：** 请求反射、伪造回显、缓存响应、相似错误页、过期依据、错身份均不能被确认。修复版本正常功能可用、原触发条件失效后才判已修复；不可达/登录失败判无法确认。移除关键对照或换回旧验证实现时，反向用例必须失败。报告引用所有关键依据及版本，缺口不能靠模型补写。

**范围控制：** 写入与执行类影响先保留现有人工/受控验证条件，不以读类 recipe 泛化。报告 Agent 不自动等同于独立验证器。

## 8. G5：全任务树预算、模型选择和故障恢复（P1）

**复用：** task-policy、task-cost、受管站点 worker、已有 provider/外部 CLI 接口。优先在现有 dsh 模型服务之上适配，先确认宿主支持哪些能力。

**交付：** 总任务的 token/请求/时间预算预留与结算，所属代理共享；失败尝试计入。每次调用记录 provider、model、角色、选择原因、用量与未知字段。金额仅在配置了带日期的价格表时估计；未知费用不显示为 0。

按规划、确定性整理、探索、独立验证角色配置模型。先允许用户显式配置，再用 G1 数据判断是否应自动选择，不能默认昂贵模型总是更好。故障链可配置且可见，模型改变时保留调用收据。

借鉴 ARTEX 模型池的切换边界：尚未输出事件时可按策略切换；已有工具调用或部分流输出后必须由任务状态核对恢复，不能盲重放。认证错误、额度耗尽、限流、上下文不足与中途断流分别处理。

**验收：** 同时启动多个代理，预算预留总和不越过剩余额度；结束/取消后正确释放；重启不重置预算。预算耗尽停止新工作并输出现有结果。中途断流不导致同一动作重复执行；切换模型和无法统计用量在 UI 中可见。超预算的“成功”不计入 G1 成绩。

## 9. G6：从聊天入口重整用户体验（P0 设计，P1 交付）

**复用：** interaction、chat-setup、聊天快速设置、已有模板/任务/成果/攻击链面板。不再从零做模式和提示词系统。

**聊天启动卡：** 首屏仅展示目标/范围、执行方式、汇报方式、代理与预算、开始/继续按钮。用户看到的描述是工作行为，协议名、存储与内部模块放高级详情。

| 设置 | 用户可理解的选项 | 必须明确的语义 |
|---|---|---|
| 执行方式 | 自主推进、关键节点确认、共同研判 | 共同研判等待用户方向判断；不绕过已有范围、预算和影响规则 |
| 汇报方式 | 结果摘要、阶段摘要、实时进展；学习讲解可单独开启 | 决定展示频率与解释程度，与是否需要确认分开 |
| 子代理 | 自动分配、手动上限 0–16 | 同时显示配置上限、实际运行数、为何排队；不把上限叫实际并发 |
| 预算 | 标准/自定义 | 显示剩余请求、时间、可统计用量，费用未知时说明 |
| 模板 | 学习讲解、快速检查、证据复核、修复复测、资料更新 | 可看、可编辑、可复制；短例子能表达目标 |

模板示例应是一句话，如“检查这个本地练习站点，每个发现给出证据和正常对照”，或“复测这条发现，保留原证据并说明结果”。范围、预算和模式通过控件传入，不要求用户读长提示词才能使用。

运行时顶部显示任务目标、阶段、活动代理、预算和等待原因。详情组织为概览/探索与覆盖/发现/证据与流量/复测与报告；图和列表互相定位。等待原因使用“等待你的身份资料”“模型额度不足”“前置验证尚未完成”等可操作文案。

**验收：** 官方 Desktop 实测新任务设置、保存默认、应用模板、复制、开始、改设置、暂停/继续和失败恢复；实际送入模型/任务的配置与界面一致。明确设置对当前任务还是新任务生效，未保存修改不被其他按钮静默覆盖。三个新用户各能在无口头引导下完成启动、找依据和定位等待原因，建议每个基本流程在两分钟内完成。没有正式用户样本时只能记为内部走查，不能冒充用户验收。

**视觉要求：** 统一间距、控件高度和文案；状态色固定且配文字；减少无意义动画、弹窗和高级选项常驻。先优化任务路径，再做装饰。

## 10. G7：知识更新变成可审计的质量维护（P1）

**复用：** 0.4.92 GitHub 订阅、固定提交/正文摘要、AI review 队列、失败重试和知识索引，不让模型代替确定性同步。

**交付：** 展示上游提交时间、本机最后成功同步、正文缺口、待处理数与最老积压。新增/改变资料优先；按漏洞编号、产品别名和正文归并。长文分段整理，引用片段带位置和哈希；失败分类、重试预算和人工复核入口明确。

建立至少 50 篇有人工标注的维护样本，覆盖旧资料、新版本、重复 PoC、相互矛盾、缺适用条件与来源删除。关键字段除了结构校验，还检查原文是否支持其语义。产品名不能仅靠文件标题机械填写；未知版本保留未知。

资料整理不执行来源代码，不自动转换为已确认发现或可执行探针。只有进入已有审核链后才可用于实际验证。来源变化使历史摘要失效或待复核，保留用户编辑，不静默覆盖。

**验收：** 正文未变不重复调用模型；新提交但正文相同能解释跳过原因；删除/更正资料使旧结论可见地失效。50 篇语料的重要字段支持率建议不低于 95%，无依据的“已复现/已修复”标记为 0；不达标不扩大自动发布。积压可恢复，单轮错误不阻塞全队列。

## 11. G8：同站多角色协作与有界过程共享（P1）

**复用：** site-workers 的原生宿主启动、消息、持久映射与恢复；trace-vault 与 task-context 继续提供上下文。当前同站唯一键改造需要迁移策略。

**交付：** 从 `(parentSession, site)` 扩展为含 role/taskKey 的工作归属；支持同站探索者与只读验证者分工。每个工作只能领取就绪任务，在父预算内运行；材料访问范围明确。共享观察使用 G3 契约，而不是给所有人复制整个会话。

**验收：** 两个 worker 不重复领取同一方向；验证者不能用发现者摘要代替原始证据；角色消息关联任务/回执且可追踪。父任务停止后不遗留继续工作的子任务；重启后映射与实际宿主一致。先做单站两个角色与少量跨站案例，再进入 G10 扩展。

**范围控制：** 保持可控深度，第一阶段不开放无限嵌套；更多代理只有在基准证明收益后才作为默认配置。

## 12. G9：索引、上下文、归档与发布可靠性（P1/P2）

**问题：** 现有知识索引约 604.6 MiB，Desktop 进程工作集合计约 1.11 GiB；两者是既有观测，不能当作独占内存或压力测试结果。

**交付：** 减少已有增量索引的全源遍历与无效刷新、批量发布合并刷新、完整正文与检索索引分开；热任务读必要字段，冷任务读摘要后按引用展开。压缩摘要带来源和失效信息，重新激活的证据不被旧摘要覆盖。

报告与任务归档包含发现、版本、关键原始依据、验证与复测历史；支持从旧数据恢复。发布记录插件/宿主兼容矩阵、文件校验和、迁移步骤与回退条件。

**验收：** 在相同知识语料和检索例上，Top-5 不比现有基线少命中超过一个用例；同机热查询 p95 建议不超过 150 ms。体积先回到现有 600 MiB 警戒线内，达不到则列出归因和取舍，不能通过删有效资料伪降。

小增量不触发不必要的全库重建；测出全量与增量的耗时、磁盘写入和资源峰值。查询、压缩、导出和录制并发时，展示失败或等待，不出现静默缺证据。归档后清理普通记录，仍能恢复关键依据与复测历史。

每次运行功能更新都执行官方 Desktop 用户流、插件激活、可见错误和实际 MCP 设置检查；刷新真实桌面快捷方式并启动当前版本，沿用日常 home、MCP 和用户数据。构建、单测、模拟和安装字节检查各自记账，不替代 Desktop 验收。

## 13. G10：并发、故障与有监督试用（P1/P2）

**交付：** 固定任务的 1/2/4/8/16 代理阶梯测试；共享目标限流、全树预算、重复任务检测与故障恢复。请求速率必须按目标/任务聚合，不能让每个 worker 都独立使用全额速率。

测量独立成功数、重复请求比例、每次成功的用量/时间、队列等待、磁盘/内存峰值、取消延迟、孤儿工作和恢复结果。模型延迟/429/中途断流、宿主重启、证据损坏、磁盘写入失败和身份过期都要有失败注入。

**验收：** 在冻结预算与有限测试集合中不重复领取、不越过范围/预算；父任务取消后新工作停止，已有不可取消动作显式显示。提高代理数必须展示收益和成本，若 8→16 没有收益则保留配置能力但不扩大默认值。目标不限于跑满 16，更不是单独提高上限。

最后完成至少 10 次有监督的本地完整任务，覆盖启动、执行、中断恢复、证据审阅、报告和复测；每个失败保留原始原因。初期以学习/受控试用描述发布，不把这 10 次经验泛化为生产性能承诺。

## 14. 发布的联合门槛

| 门槛 | 必须提交的证据 |
|---|---|
| 实际可用 | 官方 Desktop changed flow、插件激活、必需 MCP/工具真实调用；登录阻塞如实记录 |
| 状态正确 | 依赖、领取、预算、取消、重启恢复和结果不明步骤的反向用例 |
| 结论可信 | 冻结与隐藏集合的任务级成绩；阴性误确认与未确认分开；关键发现可独立复现 |
| 成本可解释 | 全树调用记录、失败重试、未知用量、每成功消耗，不能只给累计 token |
| 用户可操作 | 快速设置实际生效、短模板、可见等待原因、证据与复测入口的 Desktop 验收 |
| 数据可恢复 | 旧任务/知识兼容、证据归档和恢复、报告版本冲突、配置与用户编辑保留 |
| 交付可启动 | 当前版本桌面快捷方式与安装同步；本轮临时状态清理和 temp boundary 检查 |

某项未通过时，要么修复后再验，要么明确减少发布范围；不能用更多通过的静态断言抵消真实失败。

## 15. 第一批具体工作包

1. 形成当前任务所需能力清单和 G0 真实体检，确认工具缺口对哪些任务有影响。
2. 建 24 个冻结基准案例与独立评分器，先跑普通 Agent 和现有 Saker，记录基线。
3. 定稿统一观察、原始证据引用、任务依赖和预算事件契约，列出旧数据迁移与兼容方式。
4. 在官方 Desktop 做一版聊天启动卡与任务总览，先验证用户能设定工作并理解等待原因。
5. 在既有验证器旁增加两个有阴性对照的 recipe，再做报告版本与复测闭环。
6. 接入依赖就绪调度和同站双角色，按基准验证是否改善多步案例；然后再做模型池和高并发。

第一批必须产出原始记录和失败清单。知识质量与性能随后按上面的依赖跟进；无需为“追赶 ARTEX”重写宿主、替换数据库或继续堆插件数量。
