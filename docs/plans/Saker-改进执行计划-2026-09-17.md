### 2026-09-18 追加：子代理结果回收（第 9 项剩余）

问题：`scanner`/`semgrep` 这类长工具有 `runTrackedTask` 自动收口，但 `subagent` 家族没有——
模型漏调 `operation_task` 时，台账里那条 queued 任务会一直挂着，主代理看不到"这个方向
已经跑完/失败了"，要么重复派单，要么把没收口的意图当成还在进行。

做法（`stage-gate 1.6.2`）：按宿主生命周期事件回收，不碰工具结果改写

- `subagent/start` → 唯一匹配的 queued 任务转 `running`（顺手挡住"还在跑就被别人 claim"）。
- `subagent/end` → `completed` 收 `succeeded` 并写入子代理**自己的**最终输出；
  `error` 收 `failed`；`aborted` 收 `interrupted`（可 retry）。
- 绑定沿用保守规则：同 owner 别名 + 同 session，且候选唯一才动。

两个真宿主实测约束（先踩坑后落地，写下来省下一轮）：

1. **`subagent/start|end` 是作用域事件，监听器拿不到 parent**：
   发射器用 parent 当 scoped dispatch 的 carrier，但回调只传 `info`
   （`lifecycle.ts`: `callback(info)`）。所以 `ctx.on("subagent/start", (info, parent) => …)`
   里的 parent 永远是 undefined——必须挂 `agent/created`，再用 `agent.ctx.on(...)`
   注册作用域监听，把 agent 闭包进去；`agent/disposed` 时释放。
2. **不能用 `tools/result` 收口**：原生 `subagent` 是异步派发，工具结果只是
   `started subagent <id>`。按它收口会把任务在派发瞬间标 succeeded、摘要只有那句
   "已启动"——典型假成功。实测记录见
   `_ref/tools/probe-subagent-recycle.mjs`（真跑一次 subagent，断言 summary 里
   是子代理自己的输出而不是派发确认）。
3. 事件里的 `provider` 是 provider id（原生工具是 `spawn`），不是工具名；
   别名表补了通用 `subagent`，让模型写的 `owner: subagent` 也能命中。
4. **mock 序列会被辅助请求抢走**：标题生成等无 `tools` 请求也会打
   `/chat/completions`；旧探针的全局 sequence 会先把 `tool_call_success` 消费掉，
   表现为 release gate 偶发 19/20。现在 mock 按“第一个带 tools 的主请求”返回
   subagent 工具调用，其余请求成功；修复后连续 10/10 通过。

  证据不足的草稿**必须仍然过不了 P2 结构门禁**——否则生成器就成了新的"造假通道"。
- 结构化 JSON 校验新增**非阻断一致性告警**：`verified` 缺复核依据/二次评级、
  `fixed` 缺复测记录、`confirmed` 缺 evidence、`baseline === diffEvidence` 都会输出
  warning，但报告仍 `ok=true`，语义裁决留给复核员。

### 2026-09-18 追加：指标历史与趋势（第 7 项剩余）

单点数字只能回答"现在多大"，回答不了"是不是在慢慢变胖"。护网最关心的工具面、
请求体、任务成功率需要**随时间的序列**：

  上限 200 行（丢最旧），同盘临时文件 + rename 写入；**没测到的量写 `null` 不写 `0`**

- `scripts/record-metrics.mjs`：把**已有产物**里的数字记一行——长会话审计的工具面/请求体、

### 2026-09-18 追加：知识检索的混合语种召回（第 5/6 项剩余）

先用真实查询找缺口，再动手：中文提问 + 英文术语是最常见用法，而旧实现只有一条
BM25 排序——「Sigma 检测规则 可疑 powershell 编码命令」**只命中一篇无关中文文档**，
而同一语义的英文查询能命中 3 条 `proc_creation_win_powershell_base64_encoded_*.yml`
（对症文档其实排在第 9）。三件确定性改动（不引入向量库、不调模型）：

1. 中文术语按**人工对照表**替换成英文说法后整句再检索（编码命令→encoded command 等，命中 -1.5）；
2. 混合查询额外跑一遍"只含拉丁术语"的 FTS 计划（powershell / CVE 号这类高精度词单独进榜）；
3. **覆盖度 rerank**：命中查询概念数 ×3（封顶 +12）重排同一候选集，
   命中 4 个概念的文档超过只命中 `rule` 的元数据噪声。

评测集扩到 **40 条人工核对用例**（新增 10 条带精确 `expectPaths`：sigma 检测规则、
计划任务持久化、DFIR 内存取证、Android 证书固定/组件越权、云 SSRF 元数据、K8s RBAC、
AD CS ESC1、.NET 反序列化、Java JNDI）。实测：Top-1 95.0% / Top-5 100% / MRR 0.968、
负样例标记 4/5。
**2026-09-18 继续扩到 52 条**：新增原型污染、GraphQL、OAuth redirect_uri、格式化字符串、
RSA 共模、APK 逆向、Azure Managed Identity、DCSync、Sigma LSASS、UART/JTAG、
iOS Keychain、Linux auditd 持久化。实测 Top-1 94.2% / Top-5 100% / MRR 0.965、
低置信 Top-1 5.8%、平均 33.4ms；达到计划写明的“50 到 100 条”下限。
评测脚本同时把**最小样本数**变成硬门禁（正样例 ≥50、负样例 ≥5）；用 1 正 1 负
反向验证会亮红，防止删掉大部分用例后用 100% 指标制造假绿。反向锁本身已加入
`run-all-tests`（`knowledge-eval-guard`，3 条断言）。

**顺手修掉的性能坑**：改动一度把平均耗时推到 ~375ms，CPU profile 显示大头根本不在检索——
`ensureKnowledgeIndex()` 每次检索都会调 `status()`，而它每次都 `SELECT COUNT(*)` 整表
（8.4 万 chunk ≈140ms）。计数只在重建/失效时变，改成进程内缓存后平均耗时
**375ms → 34.9ms**（比改动前的 230ms 还快 6.6 倍），质量指标不变。

**装配路径上的同类坑（`knowledge-hub 0.3.2`）**：知识库 manifest 每回合都会装配一次，
旧实现每次重算 `stats()`（全量遍历 9.5k 文件，冷 348ms / 热 ~33ms；2 轮会话实测回调被调 3 次）。
改成缓存（5 分钟 TTL + 导入/同步/重建显式失效，空库也缓存）后装配期这次遍历归零。
**另一个同类坑（`method-stack 0.1.16`）**：方法目录 `fullCatalog()` 每回合遍历目录并读取全部
`prompt.md`（实测中位 8.5ms）。改成 60s TTL 缓存，并在 `clone / restore / save-prompt`
三条真实写路径显式失效；回归用临时 `DSH_HOME` 走 RPC handler，验证保存后立即读到新正文。
装配期中位降到 0.1ms，避免把“方法正文保存后不生效”换成缓存旧值的新问题。
**工具面体积继续观测（第 2 项剩余）**：30 轮宿主审计现在写入首轮工具定义体积前 20 和前缀聚合。
当前合计 94 个 / 83920B；宿主内置 `pwsh` 4491B、`workflow` 4060B 最大，插件侧是
`redteam_*` 11738B（10 个）、`campaign_*` 5795B（9 个）、`operation_*` 5520B（7 个）、
`subagent_*` 3321B（3 个）。真实 trace 只有 7 次调用，尚不足以证明这些是“低频包”，
因此本轮不硬收；等真实护网调用分布出现后再决定按需加载，避免省 token 反而误伤成功率。
**顺带补了审计的漏检**：30 轮工具面审计以前只断言"工具面稳定"，实测一个插件因语法错误
整个没加载时它照样全绿；现在断言 `knowledge_search/stage_gate/operation_goal/
campaign_memory_write/redteam_finding_register/tool_pack` 必须在场（用假工具名反向验证过）。

## 5. 长期记忆能力

**关键差距**

- PentAGI 使用 PostgreSQL + pgvector + Graphiti 维护长期知识。

**现有链路**

- `campaign-memory`：打法、指纹、工具经验、教训、方向。
- `knowledge-hub`：手册、PATT、知识包、CVE/Exploit-DB。

## 8. 报告交付与项目工作台

**关键差距**

- StrikeAgent 有资产画像、攻击路径和成品 HTML/PDF。
- PentAGI 有 flow report 和可观测面板。
- Saker 当前 Markdown/HTML 能力已有，但报告交付和结构化程度仍落后。

**改进目标**

- 统一 report schema。
- Markdown、HTML、JSON，PDF 从 HTML 打印。
- **项目工作台按项目共享一个**，显示目标、阶段、开放意图、中断任务、失败、
  关键 finding 和记忆利用率；不在每个会话重复创建独立面板。

**验收**

- 单人一眼看出需要人工处理的事项。
- 报告内容能从结构化状态生成，不靠模型自由发挥。

## 9. Agent 内部协作与统一本地状态

**关键差距**

- BreachWeave 有 Manager / Solver / Observer。
- PentAGI 有专业 Agent 分派和结果回收。
- Saker 的子代理状态仍分散，容易重复执行。

**边界**

- 只做单机单用户。
- 不做多真人用户、RBAC、服务端分派。
- 复用现有长期记忆和任务状态，不盲加新层。

**验收**

- 两个 Agent 不会重复领取同一任务。
- 子代理结果、失败和产物能回收到主会话。
- Observer 只做观察和纠偏，不抢占任务。

### 2026-09-18 收口：执行面阻塞与配置路径直连

这两个问题都不是新增功能，而是现有能力在真实护网路径上的断点：

1. **`settings.yaml.lock` 死锁**
   - 宿主 `atomic-write` 只在 2 秒后报超时，崩溃进程留下的 PID 锁会永久堵住
     API key / 模型端点保存。
   - 宿主层按“只回收可解析且已不存在的 PID”修复；活进程、空锁、未知格式不碰。
   - `sec-config 1.3.22` 同时保留插件级兼容兜底：捕获锁超时后只重试一次。
   - 真宿主实测：隔离 home 下写死 PID 锁后 `settings/mutate` 43ms 成功，锁文件消失。
   - 反向验证：临时关掉宿主回收逻辑后，旧报错必须重新出现；恢复后字节一致。

2. **安全配置路径没有真正接到扫描器**
   - 原先扫描器只认 `PATH`；设置页里配好的绝对路径会被误报“未安装”。
   - `scanner-tools 1.0.12` 读取同一 `sec-config` 命名空间，按 `entries / tools`
     选路径，配置失效时按 `roots` 找回正确文件；Python 仓库（sqlmap / Impacket）
     走 Python 解释器，多入口套件不会误执行选错的那个 `.py`。
   - 外部扫描器从 `spawnSync` 改为异步子进程：nuclei/ffscan 等等待不再冻结宿主
     事件循环；超时与输出上限保持原有约束。
   - 新增断言覆盖：配置路径直连执行、Python 启动、root 回退、事件循环不阻塞。

### 2026-09-19 收口：UI 性能实测（否证 + 量具纠错）

用户提过「性能问题」，这一轮专门去量。**结论是当前 UI 没有性能问题**：

| 操作 | DOM 更新 |
|---|---|
| 设置弹窗打开 | 7–13ms |
| 11 个设置分区切换 | min 4 / median 7 / max 17ms |
| 知识库「导入知识源」（8395 篇）tab 切换 | 6ms |
| `browse` RPC（20 包 / 66 分类递归计数） | 1–31ms |

这条结论一半的价值在**否证**：第一版量具把**自己的开销**算进了被测对象，

所以「知识库一大坨翻来翻去」是**信息架构**问题（已在排版与分组上修掉），
不是渲染慢。见《Saker-UI性能实测与量具纠错-2026-09-19》。

### 2026-09-19 事故与修复：WebShell 编辑覆盖导致数据丢失

**事故**：验证 WebShell 设置页时，我把用户真实文件
`E:\工作\Web Security\Tools\01-WebShell管理\WebShell\jsp_antsword.jsp`
用「编辑内容 → 保存」覆盖成了 31 字节测试串；本机无副本、回收站收不到就地覆盖、
目录非 git 仓库，无法字节级还原。最终按同目录 JDK9 孪生文件
（`jsp_antsword_jdk9.jsp`，未被破坏）**功能等价还原** 502 字节。

**根因**：`self-content-set` 直接 `writeFileSync` 到用户目录，**无备份/无版本/无撤销**。

**修复（`webshell-mgr 1.1.30`）**：覆盖前先备份到同目录 `.backups/`（每文件留 5 份），
返回值带备份路径，界面提示「旧版已备份到 .backups/」。
修的过程中被自己的测试抓到一次：第一版时间戳只到秒，同一秒连写会互相覆盖，
7 次只剩 1 份；改成毫秒 + 随机尾巴后符合预期。

**做法纠正**：凡是会写用户数据的验证，**先把库根指到隔离目录**；
只读浏览才用真实库。

见《Saker-WebShell编辑数据丢失与备份修复-2026-09-19》。

### 2026-09-19 收口：破坏性操作可恢复性审计

事故之后把问题从"我下次小心"升级成"还有哪些地方能一键永久删用户的东西"，
扫全部插件的 `rmSync/unlinkSync/writeFileSync` 破坏性路径：

| 端点 | 原状态 | 处理 |
|---|---|---|
| `webshell-mgr self-content-set`（覆盖马文件） | 无备份 | ✅ 1.1.30 先备份 |
| `webshell-mgr self-remove(deleteFile)` | 直接 unlink | ✅ 1.1.31 删除前备份 |
| `knowledge-hub remove` | 直接 rm | ✅ 0.3.16 移进同层 `.trash/` |
| `skill-browse remove-skill` | 直接 rm | ✅ 1.1.10 移进技能目录 `.trash/` |
| `method-stack restore` | 直接 rm | ✅ 0.1.18 移进 `methods/.trash/` |
| `method-stack opening-save 清空` | 直接 rm | ✅ 0.1.17 覆盖/清空前都备份 |

统一做法：**同卷 rename 进同层 `.trash/`**（原子、零成本、点开头所以不会
被目录浏览/技能发现/知识包扫描重新发现），只留最近 50 条。
界面都补了「已删除（移入 .trash/，可人工找回）」这类提示。

验证：三插件单测 `125 / 58 / 66` 全绿（含新增 8 条）；
真浏览器删除实测**先把库根切到隔离目录**，确认探测文件被删、备份落在 `.backups/`，
用户真实马库全程未被触碰。

见《Saker-破坏性操作可恢复性审计-2026-09-19》。
