# Saker 效果、性能与优化评估

补充：[ARTEX 代码差距与可借鉴设计](saker-artex-gap-analysis-2026-10-08.md) · [完整下一阶段目标与验收门槛](saker-next-stage-goals-2026-10-08.md)。

截至 2026-10-08，我的判断是：**可用于学习与有人监督的授权试用；尚不足以证明可以无人值守承担生产测试。** 当前优势是把资料、工具、任务与证据放在一个桌面工作流中，可以调节介入频率。最大缺口是缺少同预算的真实效果评测，以及跨服务与长任务的稳定性证据。

本轮按“仓库订阅 → 固定提交增量同步 → AI 提取 → 原文依据校验 → 待复核知识发布 → 检索”补齐更新链路。[实际 Desktop 验收、失败过程和性能数据](verification/source-maintenance-2026-10-08.md)。原始 Git 更新由程序完成；模型承担语义整理。让模型既追踪仓库变化又随意覆盖知识，会增加漏更新、幻觉和成本，不能替代提交、正文摘要和失败断点。

## 当前效果应怎样理解

实际知识检索 Top-1 90.4%、Top-5 98.1%，平均约 53 ms，说明已有资料定位可以帮助使用者。这个数据来自既有 52 个关键词/路径用例，不能解释为 98.1% 漏洞检出率。知识索引约 604.6 MiB，略超既有 600 MiB 体积阈值；Desktop 五个进程工作集合计约 1.11 GiB，也仍有压缩与索引优化空间。

公开仓库 194 个匹配文件已经同步；最终三篇 AI 试验只有两篇发布，一篇请求失败。多数资料仍在积压队列。成功发布的条目也可能把文件标题当作产品原文值，或缺少版本与适用条件，不能仅因 JSON 合规就认为知识质量充分。片段编号回填能解决引用抄错，不能证明摘要语义受到引用支持。

23 个知识包有现成同步能力，但本机刷新时间与上游提交时间要分开。PeiQi 和用户提供的 dayday 仓库本身较旧；Nuclei/Afrog 文件来源已有适配器，不代表本机已完成最新全库同步。当前不具备“覆盖全网最新 Nday”的依据。

本轮标准回归 83 套通过，说明覆盖的行为没有已知回归；其中大量用例来自静态目录和契约检查。真实 Desktop 验收仍捕获了依赖注册、模型截断和输出结构问题，证明代码测试不能替代实际宿主与模型检查。原 MCP 两项均未连接，四个已登记工具路径失效；这些是投入使用前具体需要处理的环境缺口。

## 与公开头部项目比较

下面是公开设计和本机证据的定性比较，未进行统一靶场对跑，没有项目排名或胜率结论。公开商业产品的描述属于其团队自述，不能当作独立验证。

| 项目/团队 | 公开实现的重点 | Saker 当前差距 | 合适的优化方向 |
|---|---|---|---|
| ProjectDiscovery Nuclei | 多协议模板执行、请求聚合、并发和 CI 工作流；官方模板签名可验证来源及完整性 | Saker 的来源整理与执行引擎仍是两个层次，未证明动态订阅资料可可靠转为探针，也没有同规模扫描性能证据 | 复用成熟引擎；把模板版本、签名、适用条件、运行结果与证据挂到任务，避免另造完整扫描引擎 |
| Black Lantern Security BBOT | 递归资产发现、模块/预设、事件流及多种输出 | 当前主要通过模型、工具与资产账本推进，尚缺大型资产任务的吞吐、背压与恢复证据 | 用确定性模块做大量发现与去重，模型只判断需要深挖的资产和异常 |
| PentestGPT | 自动测试 Agent 和会话持久化；发表过可重复评测研究 | Saker 没有同模型、同预算、固定数据集的公开效果档案，无法证明额外插件比普通 Agent 带来多少收益 | 建立普通 Agent 基线，做知识、台账、门槛、子代理分别启用/关闭的对照 |
| XBOW | 团队公开描述映射、协调、执行与验证分工；固定任务集评测与有限步数求解 | 现有成果与阶段检查能验证结构，独立的语义/可利用性复核仍不足；没有对应长期实战结果 | 先建立独立验证与失败重启策略，再按实测选择模型、代理数量与分工 |

## 优先级最高的下一步

1. **先做效果基线。** 冻结本地授权靶场、漏洞与阴性样本，保留未知版本、需要登录、无漏洞但有相似响应的案例。同模型同预算对比普通 Agent、Saker 主代理、Saker 加知识与少量子代理。统计成功复现数、误报、漏检、耗时、请求数、模型用量和人工介入次数。近期受控研究也强调模型一致的普通 Agent 基线：[Baselines Before Architecture](https://arxiv.org/abs/2607.13085)。
2. **把确认发现交给独立复核。** 复核者读取原始请求、响应、身份和对照结果，而不是只阅读探索 Agent 的结论。区分线索、适用性、复现和影响，复核失败保留原因。评估语义正确性，不只查文件和字段齐不齐。
3. **把知识维护做得更有选择。** 新增/变化优先；按产品别名、漏洞编号和正文归并，展示来源活跃度、最新提交、最后成功同步、正文缺口与积压年龄；支持长文分段精读和失败分类。先对小型已审核语料比较提取准确率，再扩大自动整理。
4. **优先减少昂贵的模型工作。** 抓取、索引、去重、版本筛选与固定验证交给程序；模型按需读片段。按每个确认发现的用量/耗时评估收益；批处理后合并重建索引，避免小变更频繁全库重建。不能把“每天 10 次”误读为严格货币预算。
5. **再优化并发与产品体验。** 先验证 1/2/4/8/16 个代理的吞吐、重复请求、内存、配额和恢复；人数越多不必然更有效。统一插件中文名称、清理历史模式说明，为新用户展示哪些能力可用、缺什么、如何恢复，而不是展示大量实现术语。

这批已完成仓库订阅与可恢复的资料整理通路；上面效果基线、独立验证、全部来源最新同步和 16 并发压力测试仍是下一阶段工作，未在本次完成。
