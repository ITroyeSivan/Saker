# Saker框架与工作方式重构方案

2026-10-03修订。依据用户最新要求和《AI辅助漏洞挖掘的一些思路-视频总结.md》。本文替代此前方案中的模式组织、主代理与子代理分工、研究推进方式；原来的移除SRC策略、简化情报更新、重写介绍、官方桌面实测和效率对比继续执行。用户已取消21:00期限。本文是验收依据；实现已进入统一验证，状态以实际验收记录为准。

## 1. 先说最重要的变化

Saker应当帮助人研究一个具体问题。人知道目标的业务、账号和可疑之处；AI负责查材料、比较请求、追查实现、做有限验证，再把发现和疑问交回人判断。不是接到一个域名，就自行决定把所有资产和漏洞都测一遍。

新工作方式：**你提供一个站和已有信息 → 主代理与你选定一个小目标 → 主代理直接研究，确有需要才分给站点子代理 → 沿相关路径连续研究和验证 → 当前任务完成或遇到真正阻碍时汇报 → 需要你补信息或改变方向时再讨论。** 新线索先记下，能服务当前问题的就继续查；不能因为发现每个疑点都暂停。

“小目标”必须具体，例如“普通账号能否调用这个人员查询接口”“这个上传接口对应什么业务功能”“这个服务是否满足某公开漏洞的条件”。“把这个机构挖透”“看看有没有漏洞”不能直接变成无限运行任务。信息少时，第一项任务可以只是有限地了解页面和已有请求，随后给人选方向。

## 2. 界面只保留一个专业入口

渗透测试下面放三个子模式：

| 子模式 | 人给什么 | AI先做什么 | 本轮给人什么 |
|---|---|---|---|
| 常规测试 | 一个站、业务说明、已有账号/流量、重点功能；资料不齐也能先做小范围观察 | 列出实际功能，和人选一个功能或一条流程，做正常行为与异常行为的比较 | 功能问题、已确认影响、下一项值得查的内容 |
| Nday发现 | 少量确认过的资产；已知产品/版本、扫描结果或怀疑的组件可补充 | 只查相关公开漏洞，先核对条件，再挑有办法验证的候选 | 适用条件、实际验证结果、未解决条件；不把指纹列表当漏洞 |
| 0Day挖掘 | 一个具体站和疑点、功能、请求或代码片段；缺疑点时先与人选方向 | 沿一条业务或处理路径追查：身份、对象、参数、处理过程和结果 | 新问题或新变体的证据；没有公开编号不代表首次发现 |

移除代码审计与CTF的模式入口、独立开场说明和默认工具组合。保留渗透任务中按需阅读JS、源码片段和补丁的能力；这不再是独立模式。旧会话和证据保留，不删除用户数据。

三个子模式的区别是这轮重点，不是三套互不相通的系统。同一个站发现明确组件时可以查Nday，发现业务异常时可以继续研究；沿用账号、报文和历史，不重新建三个代理。改变本轮重点时由主代理向人说明。

Nday不再默认拿到机构名就展开全面找资产；如果人确实要找入口，先独立约定范围和数量，返回候选让人挑站，再进入验证。常规和0Day同样不自动扩大目标。

## 3. 主代理与站点子代理如何分工

主代理负责与你交流、整理目标、分派小任务、汇总结果和控制总花费。它不重复阅读子代理看过的全部JS和报文，也不再充当第二个全站扫描器。

不默认创建子代理。小任务、短验证和主代理可以直接完成的工作，由主代理处理。只有确实需要隔离较多站点材料、承担一个清楚且较长的深入任务，或少量独立工作值得同时推进时，才分派。分派前写清任务、必要性、预算、预期结果和结束条件，不能把创建代理本身当成进展。

同一站点任务至多有一个负责深挖的子代理，运行中复用它，不按新疑点反复新建。建议通常只分派一个，确有必要时最多两个；计数包括正在工作、空闲、正在关闭及关闭失败的代理，不能只数忙碌代理。用户选中的站点先排队，不提前为每个站创建代理，不按URL、接口、CVE或脚本数量增加代理。子代理不能继续派代理。

子代理拿到的任务包括站点范围、已给的资料、本轮问题、可用身份和工具、请求及时间预算、何时向主代理报告。例如：“研究人员查询接口是否允许普通账号访问，先查看相关调用与已有请求，最多20次请求，10分钟后汇报；不测试其他站。”这些默认数字是可调建议，不是所有任务的统一死限制。

任务进行中，主代理向同一个子代理转交人的补充和修正。子代理只返回短报告：已知事实、已确认问题、失败原因、缺什么、建议下一步和证据位置。任务完成、失败、取消、超时或已决定暂停等待人补资料时，先保存结果、成本与续接信息，再调用宿主关闭/释放接口，确认已结束后移出活动列表。不能为了未来可能继续就一直保留空闲代理。

研究记录长期保留，活代理及时关闭。后续确需再分派时从记录恢复，不重新读全部材料；这不要求原代理仍存活。主代理结束或取消本轮工作时清理其创建的代理和实际外部子进程。只处理可确认属于本任务的对象，不清理其他会话或用户进程。

每次分派前核对宿主实际存活列表、清理终态残留并检查总数；每次任务结束执行清理。关闭失败必须显示出来，在确认释放前仍占名额，不能换名字继续创建。代理没有返回消息不等于已结束，也不能据此创建替代代理。运行较久后也应保持受控数量，不能累计出几十个。

不同站可以共享产品方法、接口结构等知识；登录凭证和一个站的漏洞结论不能直接移到另一个站。发现跨站线索时由主代理核对目标范围和身份适用性，再分配明确的小任务。

使用宿主能续接、能停止、能限制工具和代理层数的子代理能力。现有外部CLI代理插件声明不能保证部分限制，不能只在提示词里写“最多两个”就声称已控制并发。如果宿主无法可靠执行这些要求，明确降为主代理逐站处理，不悄悄启动不受控的CLI。

## 4. 在哪些时候与人商量

交互不应打断正常推进。当前任务、范围和预算已确定后，子代理可以自行查相关JS、核对请求和身份、验证有依据的候选、根据反证调整当前问题的验证步骤。发现新疑点不等于需要提问；不相关线索放入待办，不能擅自展开。以下时机才需要一条简短、具体的报告：

1. **开始前选问题。** 重述已有信息，给出两三个具体方向和推荐理由。已经明确指定方向就直接做，不重复问授权和资料。
2. **缺少无法自行取得的关键条件。** 新事实先自行核对已有资料；只有确实缺身份、权限预期或业务说明，且缺失会阻止可靠判断时，才一次问清。
3. **本轮任务查完，或有效路径走不通。** 合并说明检查了什么、得到什么、为什么卡住，给出“补资料继续”“换另一个功能”“结束这一轮”的具体选项。一个方法未命中且当前问题仍有其他证据支持的办法时，可以继续；不能因此展开无关功能或重复相同失败请求。
4. **需要改业务数据、扩大目标或显著增加成本。** 在已有授权内做好具体计划和恢复准备；新范围或缺失的必要许可不能靠用户没回复来推定。
5. **需要让人了解较长任务的进度。** 可以给简短、不要求回复的进度消息，继续工作；不把定时消息变成暂停或选择题。有实际阻碍则立即报告，不等待定时点。

IP封禁或正常业务访问被整体阻断时，停止受影响站点的请求。明确封禁提示出现后不再重试；原因不明时最多做一次必要的正常基线/连接状态核对，仍受阻就停止并报告。不轮换IP、代理、身份或编码反复碰运气，也不继续跑其他方法。普通接口403不能直接当成IP封禁，先结合正常业务是否仍可用判断。若阻断影响共享出口的多个任务，暂停相关任务，不能换站制造更多失败请求。

报告说清：何时开始、哪个正常请求失效、实际响应或连接错误、已停止哪些任务、哪些结果因此无法判断。用户决定恢复访问或改变计划；恢复后先确认正常基线有效，再继续原任务。封禁、登录失效、服务异常、实际安全/工具限制都不能算漏洞反证或测试通过。

人不必了解工具字段，只需回答业务问题。需要人给登录态时说清具体站点和用途，不索要整个机构的一堆账号。已有资料够用时继续做；关键资料缺失则等待，期间只做不依赖它的材料整理。实际桌面登录要求出现时立即告知，不代登录。

## 5. 视频中的挖掘思路，具体怎样用

### 从已有业务和数据包开始

先理解正常请求：谁发的、做什么、对象属于谁、正常结果是什么、凭证在何处以及预期用途。不要只有域名就猜一串漏洞。已有抓包是事实来源，不是绕过安全限制的说法。

登录页面、普通界面和后台都可以成为观察对象。0Day不再把“必须已经有后台/API成功报文”设为所有研究的前置条件；一个清楚的JS调用、登录流程疑点或业务行为也能启动材料研究。开始验证请求时，再检查实际范围、身份和对照条件。

### 看到不合理的业务联系，继续问为什么

“地图站里为什么出现教师档案接口？”值得继续看。AI先找引用位置、调用条件、目标服务和响应；人补充该站的实际用途，双方判断这是共用代码残留、正常集成还是权限问题。不要从接口名称直接跳到漏洞。

这种联想也用于上传、导出、审批、预约和证书查询。线索来自真实页面、业务资料和已观察行为，不靠把常见漏洞清单套到所有网站上。

### 查凭证能做什么，而不只看有没有凭证

视频里的关键疑点是前台拿到的凭证能否被后台错误接受、不同类型凭证的用途是否被混淆。研究要记录凭证的来源、原本用途、可用角色和服务端实际权限。无凭证401、带凭证200只能说明访问差异，还要核对返回的是谁的对象、该角色是否本来允许访问。

同样，改前端角色字段后出现菜单不等于后台权限已突破。必须验证服务端行为。跨端或跨系统存在同名接口也不说明凭证能够通用。

### 发现接口后，追到业务操作和实际效果

“有上传接口”只是起点。继续找哪个页面调用、用来处理什么文件、谁可使用、结果存在哪里、是否影响其他用户。视频中联想到logo，就是把隐藏接口与真实业务联系起来。

验证文件或业务状态变化，应使用约定的受控对象，记录前后结果与恢复状态。只返回success、得到文件路径或修改自己的允许对象不能自动算漏洞。权限读取、状态修改、文件处理和执行效果分别判定，不能都硬套当前私有JSON验证器。

### 深入分析要有明确问题

第一遍找接口和关键调用；第二遍围绕人的疑点追相关函数、认证包装、参数处理、懒加载文件和必要源码。记录哪些文件已看、哪些没看、为什么继续。文件没变、问题没变且无新线索时，不整包重读。

工具按内容去重，模型分批读相关片段；动态调用、缺失文件和解析失败留作未覆盖。出现构建或源码映射线索时再查，不因使用Webpack就认定泄露。密钥样式先定位用途，公开客户端Key不直接报严重问题。

### 查不下去就换具体方向，不草率结束整个站

403可能是正常权限、登录失效或访问阻断，分别处理。已有方法未命中，只关闭该方法；其他功能是否继续由主代理提出建议并与人沟通。实际策略限制则停止该分支，保留未覆盖原因，不能换标签继续。

视频的批量脚本思路用于把已经理解的验证做得准确、可复现。确认影响采用最小充分样本；不以获取大量真实敏感记录作为成果，也不把扩大范围当作“深入”。

## 6. 三个子模式的实际工作步骤

### 常规测试

人给站点和重点 → AI根据已有信息列出功能 → 人与主代理选一两个功能 → 主代理或确有必要的站点子代理正常走一遍并整理请求 → 检查具体权限、输入和流程问题 → 报告效果及卡点 → 人决定下一轮。

扫描器用于已选功能或明确产品检查，按需加载；不默认跑全模板、全字典、全参数。用户明确要基础检查时也先说明批次范围和预期产出。

### Nday发现

人给资产及线索 → AI说明哪些产品证据可信、哪些不清楚 → 检索少量相关漏洞 → 把“有可用方法”“缺关键条件”“不适用”分清 → 选条件最好的一组验证 → 返回实际证据或失败原因。

首次条件不足时，建议补一次关键观察或换一个已给的资产，避免在未知产品上反复匹配全库。情报源更新是后台维护，不能每测一个站重新抓全部资料。有价值发现时先报告，不擅自把用户尚未要求结束的任务全关掉。

### 0Day挖掘

人提出业务疑点，或与主代理从观察中选疑点 → 主代理或确有必要的站点子代理沿相关页面、JS、请求或源码追查 → 写出简短可验证判断 → 做正常/异常比较 → 根据结果继续追一层或反证结束 → 与人商量下一方向。

例如：“普通前台账号为什么能调用人员查询？”连续查调用与身份、核对对象和权限、验证实际影响；这些步骤不逐轮等用户确认。已有资料无法说明权限预期时再询问。用户中途补充“这个接口本应只给教职工后台”，由主代理转交原子代理，继续原路径。新变体或未公开问题不能仅凭无CVE命名成真正0Day。

## 7. 系统内部只保留必要的东西

沿用已有能力，不再加一套总控插件：

| 部分 | 留下的职责 | 要改的地方 |
|---|---|---|
| 会话与模式 | 渗透测试入口、三个子模式、人的当前问题 | 移除代码审计/CTF入口与默认配置，三个子模式使用同一站点记录 |
| 任务与子代理 | 分配站点、保存进度、预算、停止和恢复 | 真正限制同时工作数量；主代理收短报告；子代理不再派代理 |
| 资产、请求与资料 | 保存已有事实，按需读取原文 | 增加业务用途、角色、对象、相关JS位置；自动填已有事实 |
| 情报与方法 | 针对产品检索，复用审阅过的方法 | 不自动从机构名全面扩展；不强迫业务研究先排除全部已知漏洞 |
| 执行与证据 | 批次请求、对照、真实回执、结果未知时避免重发 | 将机械登记合并进执行；不同机制使用相应影响判据 |
| 成果查看 | 已确认问题、待验证线索、受阻和未覆盖 | 一眼看见哪个站、哪个功能、影响、证据与下一步 |

已有七项假设和频繁observe步骤对模型负担较重，要从“模型每轮填长表”改成程序保存事实，模型只补本轮判断与结果。保留控制范围、预算、身份和证据的检查，不靠删除检查来减少调用。

强制频繁观察可以变成批次结束自动记录；遇到异常立即回报。当前`private-json-read/v1`自动任务是可复用的一种方法，不应成为所有问题唯一的通行证。

## 8. 结果和花费怎样让人看懂

首页只需看见当前站点、本轮问题、谁在做、已用时间/请求/模型费用记录、最新发现、等待你回答什么。侧面可看排队站点和停止操作。不再用一堆流程名称表示进度。

结果列表先展示已确认问题。每项点开看到正常请求、异常请求、身份/对象、实际效果和复现方法；过程区显示线索、未命中与阻断，不能混成漏洞数量。重复根因可合并展示影响入口，但验证条件和证据分别保留。

省token的主要办法是缩小问题、按需分派、复用正在工作的同站子代理与已保存记录、程序批处理、只给模型相关片段和短报告。任务结束关闭代理，不用长期空闲来换所谓复用。主代理不重新分析全部材料；每个子代理只加载需要的工具。子代理本身也有成本，要合计主代理与全部子代理，不能只报主代理消耗。

是否省token必须实测：同模型、同推理设置、同业务数据和预算，记录实际token、缓存、请求数、时间、确认正例、误报与漏检。分别测三个子模式，并测试一个子代理、两个子代理的总成本。测试夹具和桌面模型会话的结论要分开，不能由单测推出现场检出能力。

## 9. 实施与验收

先改模式和人机对话，再接站点子代理及预算，再改各子模式的任务步骤，随后补业务材料分析和执行/结果衔接。保留此前资产路由、来源更新、响应复用、重复请求缓存、真实执行回执及成果证据的已有修复。
