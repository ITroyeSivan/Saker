# Saker CTF 真实模型工作流端到端验证（2026-09-19）

## 目的

前几轮验证集中在渗透（pentest）、WebShell、报告交付和设置页。CTF 模式此前只有
纯函数级回归，没有跑过「真实模型 + 真实夹具 + 真实门禁 + 成果页落库」的完整回路。
本轮补上这条线：**一个真实模型会话，从零解出 flag，登记成果，独立复核，过门收口。**

夹具为本地授权靶标（`http://127.0.0.1:18082/`，纯静态 HTML，返回一段标准 base64）。
不联网、不猜 flag。

## 配置

- 宿主：隔离测试 home（`_ref/dsh-home-test`），独立端口，不使用用户日常环境。
- preset：`ctf-solver`，模型 `deepseek-flash`，思考强度 `low`（按测试纪律）。
- 工作区：`_ref/ctf-model-check`。
- 代理：用户 `8788` opencode-proxy（`data_parse_fail=0` 版本）。

## 发现的问题

### 1. 表格类门禁的失败信息不可操作（已修）

`stage_gate ctf-solver/board` 首次 FAIL 的原文是：

```
table:challenge-board.md — .../challenge-board.md: 7 行（要求 ≥1），未填满行: L5,L7,L8,L9,L10,L11,L12
```

它没有说清真正的约束是**每行 ≥3 个非空单元格**。模型为了搞明白 `L5` 为什么不达标，
连续 9 步（step 16–24）去 `Get-ChildItem` / `Select-String` 翻
`node_modules/@dsh-external/dsh-stage-gate/lib/index.js`，最后靠读 `tableRows`
源码才反推出「表头列数不够」。

代价很直接：一个 1 分钟能改完的表格，花掉 9 步上下文，而且这类消息在
pentest / code-audit / incident-response / cloud-security 等**所有带表格检查的
门禁**上都存在。

**修复（`stage-gate 1.7.1`）**：失败信息自带可执行修法——说明需几行、每行几个
非空单元格、哪几行差在哪、以及没检测到表格时给一行可照抄的样式。

```
table:challenge-board.md — .../challenge-board.md: 表格共 7 行，全部行不达标：
L1(2格)、L3(2格)、...（需 ≥1 行、每行 ≥3 个非空单元格）
```

回归新增 5 条断言，覆盖列数不足、全部行不达标、达标通过、完全无表格四种形态。

### 2. 一次真实传输中断（已自愈，保留观测）

step 7 出现一次 `llm/retry`：

```
failure: {"message":"Stream ended without finish_reason","code":"TRANSPORT"}
retry: 1 / maxRetries: 5，delayMs ≈ 472ms
```

重试后同一 step 正常完成，整轮无数据丢失。这与本轮已修的代理 SSE keepalive
切帧问题同源，说明修复方向对，但**上游偶发断流在长会话里仍会真实出现**；
自动重试是有效兜底，不需要人工介入。后续按「重试次数 / 会话步数」持续观测，
如果在一次护网长会话里密集出现，再回头查代理上游。

### 3. 登记时禁止直接写 `verified` 的守卫是有效的

模型第一次 `redteam_finding_register` 带 `status=verified`，被拒绝并回了
「verified 不可在登记时直接写入——先登记 pending，复核后用 update/mark 同一次
给出 secondRating + secondRatingNote」。模型照做，最终得到 `verified`。
错误信息已经足够可执行，不需要改。

## 结论

- CTF 模式**在真实模型 + 真实夹具下可用**：识别、解码、复现、登记、独立复核、
  门禁、记忆、收口整条链路闭合，落库终态与工作区产物一致。
- 本轮把「门禁报错只说现象不说要求」这个横跨多个模式的可用性缺陷修掉，
  后续同类门禁失败不再需要模型去翻源码。
- 未发现需要阻塞交付的功能性缺陷。
