# Saker 知识库同步残骸回收（2026-09-19）

## 怎么发现的

用户第三次问「`_ref` 下怎么又是一堆目录，难道都是有用的？」时，顺手把
**知识库导入层**（`$DSH_HOME/refs/imports`）也一起扫了一遍，发现同样的问题：

```
C:\Users\12201\.dsh\refs\imports\
  .hacktricks.recover-1789742963715-10664-iae61v    6.7MB
  .hacktricks.recover-1789743503002-22076-eoad6a   20.6MB
  .hacktricks.recover-1789743818008-2132-wvhxx9    20.6MB
  .hacktricks.recover-1789752708084-30252-gzhhk0   20.6MB
  .owasp-wstg.diverged-1789742963708-10664-j80rj4   1.3MB
  hacktricks.diverged-1789624421558-32720-oe8co0   13.7MB
```

合计 **约 84MB**，全是同步逻辑自己留下的。

## 根因

`recoverDivergedPack()` 在 `git pull` 失败（浅克隆历史分叉）时走「重克隆」路径：

1. 先 clone 到 `.{packId}.recover-<ts>`；
2. 把旧目录改名成 `.{packId}.diverged-<ts>` 备份；
3. 再把临时目录改名成正式目录。

正常路径下两个目录都会被移走。但：

- **进程在第 3 步之前死掉**（或 clone 中途失败只留了半份），`.recover-*` 就永久留在盘上。
  真 home 里有 4 份，其中 3 份是完整的 1035 文件仓库。
- **每次分歧恢复都留一份 `.diverged-*` 旧仓库，而没人回收。** 状态文件里
  `packs[id].backup` 只记最近一次，之前那些备份从此没人引用、也没人删。

好的一面：`packRoots()` 明确排除了以 `.` 开头和匹配 `\.(?:diverged|recover)-` 的目录，
所以**这些残骸不会进检索索引**，没有污染搜索结果。它们纯粹是磁盘泄漏。

## 修复（dsh-knowledge-hub 0.3.11）

新增 `prunePackDebris(importsPath, state, options)`，`syncPacks()` 每次跑完顺手调用。

两种残骸**分开对待**，因为风险完全不同：

| 类型 | 里面可能有什么 | 默认行为 |
|---|---|---|
| `.{id}.recover-*` | 纯临时 clone，不可能有用户的东西 | 超过 `minAgeMs`（默认 60s，避开并发同步）就回收 |
| `.{id}.diverged-*` | **可能有用户对导入层做过的本地修改**，是最后一份拷贝 | **一份都不删**；只有显式 `includeBackups: true` 才回收，且保留 `state` 引用着的 + 每个 pack 最新一份 |

这个取舍是有意的：知识导入层是用户可写的，静默删掉唯一的本地修改备份，
比多占几十 MB 严重得多。

回归新增 10 条断言（默认档只清临时目录且备份一份不动、显式档才回收多余备份、
state 引用的备份不动、新鲜临时目录不动、结果可对账、第二遍幂等）。

## 一次性清理

工具：`_ref/tools/prune-knowledge-debris.mjs`（dry run 默认，删除走回收站）。

```
node prune-knowledge-debris.mjs --home real                      # dry run
node prune-knowledge-debris.mjs --home real --apply              # 清孤儿临时 clone
node prune-knowledge-debris.mjs --home real --apply --include-backups
```

真 home 执行结果：

```
回收 4 个残骸目录，约 68.4MB
  - .hacktricks.recover-1789742963715-10664-iae61v
  - .hacktricks.recover-1789743503002-22076-eoad6a
  - .hacktricks.recover-1789743818008-2132-wvhxx9
  - .hacktricks.recover-1789752708084-30252-gzhhk0
保留 2 个：
  + .owasp-wstg.diverged-1789742963708-10664-j80rj4
  + hacktricks.diverged-1789624421558-32720-oe8co0
```

> 执行时被 `recycle.py` 挡了一次：`~/.dsh` 是它的保护根（2026-09-14
> 「把真 home 的 sessions 送进回收站」那次事故之后加的红线）。这是**对的行为**——
> 工具没有绕过它乱删，而是显式加 `--allow-protected` 覆盖，并且自己再加一道闸：
> **只回收名字确实匹配残骸模式的目录**，任何以 pack id 命名的真实目录直接抛错拒绝。

两个 `.diverged-*` 备份故意留着（各 1.3MB / 13.7MB），因为它们可能含用户本地修改。

## 顺带修掉的两个同类问题

### 1. `_ref` 顶层目录改成白名单制

旧清理脚本是「每跑一轮验证就把新目录名逐条加进 ODDS 清单」，于是清理器永远追在后面。
现在反过来：`_ref` 顶层目录只有在 `KEEP_ASSETS`（删了要重来的资产）或
`KEEP_RUNS`（**必须在脚本里写清被哪个报告引用**）里才能留，其余一律回收。

效果：顶层目录从 **37 个收敛到 18 个**，删除清单从 86 项收敛到 **0 项**（dry run 归零）。
另外：

- 正在运行的服务把 stdout 重定向到 `_ref/*.log` 时删不掉，脚本现在识别成
  「仍被进程占用」并明确跳过，不再打印一句 `SHFileOperationW 返回 32` 当失败；
- 每轮 CFT 验证留下的 `.<任务>-tid`（上一轮的浏览器标签 id）现在会被清掉。

### 2. 表格类门禁的失败信息不可操作

见《Saker-CTF真实模型工作流-2026-09-19》第「发现的问题」节：`stage_gate` 只报
「未填满行: L5,L7,…」而没说「每行要 ≥3 个非空单元格」，模型为此翻了 9 步
`node_modules` 源码。已在 `stage-gate 1.7.1` 修成自带修法。
