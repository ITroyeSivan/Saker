# Saker UI 性能实测（含量具纠错）（2026-09-19）

用户提过「还有很多别的体验、**性能问题**」。这一轮专门去量，结论是
**当前 UI 没有性能问题**；但为了拿到这个结论，先得把**量具本身**修对——
第一版量具报出了两个吓人的假数字，差点写成"性能缺陷"。

## 最终实测（干净数字）

在页面内计时（记录起点 → 派发完整事件链 → `MutationObserver` 记首个 DOM 变化），
一次 eval 完成，不含任何 Node 侧开销：

| 操作 | DOM 更新耗时 |
|---|---|
| 设置弹窗打开 | **7–13ms**（首次 DOM 变化） |
| 11 个设置分区互相切换 | **min 4ms / median 7ms / max 17ms** |
| 知识库「导入知识源」tab（8395 篇）切换 | **6ms** |
| 知识库「随包手册」tab 切换 | **6ms** |
| `browse` RPC（列 20 个知识包 / 66 个 PATT 分类） | **1–31ms** |
| 知识检索（52 条评测集） | 平均 31.9ms |

首次可交互：`goto` 到 `readyState=complete` **约 622ms**（本机隔离宿主）。

> 这三个数（弹窗 7–13ms、分区 4–17ms、tab 6ms）都远小于人眼可感的 100ms，
> 所以**没有需要优化的 UI 渲染热点**。

## 三个把量具自己算进去的坑（都真实踩到了）

### 坑 1：在 Node 侧循环采样，把进程开销算进被测对象

第一版是「点一下 → 每 50ms 起一个 `node cdp.mjs eval` 读文本长度」。
每次 `eval` 要 spawn 一个 node 进程（~100ms），于是：

- 报出「知识库来源 tab 切换 **5.5 秒**」；
- 后来发现 `cdp-click.mjs` **自己**就要 5.4 秒才返回（3 次 spawn + CDP 往返），
  而它返回时内容长度**已经是新值**——说明渲染早就完成了，5.5 秒全是量具的开销。

### 坑 2：把「点当前已激活项」当成「永远不稳定」

设置弹窗默认就停在「通用设置」。第一版探针点了「通用设置」后等文本长度变化，
而重复点当前面板**本来就不会有任何变化**，于是报「6 秒超时未稳定」。
现在的量具把"无变化"判为 settled 并标注「已是当前项」。

### 坑 3：观察器不注销 + 结果键跨轮复用

`MutationObserver` 用完不 `disconnect`，上一次的观察器会继续往**同名键**里写；
而它闭包里的 `t0` 是更早的时刻，算出来的耗时更大——于是数字一路虚高成
`38s / 38s / 38s`。修法：每次测量用唯一键 + 用完注销。

## 修正后的量具

`_ref/tools/probe-ui-perf.mjs` 已按上述三条重写：

- 计时**全部在页面内**，一次 eval 完成，Node 只负责发起与读取；
- 观察器用完注销，结果键每轮唯一；
- "无变化"按"已是当前项"处理，不报假超时。

复跑结果：

```
11 个设置分区：min 4ms / median 7ms / max 17ms
```

## 结论

- **没有发现 UI 性能问题**：面板切换、知识库大目录切换都是**个位数毫秒**，
  最重的 `browse`（20 包 / 66 分类递归计数）也只有 1–31ms。
- 之前记录的「知识库一大坨翻来翻去」是**信息架构**问题（已在排版与分组上修掉），
  不是渲染慢。
- 这条结论的价值有一半在**否证**：如果不先修量具，就会把 5.5s 的假数字
  当成真缺陷去"优化"一个本来 6ms 的操作。
