## 二、已修复问题

### 1. SQLite 首开竞态与坏库自愈顺序

**现象**

- 8 个子进程首次打开六类 SQLite store 时偶发 `database is locked`。
- Node `DatabaseSync` 构造时不一定读取库头，坏库实际在首条 WAL/SQL 语句才报
  `file is not a database`。

**修复**

- 六套 store 统一：先开库，只有明确的 `NOTADB` 才备份重建。
- `busy_timeout` 设置早于 WAL。
- WAL 切换遇到 `BUSY/LOCKED` 时短退避重试，截止 5 秒，不误判为坏库。

**验证**

- `scripts/test-store-open-worker.mjs`：8 进程并发首开六类 store。
- `scripts/test-task-recovery.mjs`：并发首开后完整性检查通过。

### 2. 长任务状态只能手动推进

**修复**

- `dsh-stage-gate` 新增 `runTrackedTask`：按 session + owner + 工具名绑定唯一 queued 任务。
- `dsh-scanner-tools` 的 nuclei/httpx/ffuf/注册表扫描器自动执行
  `queued → running → succeeded/failed`。
- `dsh-semgrep-audit` 同样接入。
- `dsh-route-boost` 恢复盘只显示未收口任务。

**验证**

- 16 路任务并发 start/progress/succeed。
- scanner 与 semgrep 的失败路径自动落 `failed`。
- 真实工具边界测试见 `scripts/test-task-recovery.mjs`。

### 3. 工具产物同毫秒/同秒撞名

**现象**

- scanner 使用 16 位随机后缀，200 次同毫秒写入约 30% 概率碰撞。
- semgrep 文件名只精确到秒。

**修复**

- 两侧统一为毫秒时间戳 + 48 位随机后缀。

**验证**

- scanner：同秒 200 次落盘全部唯一。

### 4. Saker 工具结果裁剪几乎不生效

**现象**

- 三个 preset 将 `tool-result-pruner.thresholdChars` 配成 `1000000`，
  `headChars=900000`、`tailChars=90000`，等于一次大输出仍可占满大量上下文。

**修复**

- 三模式统一为：超过 32768 字符裁到 24576 头 + 6144 尾；
- `scripts/test-tool-budget.mjs` 增加配置门禁，防止再次写回百万阈值。

### 5. 低频工具包真实性问题

**发现的边界**

`agent.ctx.tools.restrict()` 只过滤全局工具；preset 平面注册的 scanner 工具不受其控制。
因此最初设想的 AD/内网工具包实际收不掉，已撤掉，避免 UI 宣称与真实行为不一致。

**当前实现**

- `dsh-tool-scope` 新增 `tool_pack` 按需入口。
- 只默认收起可被宿主过滤的全局 WebShell 工具包（13 个工具）。
- `list / load / unload` 均按真实全局工具存在性判断，不虚报可用。

### 6. 模型思考强度配置的路径缺口

**现象**

- 安装器传入的 `DSH_SRC` 默认是 Saker 仓库，不是 dsh 源码树；
  `configure-model-reasoning.mjs` 找不到 `js-yaml`。

**修复**

- 脚本自动发现 `_ref/dsh-src-*`，不再依赖人工设置环境变量。

### 7. 模型出站缺少凭据脱敏

**修复**

- `sec-config` 内置模型代理新增 `redaction=secrets|off`，默认 `secrets`。
- 只处理消息内容中的 Authorization/Cookie、密码、私钥、云密钥、常见 token
  和 URL 查询串里的秘密值。
- 目标 IP、域名、URL 路径和普通验证载荷保留，避免把授权测试上下文改到不可用。
- 工具 JSON schema 不进入脱敏遍历，避免改坏可执行契约。

**验证**

- `dsh-sec-config/test/run.mjs` 覆盖脱敏、目标保留、schema 保持和关闭模式。
- 设置面板可切换「密钥脱敏 / 关闭脱敏」，健康检查显示脱敏次数。

**后续修正（`sec-config 1.3.12`）**

- 模型代理转发前校验目标 URL：只接受相对路径，绝对 URL 与协议相对 URL
  会返回 `400 UpstreamTargetRejected`，并再次核对最终 origin 与配置上游一致。
- 上游重定向继续使用 `redirect: manual`，不跟随到其他 origin。
- 健康检查保留最近 20 次出站摘要（方法、路径、状态、剥字段和脱敏计数），
  设置面板显示最近一条；真实 loopback 链路测试覆盖 origin 拒绝和审计记录。
- 目标是“明确模型网关边界”，不是内容级 DLP；字段级数据分类仍属于后续项。

**继续修正（`sec-config 1.3.13`）**

- 脱敏计数按 Authorization、Cookie、私钥、Bearer、云密钥、GitHub token、
  API key、JWT、普通 secret、URL query secret 分桶。
- 健康检查保留 `redactedKinds`，设置面板显示脱敏总数后的主要类型；
  真实 loopback 链路测试同时断言分桶不为空。

### 8. 长期记忆只有“读过多少次”，没有“是否真的有用”

**修复**

- `campaign-memory` 新增 `campaign_memory_feedback`：
  `helpful / misleading / obsolete`。
- `helpful` 提权，`misleading` 降权，`obsolete` 退出召回但按 id 仍可审计；
- 反馈分参与 30 天半衰热度排序，零反馈旧数据保持兼容。

**验证**

- `dsh-campaign-memory/test/run.mjs` 覆盖反馈累加、降权、退役、按 id 读取与统计。

### 9. long task 自动绑定的 session 隔离没有落库

**现象**

`operation_intent` 接收 sessionId 做锚点校验，但注册后的 intent 没有把 sessionId 写入状态；
并行会话下，同 owner 的 queued 任务可能被另一个会话自动认领。

**修复**

- intent 落盘 `sessionId` 与 `mode`；
- 自动任务绑定只认可同 session 的候选，session 不匹配直接跳过；
- 增加“同 owner 多候选不猜测绑定”和“session 不匹配不抢”两个回归测试。

**后续修正（`stage-gate 1.6.1`）**

- owner 从子串 `includes` 改为边界匹配：短 owner（如 `scan`）不再误匹配
  `rescan` / `webscan`，只有完全相同或 `_` 分隔的前后缀关系才允许自动收口。
- 定向任务恢复套件 `21 ok / 0 fail`；全量 `dsh-stage-gate` `196 ok / 0 fail`，
  行为锁 `36 ok / 0 fail`。
- 已重新打包、安装，并核对真实与隔离 profile 各 `153` 个文件字节一致。

**真实宿主重启恢复（追加验证）**

- 在真实工作区落一条 `running` 意图任务，把心跳改为 31 分钟前。
- 启动 dsh 宿主后干净关闭，再启动第二个宿主；由真实模型工具面调用
  `operation_progress`，宿主内状态机将任务恢复为
  `interrupted`，原因是 `heartbeat expired`。
- 证据与复跑脚本：`_ref/task-recovery-host-audit/summary.json`、
  `_ref/tools/run-host-task-recovery-audit.mjs`；已接入
  `release-gate --task-baseline`。
- 连续 5 次重复运行全部通过，任务均恢复为 `interrupted`，未见端口复用或状态初始化竞态。

## 五、大工具结果压力触发实测

先按 `1M` 正常上下文做真实宿主验证：`pwsh` 输出 `120000` 字符，执行器截到
`50000` 字符；下一轮请求仍带完整 `50000` 字符。这个现象不是 pruner 配置失效。
读 dsh `compaction-basic` 源码确认：内置 `toolResultPruner` 只在
`agent/pre-step` 的压力门或 context-overflow 恢复路径运行，不是每返回一个
tool result 就立即裁剪。

随后把隔离环境模型窗口临时改为 `80000`，阈值即 `80% = 64000`；
用 dsh 自带 `llm-mock-server` 驱动真实宿主连续执行 3 个 `120000` 字符输出：

| 指标 | 结果 |
|---|---:|
| 真实模型请求数 | 5 |
| `pwsh` 工具面 | 94 个工具，包含 `pwsh` |
| 发生裁剪的请求 | 第 5 个 |
| 被检查 tool result | 3 个 |
| 最长裁剪后内容 | 30759 字符 |
| 裁剪标记 | 命中 |
| 超过 32768 字符的结果 | 0 |

证据：`_ref/large-result-audit/`，复跑工具
`_ref/tools/run-large-result-prune-audit.mjs`。结论是：Saker 的 32K 配置在
真实压力门后生效；正常 `1M` 窗口下不在每个大结果后即时裁，保留完整上下文，
到 80% 压力才做模型无关裁剪，再按需要摘要。这个边界必须写清，不能继续声称
“任何大结果都会立即裁到 32K”。
该压力门审计连续重复 3 次，最长结果均为 30759 字符且标记命中。

### dsh 0.1.6 浏览器能力适配判断

dsh 自带 `@playwright/mcp@0.0.80`。本轮直接对固定 CLI 做 stdio 握手，
确认服务端为 Playwright `1.63.0-alpha-2026-08-31`，协议
`2024-11-05`，公开 24 个 `browser_*` 工具。
握手连续重复 3 次，服务标识、协议和 24 个工具完全一致。

结论：不重写浏览器层。正确接法是把它作为 mcp-studio 的 stdio server，
用 `--headless --isolated --image-responses omit` 作为保守默认，并采用
`exposure=proxy`（24 个工具收成 `mcp_search` / `mcp_call` 两个入口）。
`dsh-mcp-studio 1.1.14` 已加入固定版本的一等预设，默认关闭；导入后
按 auto/proxy 收敛工具面。没有静默改用户 settings，因为浏览器属于实验依赖，
应由用户/Agent 明确选择是否启用。

## 七、尚未解决的问题

1. `tools.restrict()` 不能控制 preset 平面工具；若后续要让 scanner 也按包加载，
   需要先改 scanner 的注册平面或设计宿主级 scoped restriction。
2. 普通长会话已有第 10 轮真实抓包；第 30 轮可用确定性 mock 模型补压测，但仍需
   再做一次打包发布前复跑。
3. 任务 owner 仍是模型登记字段；自动绑定不做模糊猜测，避免把任务错误收口。
4. 这些改进目前只完成单机路径；release gate 已建立，但外部靶场/任务成功率基准仍未接入。
   本机没有 Docker，Argus / Cybench 那类容器化基准无法直接跑；结论是先用
   “真实宿主 + 本地任务集”的替代基线，不假装已经接入外部基准。
5. owner 已做保守边界匹配，但仍是模型登记字段；在没有稳定宿主 task metadata 前，
   宁可拒绝自动绑定，也不猜测归属。
6. sec-config“最近出站”面板已完成静态/单测验收；本轮真实 Chrome for Testing
   验证了 redteam 成果页和项目工作台非空白渲染，没有改用日常 Chrome。
7. 报告 JSON 目前只做 schema 校验与 legacy 迁移，不做字段级语义回溯；
   跨版本字段增删仍以“校验失败即报错”为准，不静默补默认值。

### 混合语种召回缺口与修复（2026-09-18 追加，`knowledge-hub 0.3.0`）

上面那句"等出现真实的语义缺口样本再升级"——这一轮就抓到了样本：

- **缺口**：中文提问 + 英文术语（最常见的用法）召回很差。
  「Sigma 检测规则 可疑 powershell 编码命令」旧版**只返回 1 条无关中文文档**；
  而语义等价的英文查询 `sigma rule powershell encoded command detection` 能命中 3 条
  `sigma-rules/rules/windows/process_creation/proc_creation_win_powershell_base64_encoded_*.yml`。
  对症文档其实**排在第 9**（分数 23.9），top-1 是只命中 `rule` 一词的
  `net_connection_win_domain_ngrok.yml`（28.4）——CJK bigram 与路径元数据把 BM25 带偏。
  同类问题还有 `计划任务持久化 排查`（召回不到任何 sigma 规则）、
  `memory forensics process injection volatility`（只有 2 条 score 5 的弱命中）。

**修复（三件确定性改动，不引入向量库、不调模型）**：

1. **术语替换**：新增人工对照表（编码命令→encoded command、检测规则→detection rule、
   计划任务→scheduled task、内存取证→memory forensics、进程注入→process injection、
   持久化→persistence、供应链→supply chain、证书模板→certificate template…），
   把中文术语替换成英文说法后**整句再检索一遍**（命中 -1.5）。
2. **拉丁术语单独成计划**：混合查询额外跑"只含拉丁术语"的 FTS 计划，
   让 `powershell`、CVE 号这类高精度词有自己的进榜机会；同时把"每个计划都跑完"
   写进引擎（旧代码"凑够 limit 就 break"会让后置兜底计划挤掉主计划召回，
   实测让 `计划任务持久化` 丢了原本命中的中文文档）。
3. **覆盖度 rerank**：按"命中查询概念数 ×3、封顶 +12"重排**同一个候选集**
   （不是新召回），把"命中 powershell/encoded/base64/rule 四个概念"的对症文档
   提到只命中一个元数据词的噪声之前。

同日把“样本量”本身纳入回归：`eval-knowledge-retrieval.mjs` 默认要求正样例 ≥50、

**性能回归的定位与修复（`knowledge-hub 0.3.1`）**：上面三件改动把平均耗时从 ~230ms
推到 ~375ms。用 `node --cpu-prof` 跑一遍评测：**`status()` 占了 749 个采样**（远超
`search` 的 195），也就是大头根本不在检索。根因是 `ensureKnowledgeIndex()` **每次检索
都会调一次 `status()`**，而它每次都 `SELECT COUNT(*)` 整表（8.4 万 chunk，实测 ~140ms）。
计数只在重建/失效时变，改成进程内缓存（`invalidate()` 清空、`status({ counts: true })`
强制刷新）后：平均耗时 **375ms → 34.9ms**（比改动前的 230ms 还快 6.6 倍），
Top-1/Top-5/MRR/低置信/负样例指标**一字未变**。
教训：**诊断型调用（计数、状态汇总）不能放在每次检索的热路径上**；性能回归要用 profiler
定位，不要凭直觉去优化检索本身。

**同类问题：装配路径上的全量遍历（`knowledge-hub 0.3.2`）**：知识库那行 manifest 走的是
`systemPrompt.context`，**每个回合都会装配一次**；旧实现每次重算 `stats()`
（`countByExt` 全量遍历），实测冷启动 348ms、热 ~33ms。用真宿主验证调用次数：
在**已安装副本**里插一行计数器，跑 2 轮会话 → **回调被调用 3 次**（94 个工具在场）。
改成缓存（5 分钟 TTL + 导入/同步/索引重建时 `invalidateKnowledgeIndex()` 显式失效，
用 `at>0` 而不是 `text!==''` 当"算过"判据，空库也缓存）后装配期这次遍历归零。

**这一轮踩的坑本身也值得记**：第一次插计数器时我用 PowerShell 双引号串里写了 `` `n ``，
把字面量换行写进了 JS 字符串 → 已装插件**语法错误、整块消失**，而 30 轮工具面审计
**照样全绿**（它只断言"工具面跨轮稳定"，不检查工具是否在场）。于是顺手给审计加了
"关键工具必须在场"的断言（`knowledge_search/stage_gate/operation_goal/
campaign_memory_write/redteam_finding_register/tool_pack`），并用假工具名反向验证过它会亮红。
教训：**"稳定"不等于"在场"**——只断言不变量的守护脚本，会在被测对象整体消失时静默通过。

## 九、统一出站策略（2026-09-18 追加）

**对标先行**：读了 `openai/codex` 的 network policy 实现
（`codex-rs/core/src/config/network_config.rs`、
`codex-rs/core/src/network_policy_decision.rs`、
`codex-rs/exec-server/src/client/network_policy_audit.rs`，以及 protocol 里的
`NetworkRequirements` / `NetworkDomainPermission` / `NetworkPolicyRuleAction`）。
借它三件事：**权限映射语义**（`{ domain: "allow" | "deny" }`）、
**"只认托管白名单"的冻结档**、**每次判定带 reason 的审计**
（`not_allowed` / `not_allowed_local`）。**不借**它的 OS 级沙箱：
Saker 明确不做隔离执行面，做的是"同一宿主内、跨插件的出站总闸 + 留痕"。

**为什么需要**：原先只有模型代理这一条出站做了脱敏与审计；知识包 git 同步、
MCP 包下载这些**基础设施出站**各管一段，护网场景下没有单一闸门。

**做法**：

- 契约是**一份文件**：`$DSH_HOME/saker-egress/policy.json`
  （`version / mode / allowHosts / updatedAt`），审计是
  `$DSH_HOME/saker-egress/audit.jsonl`（超 256KB 轮转成 `.1`）。
- 实现住在根包 `dsh-saker/lib/egress.js`（`dsh-saker/egress` 导出），
  不复制到各插件：`readPolicy / writePolicy / evaluateEgress / describeSource /
  checkEgress / readAudit`。
- 三档：`allow`（默认，判定原因写 `allow-all`，与"没配策略"区分）/
  `allowlist`（域名按标签后缀，`github.com` 命中 `api.github.com`；
  IP 只精确匹配）/ `frozen`。
- **不管目标流量**：`kind: "target"` 一律放行并记 `target-traffic`；
  回环地址（本机代理/服务）记 `loopback` 放行。避免"开了 OPSEC 就干不了活"。
- 三个消费者：`sec-config` 模型代理（转发前判定，冻结档 `403 EgressBlocked`，
  HTTP 层实测上游**一次都没收到请求**）、`knowledge-hub`（冻结档 `syncPack`
  返回 `mode: "blocked"`，git **一次都没跑**）、`mcp-studio`（包运行器
  npx/npm/pnpm/bunx/yarn/uvx/pipx 在 spawn 前拦，非包运行器不受影响）。
- 用户面：设置 → 安全配置 → 「统一出站策略」区块（切档位 / 白名单 / 最近判定），
  端点 `egress/get` / `egress/set`。
- **真实浏览器验收**（独立 Chrome for Testing，2026-09-18）：打开隔离宿主的
  设置 → 安全配置，「统一出站策略」区块正常渲染（`data-slot-error=0`）；
  点「冻结基础设施出站」后界面显示 `当前档位：frozen · 策略文件来源：file`，
  磁盘上 `$DSH_HOME/saker-egress/policy.json` 同步写成 `mode: frozen`；
  再点「不拦（默认）」回滚成功（文件回到 `allow`）。证据截图
  `_ref/shots/egress-policy-panel-20260918.png`；验完已删除测试 home 的策略文件、
  关掉浏览器与宿主。

**测试与假绿防线**：

## 十、子代理结果回收（2026-09-18 追加）

**问题（先看真实状态）**：`scanner`/`semgrep` 这类长工具走 `runTrackedTask`
自动收口，但 `subagent` 家族不在其中——模型漏调 `operation_task` 时，台账里那条
queued 任务会一直挂着；主代理看不到"这个方向已经跑完/失败了"，容易重复派单。

**做法**（`stage-gate 1.6.2`）：按宿主生命周期回收，不改写工具结果

- `subagent/start` → 唯一匹配的 queued 任务转 `running`（同时挡住被别的 Agent 认领）。
- `subagent/end` → `completed`→`succeeded`（写入子代理**自己的**最终输出）、
  `error`→`failed`、`aborted`→`interrupted`（可 retry）。
- 绑定沿用既有保守规则：同 owner 别名 + 同 session，候选唯一才动；多候选不动。
- 真宿主探针 `_ref/tools/probe-subagent-recycle.mjs` 已接入 release gate：
  真跑一次 `subagent`（mock 子代理），断言被认领的任务收口、摘要里是子代理输出
  而不是 `started subagent …`，且同台账里 `owner=bash` 的对照任务保持 queued。

**2026-09-18 flake 修复**：release gate 曾偶发 19/20——探针全局 mock sequence 被
标题生成等无 tools 辅助请求提前消费，主请求拿不到 `tool_call_success`，任务保持 queued。
探针改为按请求是否带 tools 分发：第一个主请求返回 subagent 工具调用，其余成功；
连续 10/10 通过，release gate 恢复 20/20。

**三个真宿主实测约束（这轮踩出来的）**：

1. `subagent/start|end` 是**作用域事件**：发射器用 parent 当 scoped dispatch 的
   carrier，但回调只传 `info`（`packages/subagent/subagent/src/lifecycle.ts`
   里是 `callback(info)`）。所以 `ctx.on("subagent/start", (info, parent) => …)` 的
   parent 永远是 `undefined`（实测 `session=` 空、`ws=(none)`）。正确做法是挂
   `agent/created` → `agent.ctx.on(...)` 把 agent 闭包进作用域监听，
   `agent/disposed` 时释放。
2. **不能用 `tools/result` 收口**：原生 `subagent` 是异步派发，工具结果只有
   `started subagent <id>`。按它收口会把任务在派发瞬间标 succeeded——假成功，
   而且正好是我们最不该犯的那类错（发现≠完成）。
3. 事件里的 `provider` 是 provider id（原生工具是 `spawn`），不是工具名；
   别名表补了通用 `subagent`，模型写 `owner: subagent` 也能命中。

**结果冲突只记不覆盖（`stage-gate 1.6.3`）**：多 Agent 场景下最容易出的错不是漏记，
而是**把矛盾抹平**——模型先宣布成功、子代理随后报失败，若后者直接覆盖或静默丢弃，
台账就留下一个假的 succeeded。现在的语义：

- 终态任务再收到**不同**结果 → 写 `task.conflicts[]`（最多留最近 5 条，含 from/to/明细），
  **终态不变**；同结果重复上报按幂等处理（连 `updatedAt` 都不动）。
- `subagent/start` 记 `runId → taskId`，`subagent/end` 按 runId 精确回收：
  并发同 provider 的子代理也能对上号；宿主重启后退回保守匹配（唯一才动）。
- 冲突进项目工作台 attention（`任务结果冲突`），让人复核，而不是让系统替人下结论。
- 真宿主探针补了一条反向断言：顺利路径**不得**产生冲突记录（冲突只在结论矛盾时出现）。

## 十二、长期记忆闭环与效果度量（2026-09-18 追加）

**问题（先看真实状态）**：真实 `~/.dsh/campaign-memory/memory.db` 只有 10 行冒烟数据、
`usage_count` 全为 0；`E:\工作` 下没有任何 `memory-candidates.md`。
也就是说"收尾蒸馏只出候选、不自动写库"这条设计在真实会话里没有闭环出口——
候选落盘后没人确认，记忆库长期为空，召回块自然也不出现。

**做法（只加一个出口，不加新功能）**：

- `campaign-memory 1.1.12`：装配期检测本工作区 `memory-candidates.md`，
  有候选就在召回块里补一行可操作提示（含条数与文件路径）。
- 该行只在候选文件存在时出现；没有记忆也没有候选时整块返回空串，
  不占上下文（这条不变量有单测锁：`buildMemoryBlock(mode, ws, [], 0) === ""`）。
- 整块 284 字符；真宿主实测：有候选的会话上下文 42366B，干净工作区 41848B，
  差异即这一行（≈518B，含转义）。

**效果度量**：新增 `scripts/report-memory-effect.mjs`（只读）输出
写入 / 当前召回窗口 / 被读取 / 反馈分桶，以及按项目汇总的准则、意图、任务状态，
再按「有被读取过的记忆 vs 没有」分组给项目推进度关联；样本不足时只报样本不足。
`scripts/test-memory-effect.mjs` 14 条断言，其中三条是反向验证：
门槛调高必须变成「样本不足」、跑完 `usage_count`/`feedback_score` 不得改变、
无关工作区必须匹配到 0 条记忆。

**真宿主探针**（`_ref/tools/probe-memory-candidates-inject.mjs`，已接入 release gate）：
两侧都验——有候选的工作区主回合请求里出现提示行，干净工作区完全不出现召回块。

**两个工程教训（本轮真踩）**：

1. `settings.yaml` 里 `agent-default-model.reasoningEffort` **不能带尾逗号**：
   `high,` 会被当成档位 `"high,"`，宿主直接报 `does not support reasoning effort "high,"`，
   表现为「宿主起来了、`session/prompt` 返回 200、但 mock 一条请求都没收到」——
   四个宿主类门禁同时超时。改档位用 `_ref/tools/set-test-reasoning.mjs`（已修）。
2. 真宿主探针按请求**下标**取样会取到**辅助调用**（会话标题生成也走同一 `/v1`，
   但没有 `tools`），于是「干净工作区不注入」的负样例假绿。
   正确做法是按请求里的工作区路径认领，并断言该请求带 `tools`。

## 十三、可观测性：指标历史与趋势（2026-09-18 追加）

**问题**：单点数字只能回答"现在多大"，回答不了"是不是在慢慢变胖"。护网最关心的
工具面、请求体、任务成功率需要**随时间的序列**；原有 `report-observability.mjs` /
`report-memory-effect.mjs` / `project-status.mjs` 都是"当前快照"。

**做法**：

- `scripts/metrics-history.mjs`：`$DSH_HOME/saker-metrics/history.jsonl`，
  上限 200 行（丢最旧），同盘临时文件 + rename 写入；`readMetrics` 坏行直接跳过。
- `scripts/record-metrics.mjs`：只读**已有产物**记一行——30 轮审计的工具面/请求体、
  大结果裁剪审计、各库只读统计（记忆/成果/轨迹；`(intervention)` 是**真人消息**不是工具调用，
  统计调用数时排除）。
- `scripts/report-metrics-trend.mjs`：最近 N 条 + 相对上一条的增减；**报告不是门禁**，
  不设通过线，硬门禁仍在 release gate。

**一条数据诚实性红线**：**没测到的量写 `null`，不写 `0`**。0 会被趋势读成"降到零"，
这是最容易骗到自己的一类数据事故；测试里锁死了"没有审计产物/没有库 → null"。

**2026-09-18 补标准评测两项**（`trace-vault 0.3.7`）：`sessionMetrics()` 从真实
trace 行算首次有效动作时间（会话最早一行到第一次 `outcome=ok`）和工具失败率
（blocked/error/interrupted，排除 `(intervention)`）。`report-observability.mjs`
同步输出 `firstAction` / `toolFailure`。真实库当前 7 次调用：`firstAction=7000ms`、
`toolFailure=0%`、`success=100%`；样本少，只记录事实，不做能力结论。

**验收**：单测 12 条（有界追加、坏行容错、趋势增减、null 语义、端到端记录）；
release gate 末尾新增两步（指标入历史 / 指标趋势快照），当前 **19/19**；
真实 home 首次记录：工具面 `94 个 / 83920B`、请求峰值 `144461B`、记忆 `10/0`、
成果 `9`、轨迹 `7(0 err)`。

## 十四、报告交付契约

**从结构化成果生成报告草稿（2026-09-18 追加）**：报告六字段在台账里本来就是结构化的
（`redteam-results.findings` 有 description/severity/target/poc/baseline/diff_evidence/
marker_echo/verify_note/second_rating…），让模型再从零手写一遍只会带来两种退化：
字段漏项、等级与台账不一致。现在：

- 根包 `lib/report-drafts.mjs`（`dsh-saker/report-drafts`）：纯渲染 finding → 六字段草稿；
- `scripts/generate-report-drafts.mjs`：会话 id 取自工作区台账的 `sessionId`（或 `--session`），
  读成果库写 `reports/NN-<标题>.md`，**不覆盖已有报告**、误报默认跳过、`--dry` 只出计划。
- **红线**：待补文案里不出现门禁要检查的关键词，而且**证据不足的草稿必须仍然过不了
  P2 结构门禁**。第一版就踩了：待补提示里写了「基线 / 差分 / marker / 复核」这几个词，
  结果 sparse 草稿照样通过 P2——占位文案把门禁骗过去了。测试现在把这条钉死
  （`scripts/test-report-drafts.mjs`：齐全的过、缺的不过、重复跑不覆盖、`--dry` 不写盘）。
- 校验器另加**非阻断一致性告警**（`redteam-report-schema.mjs`）：`verified` 缺
  `verifyNote`/`secondRating`、`fixed` 缺 `retestNote`、`confirmed` 缺 `evidence`、
  `baseline === diffEvidence` 都输出 warning，但报告仍 `ok=true`，由复核员决定语义。

`redteam-results 1.0.13` 起，导出菜单的“结构化报告（JSON）”产出
`schema=saker.redteam.report.v1`、`schemaVersion=1` 的稳定文件。
配套新增：

- `scripts/redteam-report-schema.mjs`：schema 定义、legacy 迁移、校验实现；
- `scripts/validate-redteam-report.mjs`：命令行校验入口；
- `scripts/test-report-schema.mjs`：4 条断言（当前版本、无 schema 的 legacy 迁移、
  未知 schema 拒绝、畸形 findings 拒绝）。

迁移口径写清楚：没有 `schema`/`schemaVersion` 的旧导出按 v1 迁移并标记
`migrated=true`；未知 schema 直接拒绝，不猜字段。真实浏览器导出的文件已过校验
（见第四节）。

## 十五、模型外发字段级分类（2026-09-18 追加）

**对标**：读 Microsoft Presidio 的 `AnalyzerEngine`、`OperatorConfig`、
`AnonymizerEngine` 源码，借“识别实体 → 按实体类型执行 operator”的分离；
不引入 spaCy/Presidio 这类重依赖，Saker 需要的是确定性的凭据字段分类。

**落点**（`dsh-sec-config 1.3.17`）：模型代理的 `redactBody` 先按字段名分类，再做文本内容识别。
结构化 `password` / `access_token` / `client_secret` / `Authorization` 以及
`{ name: "Authorization", value: "..." }` 形式都不再因为“值不像 token”漏掉。
敏感对象保持对象结构，只替换叶子值；默认放行目标 IP、域名、URL 和普通验证载荷。

**顺手修掉的两个真实坑**：

1. `Authorization: Basic dXNlcjpwYXNz` 旧正则只替换 `Basic`，base64 仍会外发；现在整段替换。
2. 字符串形态的 JSON 工具参数如果被正则吃掉引号，脱敏后会变成非法 JSON；现在只在引号内替换，
   测试用 `JSON.parse` 锁住。

**验证**：`dsh-sec-config` 136/136；真实代理 HTTP 链路把结构化 password /
Authorization 脱敏后送上游，同时保留目标 URL；全量回归 36 套 1983 ok / 0 fail / 17 skip。
已装形态另加 7 条探针（`_ref/tools/verify-redaction-installed.mjs`），直接从真实
profile 加载已装模块验证字段级脱敏、Basic 整段替换、工具 schema 不变、off 模式与
JSON 参数可解析；release gate 因此从 19 项变为 **20/20**。
