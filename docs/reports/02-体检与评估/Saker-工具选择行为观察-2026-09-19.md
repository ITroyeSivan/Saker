# Saker 工具选择行为观察：内置扫描器 vs 直接跑 CLI（2026-09-19）

## 为什么要看这个

用户提过一句很具体的验收要求：

> Burp 和 Yakit 都打开了，后面记得安排测试。不仅要测试**是否可用**，
> 也要测试**实际使用中模型是否会主动用，效果怎么样**。

上午已经验过「可用」（`katana_crawl` / `dirsearch_dirs` 真调用成功，
见《Saker-扫描器真实调用验证-2026-09-19》）。本轮用下午那次端到端回归
（`session-66517d28…`，81 次工具调用）回答后半句：**模型会不会主动用**。

## 事实：模型确实没怎么用内置扫描器

把那一轮 81 次工具调用按名字拆开：

```
pwsh=17  write=16  edit=3  stage_gate=3  read=2  skill=1  subagent=1
redteam_finding_register=5  redteam_finding_update=4  redteam_coverage_mark=18
wafw00f_detect=1  redteam_atlas_target=1  redteam_coverage_sync=1
redteam_coverage_list=1  redteam_chain_reconcile=1  campaign_memory_write=2
gates_list=1  list_agents=1  grep=1  operation_conclude=1
```

扫描类工具只出现了 **1 次**（`wafw00f_detect`）。

但本机扫描器是装齐的（实测 `Get-Command`）：

```
httpx / katana / dirsearch / ffuf / nuclei / afrog / wafw00f / subfinder   → 已装
```

而且模型**知道**它们装了 —— 第 7 步它自己跑了一遍工具平面检测：

```powershell
$tools=@("ffuf","dirsearch","nuclei","httpx","nmap","sqlmap","katana","wafw00f","whatweb","hydra")
foreach($t in $tools){ $c=Get-Command $t -ErrorAction SilentlyContinue; ... }
```

然后第 11 步直接调 CLI：

```powershell
& ffuf -u "http://127.0.0.1:18081/FUZZ" -w $wl -mc all -fc 404 -t 12 -rate 40 -s
```

输出手动落盘到 `artifacts/ffuf-root.txt`。

## 这不是 bug，是 playbook 写明的策略

`preset/pentest/skills/pentest-playbook/SKILL.md` 的「通道完整阶梯」第 1 级写的是：

> **已有直接用**——CLI 列 / MCP 列（已挂）检测到即用，**本机 bash 内置优先**；
> 目标工具缺装但已装同能力替代时先顶替……（scanner-tools 十工具的描述内已带
> 各自六节点阶梯：本机 → MCP → 已装替代 → MCP 备选 → 询问安装 → 不批准走脚本编写）

也就是说：**scanner-tools 被定位成「CLI 缺失时的封装/降级层」，而不是首选通道。**
模型的行为完全符合这条策略，不是没听话。

## 先纠正一个我自己差点写错的判断

看到这一轮只有 1 次扫描器工具调用，第一反应是"shell 里跑的扫描器不可观测"。
**这个判断是错的**，对账后推翻：

```
trace-vault（隔离 home）里该会话共 82 条轨迹，逐条覆盖全部工具调用：
  pwsh=17  write=16  redteam_coverage_mark=18  redteam_finding_register=5
  redteam_finding_update=4  stage_gate=3  read=2  edit=3  subagent=1
  wafw00f_detect=1  ... （含 `& ffuf ...` 那条，dur=120045ms）
```

**shell 里跑的扫描器一样进轨迹库。** 之前 `report-observability` 打出 `calls=7`
是因为它默认读的是**真 home**（那里确实只有 7 条），而本轮会话在**隔离 home**
（1825 条）。两个 home 看混了，就会得出"观测有盲区"的错误结论。

真正的问题不在这里，而在**分类口径**：同一批轨迹里 `blocked` 被误判（加载手册、
读源码、grep 日志都算"被拦"），并且被折进 `toolFailureRate`。
那是一个独立的缺陷，已单独修掉并出报告 —— 见
《Saker-出局分类与成功率基线修正-2026-09-19》。

## 那还剩什么值得决策

审计与观测已经证明**覆盖得到**。剩下的差异只有两项，且都是"内置工具做了额外约束"：

| 能力 | 内置工具 | 直接跑 CLI |
|---|---|---|
| 目标登记强制 | 未登记目标会拒绝并给修复提示 | 无 |
| 限速/并发预算 | 描述内带速率阶梯 | 靠模型自己写 `-rate 40`（本轮写了） |
| 审计与证据落盘 | 全文自动进 `artifacts/tool-output/` | 靠模型手动 `>`（本轮也做了） |
| 轨迹可观测 | 有 | **也有**（已核实） |

也就是说：直接跑 CLI 的代价比一开始想的小得多 —— 真正的差异是
「目标登记强制」和「限速阶梯由工具保证而不是靠模型自觉」。

## 建议（本轮未改，留决策）

1. **改 playbook 排序**：把「扫描器类（ffuf/dirsearch/nuclei/httpx…）优先走内置工具」
   写进阶梯第 1 级，curl 这类一次性探测仍走 CLI。
   代价：改一行提示词；收益：目标登记强制与限速阶梯覆盖到扫描主力。
2. **不改**：接受"模型自己写 `-rate`、自己落盘"，只在报告里说明口径。
   代价：目标登记这道闸对 CLI 路径不生效；收益：零风险、零 token 增长。

**本轮选择不动策略** —— 这是设计取舍不是缺陷，而且改动直接影响模型行为与
token 成本，不适合在没有明确结论前单方面改。
