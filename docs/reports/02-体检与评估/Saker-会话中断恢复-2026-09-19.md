# Saker 会话中断恢复验证（2026-09-19）

## 为什么补这一条

已有恢复测试覆盖了两层，但都没有覆盖「长会话被打断」这件事本身：

- **任务级**：宿主重启后，过期 `running` 任务恢复成 `interrupted`（连续 5/5）。
- **轮次级**：真实宿主跑 30 / 100 / 300 轮 mock 会话，验证工具面恒定、消息增长有界。

缺的是**会话级**：宿主在某一轮**正在流式输出到一半**时被强杀，重启后这个会话还能不能打开、
历史还在不在、还能不能接着用。护网是长会话，宿主中途崩一次或用户手动重启一次很常见；
这条路径一旦坏掉，现场看到的是「会话打不开 / 历史乱掉」，整场战役的上下文就没了。

## 做法

工具：`_ref/tools/run-session-interrupt-recovery-audit.mjs`（可复用，已进清理白名单）。

用真实宿主 + dsh 自带的脚本化 mock LLM，不依赖外部模型、不消耗线上额度：

1. 起宿主（隔离 home，端口 3091），建 `pentest` 会话，第 1 轮跑完并确认已落盘。
2. 再发一轮 => `taskkill /t /f` 直接打死宿主进程树。
   **"正在流式"是判定的，不是 sleep 猜的**：mock 的每条请求记录带
   `chunksSent` / `outcome`，只有当某条记录 `chunksSent > 0 && outcome === undefined`
   （已经开始吐 chunk、且还没结束）时才动手。
3. 用**同一个 DSH_HOME、同一个端口**重启宿主。
4. 断言：会话日志逐行可解析（零坏行）、崩溃前已收口的轮次一条不少、原文还在、
   会话还能再收一条新消息并正常收口。

> 踩坑记录：mock 的 `success` 行为是 `delay = 0`，瞬间写完，**根本没有流式窗口**——
> 第一版用它做"慢速输入"，结果杀进程时那一轮早已写完，测的其实是"杀在轮次之间"。
> 只有 `slow_success` 才按 `chunkSize` / `chunkDelayMs` 逐块吐。换成它之后
> 才真正切在 `chunksSent=2/42` 的位置。

## 结果（连续 3 次，3/3 通过）

| 断言 | 结果 |
|---|---|
| 第 1 轮正常完成并落盘 | 26 行 / 50880B |
| 确认宿主正在流式输出 | `chunksSent = 2/42`（真的切在流中间） |
| 宿主已被强杀（含子进程） | 是 |
| 重启后会话日志仍可逐行解析 | 28 行，**坏行 0** |
| 崩溃前已收口的轮次一条不少 | kill 前 1 → 重启后 1 |
| 崩溃前回复原文还在会话里 | 是 |
| 重启后会话仍可接收新消息 | HTTP 200 |
| 重启后的新轮次正常收口 | completed 1 → 2 |
| 全程日志无损坏行 | 47 行，坏行 0 |

三次运行的最终 `badLines` 都是 `0`，`completed` 都从 1 正常涨到 2。

## 关键发现：流式内容是「收满才写」

被打断时 mock 已经吐了 2 个 chunk，但重启后的会话日志里**没有任何半条 assistant 消息**——
`partialAssistantPersisted = false`。

也就是宿主不是逐块追加落盘的，而是**一条消息收全了才写**。这是对的设计：

- 半条流式消息不会进历史，所以不会出现「历史里挂着一段没头没尾的回复」；
- 被打断那一轮直接消失，会话回到一个干净的、可继续的状态。

结论：**会话级中断恢复通过**。长会话被打断一次不会污染历史，也不会让会话不可用。
