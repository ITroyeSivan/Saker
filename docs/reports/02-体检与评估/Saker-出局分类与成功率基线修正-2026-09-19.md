# Saker 出局分类与成功率基线修正（2026-09-19）

## 怎么发现的

复盘下午那次端到端回归时，把会话的工具调用拿去和 `trace-vault` 对账，
发现一个说不通的地方：

```
session-66517d28…  pwsh=17 次，其中 10 次 outcome = blocked，但 is_error = 0
```

那 10 条命令全是**只读侦察**：抓首页、读 JS、批量探路径、跑复现脚本、
`Test-Path` 查文件。它们明明都跑成功了，为什么算"被拦"？

翻 `plugins/dsh-trace-vault/lib/store.js`：

```js
const BLOCKED_RE = /\b(403|forbidden|waf|blocked|rate.?limit|429|too many requests|captcha|denied)\b/i;
export function classifyOutcome(isError, text) {
	if (isError === true) return "error";
	return BLOCKED_RE.test(String(text ?? "")) ? "blocked" : "ok";
}
```

**它对整条结果文本跑正则。** 于是凡是输出里出现过这几个词的调用都被记成 blocked。

把那 10 条 blocked 的结果文本逐条查命中词：

| 工具 | 结果里命中的词 | 真实情况 |
|---|---|---|
| `skill` | 403 / blocked / rate-limit / waf | **加载渗透手册**，手册正文里当然有这些词 |
| `read` | 403 / forbidden | **读靶标源码**，源码里有 403 分支 |
| `grep` | 403 / forbidden | **搜日志**，命中行里带 403 |
| `wafw00f_detect` | waf | 扫描器 exit 0，输出里含 "wafw00f" |
| 6× `pwsh` | 403 / forbidden | 探测目标时**观察**到 403（那是情报） |

**10 条里没有一条是"目标把我们拦了"。**

## 两个后果

### 1. 出局分类本身错了（本地工具不该看文本）

加载手册、读源码、grep 日志 —— 这些工具**根本不和目标说话**，
它们的输出文本不可能证明"目标拦了我们"。

### 2. `toolFailureRate` 把情报算成了故障

```js
toolFailureRate = (blocked + error + interrupted) / calls
```

护网里"目标回 403"是**换路径的信号**（插件注释自己也这么写），不是工具坏了。
把它折进失败率，等于让"扫到一个 403"看起来像"工具不可用"。
用户点名的「工具面和任务成功率基线」就建立在这个数上。

实测这个会话：`toolFailureRate = 17.1%`，而真实 `errorRate` 只有 `4.9%`。

## 修复（dsh-trace-vault 0.3.8）

1. **分类按工具分流**：新增 `isLocalTool()`，本地工具（`skill/read/write/edit/grep/glob/
   list/subagent/tool_pack` + `redteam_*/campaign_memory_*/knowledge_*/operation_*/stage_*/todo*/gate*`
   前缀）**不做文本判定**，只按 `isError` 判 ok/error。
   面向目标的工具（httpx/nuclei/ffuf/pwsh…）保持原文本判定不变。
2. **指标拆开**：
   - `toolFailureRate = (error + interrupted) / calls` —— 工具真的失败了；
   - 新增 `blockedRate = blocked / calls` —— 目标拦了我们（情报）。
   `report-observability` / `record-metrics` / `metrics-history` 同步带上 `blockedRate`，
   控制台一行里两个数分开打，不再混成一个"失败率"。

回归新增 5 条：本地工具不因正文含 403 被记 blocked、台账类只按 isError 判、
面向目标的工具仍按文本判、失败率只看 error/interrupted、只有 blocked 的会话
失败率 0 而 blockedRate 100。

### 历史数据回填

`_ref/tools/reclassify-local-blocked.mjs`（默认 dry run）：
只把 **本地工具 && outcome=blocked && is_error=0** 的行改回 ok，
面向目标的工具一行不动。

隔离测试 home 实测：

```
库里 blocked 共 113 条；其中本地工具误判 32 条
  knowledge_read × 8   read × 7   grep × 4   skill × 3   knowledge_search × 3
  knowledge_list × 2   redteam_finding_update × 2   subagent × 1   glob × 1
  redteam_finding_register × 1
已回填 32 条 blocked → ok
```

真 home 的 `blocked` 是 0 条，无需回填。

## 修正前后（同一份数据）

```
修正前： calls=782 ok=642 blocked=113 error=15 interrupted=12 success=82.1%
        （旧口径 toolFailure = (113+15+12)/782 = 17.9%）
修正后： calls=782 ok=674 blocked=81  error=15 interrupted=12 success=86.2%
        toolFailure = (15+12)/782 = 3.5%　targetBlocked = 81/782 = 10.4%
```

成功率 +4.1 个百分点；失败率从 17.9% 落到 3.5% —— **这 14.4 个百分点里，
大部分是"目标回 403"被当成了"工具坏了"**。

## 结论

- 出局分类的误判面从"任何提到 403 的输出"收窄到"面向目标的工具的响应"。
- 工具失败率与目标拦截率分开后，护网基线才有意义：
  前者衡量**我们的工具**，后者衡量**对手的防御**。
- 未改动任何面向目标工具的分类行为，扫描器的"换路径信号"语义保持不变。
