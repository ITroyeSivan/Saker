# Saker 全面评估：竞品差距、性能代价与护网可用性

> 评估日期：2026-09-17
> 评估对象：Saker `0.3.3`，dsh 适配基线 `0.1.6-alpha.1`，上游 master `0d1f500`
> 方法：项目源码、现有真实抓包、真实宿主回归、GitHub 官方 README 与仓库元数据

## 1. 结论摘要

Saker 已经不是“玩具型 AI 渗透助手”。它在**领域知识、攻防流程、证据纪律、成果登记、工具治理、
中文交互和 MCP 工具压缩**上明显强于多数同类开源项目；但在**运行时隔离、可观测性、标准基准评测、
上下文压缩和 OPSEC**上落后于 PentAGI、AIRecon、BreachWeave、StrikeAgent 等成熟方向。
本项目当前只面向单人测试，因此多真人用户协作、RBAC 和团队分派不作为改进目标。

当前最准确的定位是：

> **一套治理和证据能力较强的单机安全 Agent 工作台，适合授权测试、CTF、代码审计和单操作员护网辅助；
> 还不是可独立承担高风险实战的隔离式红队平台。**

护网场景下可直接使用，但应限定在侦察、分析、验证、证据整理、报告辅助和人工确认后的低风险操作。
涉及真实攻击载荷、不可信样本、内网横向和高权限利用时，当前默认缺少可靠隔离，不应把 Saker 直接
当作 Kali/Docker 红队执行平台。

## 2. 当前项目基线

### 2.1 规模

| 项 | 当前值 |
|---|---:|
| 专业预设 | 3 个：`pentest` / `code-audit` / `ctf-solver` |
| 插件 | 23 个 |
| 模型工具定义 | 源码中 58 个 `defineTool` 调用点 |
| `systemPrompt.context` 注册 | 8 处 |
| 常驻计时器/轮询 | 9 处 `setInterval` |
| SQLite 数据层 | 7 处 `DatabaseSync` 使用 |
| 全量回归 | 25 套，1659 ok / 0 fail / 17 skip |
| 真实/隔离装机同步 | 152 个文件字节一致，deps/bundles 对齐 |

### 2.2 已知提示词与工具面成本

最近一次真实请求抓包结果仍然是评估上下文成本的最佳基线；之后的知识同步、协议容错和配置工具
没有改变工具 schema 主体：

| 模式 | 首轮请求 | 工具定义 | 估算输入 token |
|---|---:|---:|---:|
| 渗透测试 | 128.0K | 83.7K | 约 29.1K |
| 代码审计 | 103.4K | 60.8K | 约 23.6K |
| CTF 解题 | 120.1K | 78.8K | 约 27.4K |

工具的 65% 左右是自然语言描述。32K 窗口可以启动首轮，但继续多轮后余量很小。

### 2.3 知识库

- 20 个自动同步知识包。
- SQLite FTS5 + BM25 + 中文 bigram，本地查询通常为毫秒级。
- 真实 home 当前包含数千至近万份文本资料、数万到十万级 chunks。
- 已加入 shallow clone 分叉自愈、Windows 长路径、旧目录备份和单包重试。
- 仍缺少语义检索基准、reranker、增量索引质量和跨语言问题的量测。

## 3. 与专业项目的对标

### 3.1 对标对象

本节只采用官方仓库公开资料：

| 项目 | 公开定位 | 参考价值 |
|---|---|---|
| [PentAGI](https://github.com/vxcontrol/pentagi) | 全自主多 Agent 渗透测试系统 | Docker 隔离、任务队列、持久化、可观测性、知识图谱 |
| [AIRecon](https://github.com/pikpikcu/airecon) | Kali Docker + 本地模型的自主侦察 Agent | 本地模型、上下文压缩、记忆、Caido、1.09M 本地知识集 |
| [BreachWeave](https://github.com/m-sec-org/BreachWeave) | Manager / Solver / Observer 多角色架构 | 并行 Solver、旁路 Observer、上下文压缩与降噪 |
| [StrikeAgent AtkBrain](https://github.com/Yean-Sec/StrikeAgent_AtkBrain-Flash) | 红队打点、SRC、CTF 平台 | Kali 部署、Web 控制台、资产画像、HTML/PDF 报告 |
| [Argus Benchmarks](https://github.com/pensar-x/argus-validation-benchmarks) | AI 渗透 Agent 的 Docker 靶场基准 | 71 个渗透 + 10 个威胁模型基准 |
| [HexStrike AI](https://github.com/0x4m4/hexstrike-ai) | 150+ 安全工具的 MCP Agent 平台 | 工具体量、MCP 接入和自动化广度 |
| [PyRIT](https://github.com/microsoft/PyRIT) | 生成式 AI 风险识别 | 评测、实验组织和专业安全工程方法 |

CAI 原框架已经归档，当前公开仓库主要指向商业化 CSI；因此只把它作为历史评测与基准研究参考，
不作为可继续直接对比的活跃产品线。

### 3.2 关键差距

| 能力 | Saker | 专业项目常见做法 | 差距判断 |
|---|---|---|---|
| 执行隔离 | 主要在当前主机/当前 Node 进程执行 | PentAGI、AIRecon 使用 Docker 沙箱；StrikeAgent 明确 Kali/Docker 验证环境 | 最大短板 |
| 多 Agent 编排 | 主要是单 Agent + 专用子代理；CTF 有 Observer | BreachWeave 有 Manager/Solver/Observer；PentAGI 有任务队列和专业 Agent | 明显落后 |
| 长期记忆 | 多个 SQLite 插件各自存状态 | PentAGI 使用 PostgreSQL + pgvector + Graphiti；AIRecon 有跨目标记忆与 verified-only 学习 | 落后 |
| 可观测性 | Web UI + Trace Vault，无统一指标/追踪 | Grafana/Prometheus/Langfuse/OTel 常见 | 落后 |
| 标准评测 | 单测、真实宿主回归、临时提示词抓包 | CAIBench、Cybench、Argus 71+10 Docker 靶场 | 最大可信度短板 |
| 本地模型/OPSEC | 默认云模型；知识同步会访问外网 | AIRecon 可完全本地；PentAGI 支持 Ollama、Bedrock 等 | 落后 |
| 人类多操作员协作 | 单机单用户为主，无 RBAC、共享任务队列 | StrikeAgent/PentAGI 更接近服务端操作平台 | **当前明确不做** |
| 上下文压缩 | route-boost、method-stack、历史快照；无通用压缩器 | BreachWeave/AIRecon/PentAGI 都把上下文压缩和摘要作为核心机制 | 落后 |
| 工具广度 | 58 个插件工具 + MCP proxy | HexStrike 150+ 工具；PentAGI 20+ 深度工具 | 数量落后，治理领先 |
| 证据与门禁 | scope、constraint、stage gate、finding、trace vault | 很多项目只做自动化，证据链不如 Saker 系统 | Saker 优势 |
| 中文知识与流程 | 大量中文方法、报告模板、应急/AD/CTF pack | 多数项目偏英文和工具自动化 | Saker 优势 |
| MCP 工具压缩 | auto/proxy/hybrid，按需暴露 | 同类多数全量直连或仅 MCP 透传 | Saker 优势 |
| 报告交付 | Markdown + HTML，可打印 PDF | StrikeAgent 有成品 HTML/PDF 报告和资产画像 | 稍落后 |

### 3.3 对标结论

**Saker 应该继续做“治理层”，不要把项目重心转向再造 PentAGI。**

专业项目最值得借鉴的不是更多工具，而是四件基础设施：

1. 隔离执行面。
2. 可恢复的任务编排。
3. 可观测和可量化的评测。
4. 能压缩长战役上下文的记忆/摘要层。

Saker 已有自己的差异化资产：目标授权、操作门禁、证据登记、覆盖率、成果页、中文知识和报告约束。
这些资产应与上述基础设施组合，而不是被大量插件和 UI 面板淹没。

## 4. 当前存在的性能与效率问题

### 4.1 已做但是代价变高的设计

#### 工具面收窄只省 token，不卸载插件

`dsh-tool-scope` 使用宿主 `tools.restrict({ deny })`，效果是模型请求里的工具声明减少。
但 23 个 bundle 仍在宿主启动时加载，插件模块、计时器、设置面板、SQLite 句柄和事件监听仍然存在。

- 对模型请求：有效。
- 对内存、启动时间、依赖面、潜在故障面：没有根本改善。

建议后续按模式拆 bundle 或把重插件改为真正按需激活，而不是只在模型工具列表里隐藏。

#### 知识库首次同步和首次索引成本高

知识库内容本身是资产，但默认行为包括：

- 20 个 Git 稀疏仓库同步；
- 首次大量文本扫描；
- chunks 索引构建；
- 后台索引进程和独立 SQLite。

这些操作放在后台，不会直接阻塞聊天，但会消耗带宽、磁盘和 CPU。离线护网、弱网环境、临时
应急笔记本上尤其明显。知识同步应默认为“按需/手动或低频”，并提供离线冻结模式和索引预算。

#### 工具描述压缩取得了效果，但仍有天花板

已经把工具描述从早期 111.5K 级别压到当前 60.8K 到 83.7K，收益真实。
但主要仍然在压缩自然语言，没有从 schema 结构上减少：

- 多模式共用工具携带大量模式专属字段；
- redteam/campaign 工具字段数仍然很多；
- 低频大工具没有真正的懒加载；
- 每次会话重新携带全量模式工具。

下一步应从“描述瘦身”升级为“按需工具包 + 短入口 + 详细字段 refs”。

#### route-boost 和动态快照可能随轮次放大

route-boost、method-stack、campaign-memory 等使用结构化 context 注入。
dsh 每轮把 context 作为新消息追加到历史，旧快照不一定被回收。单轮看起来只有 1K 到 3K，
连续 20 到 50 轮就可能变成显著的历史体积。

需要实测“第 1 轮与第 30 轮”的真实请求差异，而不只看首轮。

#### MCP proxy 是正确方向，但小目录可能被过度代理

proxy/auto 对大工具目录能节省大量 token；但对 2 到 5 个工具的小服务，搜索再调用会产生额外
一轮模型交互。应保留 `auto` 阈值，并记录首调用延迟和失败率。

#### UI 面板和轮询数量偏多

当前存在多个设置面板、会话页签和客户端轮询。单个 3 秒、5 秒、15 秒轮询通常不致命，但叠加后
会让 Electro/Web 前端长期活跃。护网时用户通常只关心：当前目标、当前阶段、未收口事项、
最近失败、关键成果，不应让所有插件面板同时展示。

### 4.2 没有发现明显“负优化”的地方

以下设计虽然有成本，但收益明确，不建议回退：

- `tools.restrict`：减少模型工具声明，收益真实。
- MCP auto/proxy：大工具目录下节省非常明显。
- 方法栈默认空：避免默认全量注入。
- session-pulse 默认停用：避免与宿主能力重复。
- SQLite 持久化：比纯内存状态更适合长时任务和压缩后恢复。
- route-boost：对阶段门禁和证据纪律有实际约束价值，但应控制注入频率。

## 5. 护网时是否好用

### 5.1 好用的部分

- 中文操作界面，适合中文应急/护网团队。
- 目标授权、边界、约束和阶段门禁比普通 Agent 完整。
- finding、证据、修复建议、覆盖率、意图台账能形成交付物。
- 支持 FOFA/Hunter/Quake、MCP、WebShell、扫描器和代码审计链路。
- 离线知识库和本地工具路径可配置，适合内网环境。
- MCP 工具代理能避免把几十个工具全部塞给模型。
- Trace Vault 可以回看工具调用，适合复盘。

### 5.2 护网实战的主要风险

1. **没有强隔离执行面。** 工具默认在当前用户权限下运行，误操作、越权或恶意目标可能影响本机。
2. **没有统一任务队列。** 长任务遇到宿主重启、网络中断或模型超时，恢复依赖会话历史而非可恢复作业。
3. **Agent 内部任务状态还不够统一。** 子代理之间没有共享的 job、取消、恢复和结果回收模型，
   每个插件的状态仍相对分散。这不是多真人用户协作，当前单人测试也会受益。
4. **缺少 OPSEC 控制。** 默认云模型和知识同步会产生外部网络请求；没有目标数据脱敏、出站白名单和
   本地模型优先策略。
5. **结果可信度未量化。** 有证据门禁，但没有标准 false-positive 率、目标级成功率、MCP 成功率、
   长任务恢复率等阈值。
6. **上下文会随长战役增长。** 对 32K 模型尤其明显，护网长会话容易进入压缩、遗忘和成本上升区。
7. **操作入口偏多。** 23 个插件、多个设置页和成果页，新操作员需要较长学习时间。
8. **高风险插件缺少统一熔断。** 扫描、爆破、WebShell、数据库等插件各自有约束，但缺少跨插件的
   目标级全局速率、并发和危险操作预算。

## 6. 改进方向

> 当前明确暂缓：独立 Docker/Kali 隔离执行面、本地模型。原因是前者与 dsh 快速变化的宿主契约绑定太深，
> 后者受本机算力限制。以下路线不依赖这两项。

### P0，决定护网可用性

1. **任务队列与恢复**
   - 把长任务从“会话里的自然语言”提升为可查询的 job。
   - 支持 pending/running/succeeded/failed/cancelled、重试、超时、取消和人工接管。
   - 宿主重启后能恢复或明确标记中断。

2. **标准评测基准**
   - 接入 Argus 类 Docker 靶场，或建立 Saker 自己的可重复靶场。
   - 指标至少包括：成功率、误报率、首次有效动作时间、工具失败率、token、成本、恢复率。
   - 评测结果进入 release gate，而不是只看单测通过。

3. **上下文预算与长会话压缩**
   - 首轮、第 10 轮、第 30 轮分别抓包。
   - 对 route-boost、method-stack、campaign-memory 做增量摘要，不只追加完整快照。
   - 为每个模式设置工具定义、消息历史和总上下文三档预算。

4. **OPSEC 与数据边界，不依赖本地模型**
   - 模型出站白名单、目标数据脱敏、知识同步开关。
   - 明确哪些字段允许进入模型、哪些字段只落本地。
   - 维护“冻结知识库”模式，护网期间停止 Git 同步。

### P1，决定长战役效率

5. **按需工具包**
   - 把低频大类工具改成“发现入口 + 调用入口”。
   - 高频工具保持直连，低频工具走 proxy。
   - 不要让模型在同一轮看到所有模式的字段。

6. **知识库从“能搜”升级为“搜得准”**
   - 建立 50 到 100 条真实问题的 ground truth。
   - 先测 FTS5/BM25，再决定是否引入 embedding、reranker 或 knowledge graph。
   - 增加增量索引、索引版本和来源 commit 校验。

7. **统一本地状态与 Agent 内部协作**
   - 至少支持一个统一 campaign database，而不是每个插件独立 SQLite。
   - 保留 Manager / Observer / Solver 之间的状态传递、任务分派和结果回收。
   - 不做多真人用户、RBAC、共享服务端、跨操作员交接和只读观察员。

### P2，决定工程成熟度

8. **可观测性**
   - OpenTelemetry trace、工具延迟、模型调用成本、MCP 连接状态、任务队列状态。

9. **交付格式**
    - 一个稳定的 JSON report schema。
    - HTML/PDF 报告和资产/攻击路径附录。

10. **插件健康度与依赖治理**
    - 插件启动耗时、内存占用、定时器数量、数据库句柄和失败率面板。
    - 对无使用价值的插件做退役，而不是永久保留兼容面板。

11. **UI 精简**
    - 面向护网提供一个“工作台首页”：目标、阶段、开放意图、最近失败、关键成果、待人工确认。
    - 其余插件进入二级页面，不再默认占据首屏。

## 7. 推荐路线

### 第一阶段，保护性和可度量

- 明确隔离和本地模型暂缓，不阻塞其它工作。
- 上标准基准和 release gate。
- 加 OPSEC、脱敏和知识同步冻结开关。
- 抓长会话上下文，建立压缩基线。

### 第二阶段，提升护网效率

- 任务队列和恢复。
- 按需工具包。
- 统一本地 campaign 状态和 Agent 内部任务传递。
- 工作台首页和统一审计视图。

### 第三阶段，扩大专业深度

- 知识图谱/语义检索。
- Agent 内部协作和任务状态传递。
- 报告 schema、PDF/JSON 交付。
- 插件健康度和自动退役。

## 8. 不应优先做的事情

- 不继续单纯堆工具数量。HexStrike 式“150+ 工具”不等于更好的实战效果。
- 不为所有模式增加更多提示词。提示词已经足够多，优先做结构化工具和压缩。
- 不照搬多 Agent 名词，而不解决隔离、状态和评测。
- 不把 RAG 当成万能解。先证明当前 FTS5 在真实护网问题上的召回不足，再做向量层。

## 9. 最终判断

Saker 当前的价值不在“比 PentAGI 更自主”或“比 HexStrike 工具更多”，而在于：

- 更适合中文攻防工作流；
- 更重视授权、边界、证据和交付；
- 更容易接入本地工具和 MCP；
- 已经有实战需要的成果台账和过程留痕。

只要补上任务队列、评测基准、上下文压缩、可观测性和 OPSEC，它可以从“单机安全 Agent 工作台”
升级为“可审计、可评测的单人护网作战平台”。多用户协作与隔离执行面不在当前路线内。

在这些基础设施补齐前，护网中最合适的定位是：

> **人工主导下的侦察、分析、验证、证据整理和报告助手，而不是无人值守的自动化攻击平台。**
