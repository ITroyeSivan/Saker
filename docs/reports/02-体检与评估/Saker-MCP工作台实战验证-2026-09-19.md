## client bundle rev 缓存复验（风险已排除）

先前观察到单一行 rev 在多个宿主重启间看似相同，因此怀疑浏览器缓存会拿到旧 bundle。
本轮直接做了两次独立宿主重启并抓首屏 HTML：

```text
第一次非ce：a15d2eeba1c3ed70-*
第二次 nonce：f9ccf173ad0cffcf-*
```

宿主 `packages/client/modules` 在每次激活时为每个客户端行生成独立随机 initial revision
（`initialRevisionNonce + 行号`），浏览器请求 URL 因此变化；combo 大图则使用内容派生 rev。
连续重启验证未复现“rev 不变却返回新 bytes”的情况，之前记录的风险降级为
**已排除，非缺陷**。

## 模型主动调用 Burp / Yakit 实测

只验证工作台“能握手”不够，本轮补了一条模型级真实调用。隔离宿主、授权本地靶标
`http://127.0.0.1:18081`、临时修好的隔离代理 `8789`，提示模型优先使用
`mcp_search` / `mcp_call` 检查 Burp / Yakit，并用普通 HTTP 做对照。会话
`session-8993a557-1fac-4546-b9d7-cb5f1bc25fe4`。

模型实际执行：

- `mcp_search` 按 `burp` / `yakit` 查询工具目录；
- `mcp_call(burp.send_http1_request)` 直接发真实 HTTP/1.1 请求到靶标，收到
  `200`、`x-saker-fixture: pentest-e2e`，并有 Burp 自身 `Linkfinder (3)` 注释；
- `mcp_call(yakit.send_http_request_packet)` 发 `/health`，Yakit 返回连接耗时、
  真实状态码，并把请求/响应包落盘；模型回读落盘响应验证内容；
- `mcp_call(yakit.send_http_request_by_url)` 发 `/admin?role=user`，返回真实 `403`
  及参数解析后的完整请求包；
- 普通 `pwsh/Invoke-WebRequest` 对 `/`、`/health`、`/admin?role=user` 做对照，
  状态码、长度、响应头和正文四维一致。

模型输出报告：[`_ref/mcp-active-check/mcp-tool-availability-check.md`](E:/工作/WorkBuddy/WebSec/dsh/_ref/mcp-active-check/mcp-tool-availability-check.md)。

结论：模型不是“看见工具名但不会用”，也不是只做本地回显；它主动用 MCP 发了真实请求，
并能把 Burp/Yakit 的响应、落盘包与普通 HTTP 基线对齐。目录数差异也可解释：
工作台显示 `219`（含直连小 fixture），模型侧 `mcp_search` 的代理编目为 `216`
（不含 `fixture-small` 的 3 个直连工具）。
